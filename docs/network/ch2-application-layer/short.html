1. หลักการของแอปเครือข่าย

เขียนโปรแกรมที่รันบน end systems และสื่อสารผ่านเครือข่าย — ไม่ต้องเขียนซอฟต์แวร์ให้อุปกรณ์ใน network core เพราะ router/switch ไม่รันแอปของผู้ใช้ และการอยู่ที่ end systems ทำให้พัฒนาและเผยแพร่แอปได้เร็ว

Client-Server vs P2P ⭐

Server Client
เปิดตลอดเวลา (always-on) ติดต่อและสื่อสารกับ server
IP address ถาวร อาจเชื่อมต่อเป็นช่วง ๆ, IP แบบ dynamic
มักอยู่ใน data center ไม่สื่อสารกันเองโดยตรง

ตัวอย่างโปรโตคอล: HTTP, IMAP, FTP

P2P: ไม่มี server ที่เปิดตลอดเวลา / end systems สื่อสารกันตรง ๆ / peer ขอบริการและให้บริการกลับ → self scalability (peer ใหม่นำความสามารถใหม่มาพร้อมความต้องการใหม่ = ยิ่งคนใช้เยอะยิ่งเร็ว) / peer เชื่อมต่อเป็นช่วง ๆ + เปลี่ยน IP → จัดการซับซ้อน

Client-Server P2P
พึ่งเซิร์ฟเวอร์ สูงมาก ไม่มี
Scalability ต้องเพิ่มเซิร์ฟเวอร์ใน data center self-scaling
การสื่อสารระหว่าง client ผ่านเซิร์ฟเวอร์เท่านั้น โดยตรง
ความซับซ้อน ง่าย (centralized) ซับซ้อนมาก (dynamic IPs)

ตัวอย่างจริง: Client-Server (ใช้มากที่สุด คุมความปลอดภัยง่าย เก็บข้อมูลพฤติกรรมได้) = LINE, Facebook, YouTube, Netflix, Mobile Banking, RoV | P2P = BitTorrent, Bitcoin/Ethereum (blockchain), AirDrop/Quick Share, WebRTC (Zoom, Discord)

Process, Socket, Addressing ⭐

  • process = โปรแกรมที่กำลังรันในโฮสต์ | ในเครื่องเดียวกัน ใช้ IPC (OS กำหนด เช่น Shared Memory) | ต่างเครื่อง ใช้ การแลกเปลี่ยน messages
  • client process = ฝ่ายเริ่ม / server process = ฝ่ายรอ — ⚠️ P2P ก็มีทั้งสองบทบาทในเครื่องเดียว
  • Socket = ประตู — ผู้ส่งผลักข้อความออกประตู แล้วพึ่งโครงสร้างพื้นฐาน transport ให้ส่งถึง socket ผู้รับ (มี 2 sockets ฝั่งละ 1) | นักพัฒนาคุม "ในบ้าน" (application) / OS คุม "นอกบ้าน" (transport, network, link, physical)
  • ⚠️ IP address อย่างเดียวไม่พอ — IP อยู่ L3 ระบุแค่เครื่อง แต่เครื่องเดียวรันหลาย process → ต้องใช้ IP address + port number (+ โปรโตคอล transport) | ภายในเครื่อง OS ใช้ PID 💡 IP = บ้านเลขที่ / Port = หมายเลขห้อง เช่น 128.119.245.12:80 = Web server

แอปกับ Transport Protocol

Application Protocol Transport
file transfer FTP [RFC 959] TCP
e-mail SMTP [RFC 5321] TCP
Web documents HTTP [RFC 7230, 9110] TCP

TCP vs UDP ⭐

TCP UDP
ความน่าเชื่อถือ reliable transport unreliable
Flow control ✅ ไม่ส่งท่วมผู้รับ ❌
Congestion control ✅ ชะลอเมื่อเครือข่ายแน่น ❌
Connection connection-oriented (setup ก่อน) ❌ ไม่มี setup
Timing, throughput guarantee, security ❌ ❌

มี UDP ไว้ทำไม? ไม่มี overhead ของ setup/การรับประกัน จึงเร็วและเบา เหมาะกับแอปที่ยอมข้อมูลหายได้บ้างแต่ต้องการความหน่วงต่ำ (เสียง วิดีโอสด เกม DNS)

TLS

  • Vanilla TCP/UDP sockets ไม่มี encryption — รหัสผ่านวิ่งแบบ cleartext (!) ดักอ่านได้เลย
  • TLS ให้ TCP connection ที่เข้ารหัส + data integrity + end-point authentication
  • ⚠️ TLS implement ใน application layer — แอปใช้ TLS libraries ซึ่งเรียก TCP อีกที

2. Web และ HTTP

  • web page = base HTML file + objects (HTML, JPEG, applet, audio, .css, .js, ฟอนต์) แต่ละชิ้นมี URL และเก็บคนละ server ได้ (เช่น base HTML จาก server-a, รูปจาก CDN, ฟอนต์จาก Google)
  • URL www.someschool.edu/someDept/pic.gif → host name + path name

HTTP Overview

  • HTTP = HyperText Transfer Protocol — ใช้ client/server | client = browser, server = web server (เช่น Apache)
  • ใช้ TCP port 80: 1. client เริ่ม TCP connection → 2. server accept → 3. แลกเปลี่ยน HTTP messages → 4. ปิด TCP connection
  • ⭐ HTTP เป็น "stateless" — server ไม่เก็บข้อมูลเกี่ยวกับ request ในอดีต ทำไม? โปรโตคอลที่เก็บ state ซับซ้อน ต้องเก็บประวัติ และถ้า crash มุมมอง state ของสองฝั่งอาจไม่ตรงกัน 💡 ปลาทองความจำสั้น

HTTP Connections ⭐

Non-persistent HTTP Persistent HTTP (HTTP 1.1)
เปิด TCP → ส่ง object ได้สูงสุด 1 ชิ้น → ปิด เปิด TCP → ส่ง หลาย objects บน connection เดียว → ปิด
โหลดหลาย object = เปิดหลาย connection server เปิด connection ค้างไว้ หลังส่ง response
รถส่งของวิ่งส่ง 1 กล่องแล้วกลับ สายพานส่งหลายกล่องต่อเนื่อง

ตัวอย่าง non-persistent: 1a. client เริ่ม TCP ที่ port 80 / 1b. server accept → 2. client ส่ง request message → 3. server สร้าง response ส่งกลับ → 4. server ปิด TCP → 5. client แสดงผล parse html เจอ jpeg อีก 10 รูป → 6. ทำ 1–5 ซ้ำอีก 10 ครั้ง

Response time ⭐ — RTT = เวลาที่ packet เล็ก ๆ เดินทางไป server และกลับ $$\text{Non-persistent} = 2,RTT + \text{file transmission time}$$ → เสีย 2 RTT ต่อ object 1 ชิ้น! + OS overhead ในการสร้างแต่ละ TCP connection (browser จึงมักเปิดหลาย connection ขนาน) Persistent: client ส่ง request ทันทีที่เจอ object ที่อ้างถึง → ใช้ ~1 RTT สำหรับทุก object (ลด response time ครึ่งหนึ่ง)

3. Cookies ⭐

แก้จุดอ่อนที่ HTTP เป็น stateless ให้ระบบจำได้ว่าผู้ใช้คือใคร

4 องค์ประกอบ:

  1. Header Set-Cookie: ใน HTTP response — server มอบ cookie ID ให้เบราว์เซอร์
  2. ไฟล์ cookie ฝั่ง client — เบราว์เซอร์เก็บไว้บนเครื่อง
  3. Header Cookie: ใน HTTP request — แนบกลับไปอัตโนมัติ
  4. Back-end database ฝั่ง server — ใช้ cookie ID ค้นว่าผู้ใช้คือใคร

ตัวอย่าง Amazon: client มี ebay 8734 อยู่แล้ว → Amazon สร้าง ID 1678 + entry ใน database → ตอบ set-cookie: 1678 → request ถัดไปแนบ cookie: 1678 → cookie-specific action → หนึ่งสัปดาห์ต่อมายังจำได้

ประโยชน์: Session management (จำล็อกอิน) / Shopping cart / User preferences / Tracking & Recommendation

First-party cookies = จากเว็บที่เราตั้งใจเข้า (ให้ base html) — มีประโยชน์แต่ก็ใช้บันทึกประวัติสร้างโปรไฟล์ Third-party tracking cookies = จากเว็บที่เราไม่ได้เลือกเข้า (บริษัทโฆษณา) — หลายเว็บฝังโค้ดเจ้าเดียวกัน → ตามรอยผู้ใช้ข้ามทุกเว็บ → targeted ads

ตัวอย่างการตามรอย (NY Times + AdX.com):

  1. เข้า nytimes.com/sports → Set cookie: 1634 (first-party) + หน้ามีโฆษณา → GET ไป AdX.com พร้อม Referrer: NY Times Sports → Set cookie: 7493 (third-party)
  2. วันถัดมาเข้า socks.com ที่มีโฆษณา AdX → GET พร้อม cookie: 7493 → AdX บันทึก socks.com
  3. อีกวันกลับไป nytimes.com/arts → GET ไป AdX พร้อม cookie: 7493 → AdX แสดงโฆษณาถุงเท้า!
  • Cookie ID ที่ปลอดภัย: สร้างตาม RFC 4122/9562 ด้วย CSPRNG เพื่อสร้าง UUID version 4 (สุ่ม 128 บิต)
  • การติดตามอาจมองไม่เห็น — เป็น invisible link ที่สั่ง HTTP GET ไป tracker

นโยบายเบราว์เซอร์: Firefox (Gecko) บล็อก 100% ผ่าน ETP | Safari (WebKit) บล็อก 100% ผ่าน ITP | Chrome (Blink) ไม่บล็อกทั้งหมด เน้น User Choice + Privacy Sandbox | Edge บล็อกเฉพาะ บัญชีดำ (Known Trackers) GDPR (recital 30, May 2018): IP address และ cookie identifiers ทิ้งร่องรอย เมื่อรวมกับข้อมูลอื่นอาจสร้างโปรไฟล์ระบุตัวได้ → cookie ที่ระบุตัวได้ = ข้อมูลส่วนบุคคล → ผู้ใช้ต้องควบคุมได้ (จึงมี cookie consent popup)

4. Web Caches (Proxy) ⭐

เป้าหมาย: ตอบ request โดยไม่ต้องไปถึง origin server — browser ส่งทุก request ไป cache → อยู่ใน cache ส่งให้เลย / ไม่อยู่ cache ขอจาก origin server แล้วเก็บไว้ Web cache เป็นทั้ง client (ของ origin server) และ server (ของ client ที่ขอมา) Server บอก cache ว่าเก็บได้นานเท่าไหร่: Cache-Control: max-age=<seconds> | Cache-Control: no-cache (ต้องถาม server ทุกครั้ง) ทำไมต้อง cache: ลด response time (อยู่ใกล้กว่า) / ลด traffic บน access link / ช่วยให้ content provider รายเล็กงบน้อย ส่งเนื้อหาได้มีประสิทธิภาพ

ตำแหน่ง cache 4 แบบ:

ตำแหน่ง หน้าที่
1. Client-side / Browser cache ดิสก์หรือ RAM ของผู้ใช้ — เข้าซ้ำโหลดทันที
2. Institutional / Forward proxy ใน LAN องค์กร (ก่อนถึง access router) — คนอื่นดึงจาก cache ได้ ไม่ต้องวิ่งออก access link
3. ISP edge / CDN cache edge node ของ ISP/CDN (Cloudflare, Akamai) — ลด RTT
4. Server-side / Reverse proxy หน้า origin server — รับภาระส่ง static assets แทน

Forward proxy (ฝั่ง client): ซ่อน IP ผู้ใช้, บล็อกเว็บ, caching ในองค์กร | Reverse proxy (ฝั่ง server): load balancing, ป้องกันการโจมตี, cache ไฟล์คงที่

ตัวอย่างคำนวณ Caching ⭐⭐

Scenario: access link 1.54 Mbps | RTT ไป server 2 sec | object 100K bits | request rate 15/sec | avg data rate 1.50 Mbps | LAN 1 Gbps

สภาพเดิม (ไม่มี cache):

  • Access link utilization = 1.50/1.54 ≈ 0.97 (97%) | LAN utilization = 1.50/1000 = 0.0015
  • Transmission delay = 100K/1.54M ≈ 0.065 s
  • End-end delay = 2 sec + minutes + usecs → utilization สูงมาก → queueing delay มหาศาล

Option 1: ซื้อลิงก์เร็วขึ้น (154 Mbps): utilization = 1.50/154 ≈ 0.0097, delay เหลือ msecs → แต่แพง!

Option 2: ติดตั้ง web cache (ถูก!) — cache hit rate = 0.4

  • traffic ผ่าน access link เหลือ 60%: 1.50 × 0.60 = 0.90 Mbps → intensity = 0.90/1.54 ≈ 0.58 → ตัด queueing delay ทิ้งได้ $$\text{Avg Delay} = \text{HitRate} \times \text{Delay}{hit} + \text{MissRate} \times \text{Delay}{miss}$$
  • Hit (40%): จาก LAN → ≈ 0 s | Miss (60%): 2 + 0.065 = 2.065 s
  • Average Delay = 0.4 × 0 + 0.6 × 2.065 ≈ 1.24 วินาที — ดีกว่าและถูกกว่าซื้อลิงก์ 154 Mbps!

⚠️ ตัวเลขที่ต้องจำ: 0.97 → 0.0097 → 0.58; delay ≈ 1.24 s

Conditional GET ⭐

ไม่ส่ง object ถ้า browser มีเวอร์ชันใน cache ที่ยังใหม่

  • client: If-modified-since: <date>
  • server: ไม่เปลี่ยน → HTTP/1.0 304 Not Modified (ไม่มีเนื้อหาไฟล์) | เปลี่ยนแล้ว → 200 OK + <data>

5. HTTP/2, HTTP/3, QUIC

ปัญหาของ HTTP/1.1: มี pipelined GETs หลายตัวบน TCP เดียว แต่ server ตอบ ตามลำดับ (FCFS) → object เล็กต้องรอ object ใหญ่ข้างหน้า = head-of-line (HOL) blocking + loss recovery ทำให้การส่งหยุดชะงัก (ทุกอย่างวิ่งบน TCP เส้นเดียว แพ็กเก็ตหาย TCP หยุดส่งทั้งหมด)

HTTP/2 [RFC 7540, 2015]: ใช้ multiplexing หั่นไฟล์เป็น frame เล็ก ๆ ส่งสลับกัน

  • methods, status codes, header fields ส่วนใหญ่ไม่เปลี่ยน → นักพัฒนาไม่ต้องเขียนเว็บใหม่
  • ลำดับการส่งตาม priority ที่ client กำหนด (ไม่ต้อง FCFS) | push object ที่ client ยังไม่ขอได้
  • แบ่ง object เป็น frames + schedule สลับกัน → ลด HOL blocking (O2, O3, O4 ถึงเร็วขึ้น, O1 ช้าลงเล็กน้อย)

HTTP/3: HTTP/2 แก้ HOL ได้ แต่ยังติด retransmission บน TCP เส้นเดียว + ไม่มี security บน vanilla TCP → HTTP/3 เพิ่ม security + error/congestion control แยกต่อ object บน UDP

Stack Application Transport
HTTP/2 over TCP HTTP/2 + TLS TCP
HTTP/3 HTTP/2 (slimmed) + QUIC UDP

QUIC = Quick UDP Internet Connections — โปรโตคอล application-layer บน UDP ใช้ใน Google servers, YouTube, Search, Maps, Gmail, Facebook, Instagram, WhatsApp, Uber, Spotify, Netflix

TCP + TLS QUIC
TCP handshake (reliability, congestion control) แล้วตามด้วย TLS handshake (authentication, crypto) reliability, congestion control, authentication, crypto ทำพร้อมกัน
2 serial handshakes 1 handshake (1-RTT)

QUIC 0-RTT: ตอนจบ connection แรก server ส่ง TLS session ticket → client cache ไว้ → connection ที่สองใช้ ticket เดิม → ส่ง data ได้ทันที = 0 RTT 💡 TCP+TLS = แลกบัตรที่ป้อมยาม + สแกนนิ้วอีกด่าน / QUIC 1-RTT = ด่านเดียว / QUIC 0-RTT = มีบัตรผ่านถาวรแล้ว

7. E-mail

3 องค์ประกอบ: User agents (mail reader: Outlook, iPhone mail) | Mail servers (mailbox = ข้อความขาเข้า, message queue = ขาออกที่รอส่ง) | SMTP (ใช้ ระหว่าง mail servers)

SMTP [RFC 5321]: ใช้ TCP port 25 ส่งอย่างเชื่อถือได้ | ส่งตรง (direct transfer) server ผู้ส่ง → server ผู้รับ 3 phases: 1. handshaking (greeting) → 2. transfer of messages → 3. closure command/response แบบเดียวกับ HTTP — commands = ASCII text (HELO), response = status code + phrase ตัวอย่าง code: 220 พร้อมให้บริการ, 250 Hello ตอบรับ HELO, 354 Start mail input

Alice ส่งถึง Bob 6 ขั้น: 1. Alice เขียนด้วย UA → 2. UA ส่งไป mail server ของ Alice เข้า message queue → 3. SMTP client ที่ server ของ Alice เปิด TCP กับ server ของ Bob → 4. ส่งข้อความ → 5. server ของ Bob วางลง mailbox → 6. Bob เปิด UA อ่าน

Message format: RFC 5321 = SMTP (โปรโตคอล) / RFC 2822 = syntax ของตัวอีเมล | โครงสร้าง header → blank line → body

  • header lines: To:, From:, Subject: — ⚠️ ต่างจากคำสั่ง SMTP MAIL FROM:, RCPT TO:! | body = ASCII characters only

Mail access protocols: SMTP = push (ส่งไป server ผู้รับ) / mail access protocol = pull (ดึงจาก server)

SMTP POP3 IMAP [RFC 3501]
ส่ง (push) รับเฉพาะ ASCII 7-bit (แนบไฟล์ด้วย MIME) ดาวน์โหลดแล้วลบทิ้ง อ่านจากเซิร์ฟเวอร์ ซิงก์โฟลเดอร์หลายอุปกรณ์ (ดึง ลบ จัดโฟลเดอร์บน server)

Gmail, Hotmail, Yahoo ให้ web interface โดยใช้ SMTP ส่ง และ IMAP/POP ดึง

8. DNS ⭐⭐

DNS = distributed database ที่ implement เป็นลำดับชั้นของ name servers + application-layer protocol ที่ hosts กับ DNS servers ใช้ resolve ชื่อ ⚠️ เป็นฟังก์ชันหลักของอินเทอร์เน็ต แต่ implement เป็น application-layer protocol — ความซับซ้อนอยู่ที่ "edge"

  • UDP port 53 | บริการ: hostname → IP translation, host aliasing, mail server aliasing, load distribution (หลาย IP ต่อชื่อเดียว)

ทำไมไม่รวมศูนย์: single point of failure / traffic volume มหาศาล / distant centralized database / maintenance ยาก → มันไม่ scale! (Comcast DNS อย่างเดียว 600B queries/วัน, Akamai 2.2T queries/วัน)

ลำดับชั้น: Root → TLD (.com, .org, .edu) → Authoritative (yahoo.com, amazon.com…) ตัวอย่าง: ถาม root → ได้ .com server → ถาม .com → ได้ amazon.com server → ถาม → ได้ IP

ประเภท รายละเอียด
Root name servers "contact-of-last-resort" — อินเทอร์เน็ตทำงานไม่ได้หากไม่มี! | DNSSEC ให้ authentication + message integrity | ICANN ดูแล | 13 logical root servers (a–m.root-servers.net) แต่ละตัว replicate หลายชุด
TLD servers .com, .org, .net, .edu + โดเมนประเทศ | Network Solutions = .com/.net | Educause = .edu
Authoritative DNS server ขององค์กรเอง ให้ mapping hostname → IP ที่เป็นทางการ
Local DNS โฮสต์ถามที่นี่ก่อน — ตอบจาก local cache (อาจล้าสมัย!) หรือส่งต่อเข้า hierarchy | ทุก ISP มี (scutil --dns / ipconfig /all) | ⚠️ ไม่ได้อยู่ในลำดับชั้นอย่างเคร่งครัด

Iterated vs Recursive ⭐

Iterated query Recursive query
server ตอบกลับด้วยชื่อ server ที่ควรไปถามต่อ ("ไม่รู้ แต่ลองไปถามคนนี้") ภาระการ resolve อยู่ที่ server ที่ถูกถาม มันไปถามต่อเองจนได้คำตอบ
local DNS วิ่งไปถาม root → TLD → authoritative เอง ปัญหา: ภาระหนักที่ระดับบนของ hierarchy

⚠️ โดยทั่วไป host → local DNS เป็น recursive แต่ local DNS → root/TLD/authoritative เป็น iterated ลำดับ iterated 8 ขั้น: host → local → root → (ตอบ TLD) → local → TLD → (ตอบ authoritative) → local → authoritative → (ตอบ IP) → local → host

Caching: name server ที่เรียนรู้ mapping จะ cache ไว้ → ลด response time | cache หมดอายุตาม TTL | TLD servers มักถูก cache | ⚠️ cache อาจล้าสมัย — โฮสต์เปลี่ยน IP อาจไม่รู้ทั่วอินเทอร์เน็ตจน TTL หมด = best-effort name-to-address translation!

DNS Records (RR) — format (name, value, type, ttl) ⭐

type name value
A hostname IP address
NS domain hostname ของ authoritative name server
CNAME alias name canonical (ชื่อจริง) name (www.ibm.com → servereast.backup2.ibm.com)
MX domain ชื่อ SMTP mail server

💡 A = Address, NS = Name Server, CNAME = Canonical NAME, MX = Mail eXchanger

DNS protocol messages (query และ reply รูปแบบเดียวกัน): identification 2 bytes (16 bit) (reply ใช้หมายเลขเดียวกัน) | flags 2 bytes (query/reply, recursion desired, recursion available, reply is authoritative) | # questions/answer RRs/authority RRs/additional RRs | questions, answers, authority, additional info

จดโดเมนใหม่ (Network Utopia): 1. จดชื่อที่ DNS registrar → registrar ใส่ NS และ A RRs ลง .com TLD server: (networkutopia.com, dns1.networkutopia.com, NS) + (dns1.networkutopia.com, 212.212.212.1, A) → 2. สร้าง authoritative server เอง มี record A สำหรับ www และ MX สำหรับโดเมน

DNS Security: DDoS root (ยังไม่เคยสำเร็จ — มี traffic filtering + local DNS cache IP ของ TLD จึง bypass root ได้) | DDoS TLD อันตรายกว่า | Spoofing — ดักจับ query แล้วส่งคำตอบปลอม → DNS cache poisoning → ป้องกันด้วย RFC 4033: DNSSEC

9. Video Streaming & CDNs

บริบท: Netflix + YouTube + Amazon Prime = 80% ของ traffic ISP ตามบ้าน (2020) | ความท้าทาย = scale (~1B คน) + heterogeneity (มีสาย vs มือถือ) → ทางแก้ = โครงสร้างพื้นฐานแบบ distributed, application-level

Video coding: video = ลำดับภาพที่อัตราคงที่ (24 ภาพ/วินาที) | ใช้ ความซ้ำซ้อน (redundancy) ลดบิต

  • Spatial coding (ภายในภาพ): ส่ง สี + จำนวนครั้งที่ซ้ำ แทนค่าสีทั้ง N ค่า
  • Temporal coding (ระหว่างภาพ): ส่งแค่ส่วนที่ต่างจากเฟรมก่อน
  • CBR (อัตราคงที่) vs VBR (เปลี่ยนตามปริมาณ coding) | MPEG1 1.5 Mbps / MPEG2 3–6 Mbps / MPEG4 (บนอินเทอร์เน็ต) 64 Kbps–12 Mbps

ความท้าทาย streaming: bandwidth เปลี่ยนตามเวลา ตาม congestion → packet loss/delay → เล่นช้าหรือคุณภาพแย่ | continuous playout constraint (timing ต้องตรงต้นฉบับ แต่ network delay แปรผัน = jitter) → ต้องมี client-side buffer | client interactivity (pause, fast-forward, rewind) Playout buffering: ส่งแบบ constant bit rate → ผ่าน delay ที่แปรผัน → client รับไม่สม่ำเสมอ → เก็บใน buffer → เล่นแบบ constant bit rate หลังรอ playout delay ตัวอย่าง: ที่เวลา t0 มาถึง 6 chunks เล่นไป 2 chunks → buffer มี 4 chunks

DASH (Dynamic, Adaptive Streaming over HTTP) ⭐

  • Server: แบ่งไฟล์เป็น chunks → แต่ละ chunk encode หลายอัตรา (360p, 720p, 1080p, 4K) เก็บคนละไฟล์ → replicate ไปหลาย CDN nodes → มี manifest file ให้ URL ของ chunk
  • Client: ประเมิน bandwidth เป็นระยะ → อ่าน manifest → ขอทีละ chunk เลือกอัตราสูงสุดที่ bandwidth รองรับ เปลี่ยนอัตราและ server ได้ระหว่างทาง
  • ⭐ "ความฉลาด" อยู่ที่ client — ตัดสินใจ เมื่อไหร่ขอ chunk (ไม่ให้ buffer หมด/ล้น), rate ไหน, ขอจากที่ไหน

Streaming video = encoding + DASH + playout buffering

CDN ⭐

  • Option 1 "mega-server" ตัวเดียว: single point of failure + จุด congestion + เส้นทางไป client ไกล → ไม่ scale
  • Option 2 (CDN): เก็บหลายสำเนาที่หลายไซต์กระจายตามภูมิศาสตร์
Enter deep Bring home
ดัน CDN servers ลึกเข้าไปใน access networks จำนวนมาก — ใกล้ผู้ใช้มาก cluster ใหญ่จำนวนน้อย (หลักสิบ) ใน POPs ใกล้ access nets — จัดการง่ายกว่า
Akamai (240,000 servers ใน >120 ประเทศ ปี 2015) Limelight

Akamai today: 360K servers, 100+ M hits/วินาที, 7+ trillion deliveries/วัน, 175+ Tbps, 4,200+ locations, 135 countries Netflix: เก็บสำเนาที่ OpenConnect CDN nodes ทั่วโลก → ผู้ใช้ขอ → ส่ง manifest file กลับ → client ดึงที่อัตราสูงสุดที่รองรับได้ (เปลี่ยนสำเนาได้ถ้าเส้นทางแน่น) OTT ("over the top") = สร้างบริการ "บน" อินเทอร์เน็ตโดยไม่ได้เป็นเจ้าของเครือข่าย — ความท้าทาย: เนื้อหาไหนควรวางที่ CDN node ไหน? ดึงจาก node ไหน? ที่อัตราเท่าไหร่?

10. Socket Programming

socket = ประตูระหว่าง application process กับ end-end transport protocol (ฝั่ง app คุมโดย developer, ฝั่งล่างคุมโดย OS) 2 ชนิด: UDP = unreliable datagram | TCP = reliable byte stream-oriented ตัวอย่างแอป: client อ่านบรรทัดจากคีย์บอร์ด → ส่งไป server → server แปลงเป็นตัวพิมพ์ใหญ่ → ส่งกลับ → client แสดงผล UDP socket: ไม่มี connection / ไม่มี handshaking | ผู้ส่งแนบ IP ปลายทางและ port# ไปกับทุกแพ็กเก็ตเอง | ผู้รับดึง IP และ port# ของผู้ส่งออกจากแพ็กเก็ต | ข้อมูลอาจหายหรือมาถึงไม่เรียงลำดับ

จุดที่มักออกสอบ (สรุปเร็ว)

  1. Client-server vs P2P (self-scalability, dynamic IP); P2P ก็มี client/server process
  2. Process ระบุด้วย IP + port (IP อย่างเดียวไม่พอ) — ในเครื่องใช้ PID
  3. TCP (reliable, flow, congestion, connection-oriented) vs UDP — ทั้งคู่ไม่ให้ timing, throughput guarantee, security
  4. TLS implement ที่ application layer
  5. HTTP ใช้ TCP port 80 และ stateless
  6. Non-persistent = 2RTT + transmission time ต่อ object / persistent ≈ 1 RTT รวม
  7. Methods: GET (ข้อมูลใน URL หลัง ?), POST (entity body), HEAD, PUT | Status: 200, 301, 304, 400, 404, 505
  8. Cookies 4 องค์ประกอบ + first/third-party + GDPR
  9. คำนวณ caching: 0.97 → 0.0097 (ลิงก์เร็ว, แพง) → 0.58 (cache), delay ≈ 1.24 s
  10. Conditional GET: If-modified-since → 304 Not Modified
  11. HOL blocking (FCFS) → HTTP/2 (frames, priority, push) → ยังติด TCP retransmission → HTTP/3 = QUIC over UDP
  12. QUIC: 1-RTT (แทน 2 handshakes) และ 0-RTT ด้วย session ticket
  13. Ports: 21 FTP, 22 SSH, 23 Telnet, 25 SMTP, 53 DNS, 80 HTTP, 110 POP3, 143 IMAP, 443 HTTPS
  14. SMTP = push (port 25, 3 phases, ASCII) / IMAP-POP3 = pull; RFC 5321 = SMTP, RFC 2822 = message format
  15. DNS: hierarchy (Root 13 logical, ICANN → TLD → Authoritative), local DNS ไม่อยู่ใน hierarchy, iterated vs recursive, TTL → best-effort
  16. RR types: A, NS, CNAME, MX
  17. DNS security: DDoS root (bypass ด้วย cache TLD), DDoS TLD อันตรายกว่า, cache poisoning → DNSSEC
  18. Streaming = encoding + DASH + playout buffering; DASH: ความฉลาดอยู่ที่ client
  19. CDN: enter deep (Akamai) vs bring home (Limelight); Netflix = OpenConnect
