ส่วน A — Software Engineering Foundation

1. Business Need → Business Process → Software Development ⭐

ขั้น ความหมาย
Business needs แรงผลักดัน (driving force) — สิ่งที่ธุรกิจอยากได้ อยากแก้
Business processes การลงมือทำเพื่อตอบความต้องการ (execution of needs)
Software development ช่วยให้ business process ทำงานได้ (enabling) และ ดีขึ้น (improving)

Business Process: เน้นคำถาม "งานนี้ทำให้เสร็จได้อย่างไร"

  • องค์ประกอบ 4 อย่าง: Actors / Tasks-activities / Rules / Inputs and outputs
  • วาดด้วย BPMN (Business Process Model and Notation) | ⭐ อาจมีหรือไม่มีระบบมาช่วยก็ได้ (จองโต๊ะทางโทรศัพท์ก็เป็น business process)
  • Software development ช่วย: ทำให้ efficient, accurate, scalable + digitised, automated, improved

💡 Need = อยากได้อะไร / Process = ทำอย่างไร / Software = ช่วยทำให้ดีขึ้น

2. Software คืออะไร ⭐

องค์ประกอบ 3 ส่วน (Pressman):

  1. Instructions (โปรแกรม) — ชุดคำสั่งที่ให้ features, function, performance
  2. Data structures — โครงสร้างข้อมูล
  3. Documents — เอกสารอธิบายการทำงานและวิธีใช้ ⚠️ มักออกสอบ: เอกสารก็นับเป็นส่วนหนึ่งของ software

Interaction Hierarchy: ผู้ใช้ → แอป → OS → hardware

ลักษณะของ Software อธิบาย
Developed / engineered, not manufactured สร้างด้วยการออกแบบและพัฒนา ต้นทุนหลักอยู่ที่การพัฒนา การ copy แทบไม่มีต้นทุน
Intangible จับต้องไม่ได้ → วัดความคืบหน้าและคุณภาพยาก
Labour intensive ต้นทุนหลักคือคน
Difficult to make changes แก้จุดหนึ่งอาจกระทบหลายจุด
Does not wear out ไม่สึกหรอ
Can be obsolete ⭐ แต่ล้าสมัยได้ (Windows XP หมดอายุ 2014, Windows 7 หมดอายุ 2023)

⚠️ ไม่ wear out ≠ ใช้ได้ตลอดไป — XP ไม่ได้พังเอง แต่ไม่มี security update ประเภทแอป: Productivity (Word, Canva, Notion) / Communication (Zoom, Slack, Teams) / Media (VLC, Photoshop) / Education (Duolingo, Coursera) / Business (QuickBooks, Salesforce, SAP) "Software is eating the world" — Marc Andreessen (ร้านหนังสือแพ้ Amazon, แท็กซี่ถูกแทนด้วย Grab) 7 Trends 2026: AI in SD, Low-Code, DevSecOps, Cloud/Azure, .NET Core, DevOps, Offshore

3. Software Engineering คืออะไร ⭐

"A process of solving customers' problems by the systematic development and evolution of large, high-quality software systems within cost, time and other constraints." (Lethbridge)

วลี ความหมาย
Solving customers' problems เป้าหมาย — ไม่ใช่แค่เขียนโค้ดให้รัน
Systematic development and evolution ความเป็นวิศวกรรม — เป็นขั้นตอน + ดูแลต่อเนื่อง
Large, high-quality software systems ความซับซ้อนสูงมาก
Cost, time and other constraints ข้อจำกัด

5 ด้านที่ต้องคำนึง (Tsui & Karam): 1. Technical and business processes 2. Specific methodologies and techniques 3. Product characterization and metrics 4. People skills and teamwork 5. Project coordination and management 💡 มีแค่ข้อ 2 ที่เกี่ยวกับเทคนิคจริง ๆ — SE จึงไม่ได้มีแค่การเขียนโค้ด

4. ทำไมต้องมี SE — การ์ตูน "Tree Swing"

ลูกค้าอธิบาย (ชิงช้า 3 ชั้น) → PM เข้าใจ (ตัดกลางต้นไม้) → SA ออกแบบ (ใช้งานไม่ได้) → Programmer เขียน (ไม่ติดต้นไม้) → เอกสาร (ว่างเปล่า) → ติดตั้งจริง (มีแค่เชือก) → เรียกเก็บเงิน (รถไฟเหาะ) → ที่ลูกค้าต้องการจริง ๆ = ยางรถยนต์ผูกเชือกธรรมดา ⭐ บทเรียน: ปัญหาส่วนใหญ่มาจากการสื่อสารและ requirement ที่ไม่ชัด ไม่ใช่เพราะเขียนโค้ดไม่เป็น

5. ปัจจัยของโครงการซอฟต์แวร์ ⭐

ต้องบาลานซ์ 4 อย่าง: Scope – Time – Cost – Quality โครงการที่ดีต้องมี: clear objectives and goals / requirement ชัดเจน / stakeholder มีส่วนร่วม / executive management support / realistic planning / บริหารจัดการดี

✅ Key success factors ❌ Top failure reasons
User involvement Lack of user input
Executive management support Incomplete requirements
Clear requirement statements Changing requirements
Proper planning

สัดส่วนชนิด defects: Code errors 38.33% > Design errors 24.17% > Documentation 13.33% > Requirements 12.50% > Bad-fix errors 11.67% 💡 ⭐ สาเหตุล้มเหลวอันดับต้น ๆ เป็นเรื่อง requirement ทั้งหมด แม้ requirement error มีแค่ 12.5% ของบั๊ก แต่ผลกระทบใหญ่ถึงขั้นทำให้ทั้งโครงการล้มได้

Estimation: ต้องประมาณ effort / cost / time-scheduling Requirements: ใช้ กำหนด (define) และ ระบุคุณสมบัติ (qualify) ของระบบ — ⭐ ลูกค้าเป็นคนกำหนด โดยมีวิศวกรช่วย

ชนิด ความหมาย
Functional ระบบต้องทำอะไร
Non-functional ระบุคุณภาพของ functional
Design constraints ข้อจำกัดของการออกแบบ/implement (ภาษา แพลตฟอร์ม)

Roles — ฝั่งลูกค้า:

บทบาท หน้าที่
Customers กำหนด business needs, ออกเงิน (fund), อนุมัติผลงานสุดท้าย
End users ใช้ซอฟต์แวร์จริง, ให้ feedback เรื่อง usability และ functionality

⚠️ Customer ≠ End user (มหาวิทยาลัยจ่ายเงิน = customer / นักศึกษาใช้ = end user)

Roles — ฝั่งพัฒนา:

บทบาท หน้าที่หลัก
Project Manager (PM) วางแผน, กำหนด scope, จัดตาราง, จัดสรรทรัพยากร, ติดตาม, บริหารความเสี่ยง, ประสาน stakeholder
Business Analyst (BA) elicit, วิเคราะห์, ตรวจสอบ requirement (business, functional, non-functional), ทำ requirement spec, ⭐ เป็นสะพานระหว่างลูกค้ากับทีมพัฒนา
System Analyst (SA) ⭐ แปลง requirement เป็น technical specification, ออกแบบสถาปัตยกรรม, เลือกเทคโนโลยี, กำหนด coding standard
Software Developer เขียน/ดูแลโค้ด, unit test, แก้ defect, review, integrate
UX/UI Designer user research, persona, wireframe, mockup, prototype
QA Engineer / Tester test plan, test case, ทดสอบ, รายงาน defect

💡 ⭐ BA อยู่ฝั่งธุรกิจ ถามว่า "ต้องการอะไร" / SA อยู่ฝั่งเทคนิค ตอบว่า "จะสร้างด้วยอะไร อย่างไร"

6. Technical vs Non-technical Issues

Technical: (1) Process and Methodology (เลือก process เช่น waterfall/agile, methodology, เครื่องมือ) (2) Technology and tools (platform, language, database, network, configuration management) Non-technical: (1) Effort Estimation and Scheduling — ระบบใหญ่ขึ้นต้องประมาณมากขึ้น, ประสาน pre-requisite / co-requisite, ความเสี่ยงมากขึ้น (2) Assignments and Communications — คนมากขึ้น ทักษะหลากหลาย สื่อสารมากขึ้น ผิดพลาดมากขึ้น

⭐ เพิ่มคนแล้วงานเสร็จเร็วขึ้นไหม? ไม่เสมอไป เพราะเส้นทางการสื่อสารเพิ่มเร็วกว่าจำนวนคน

จำนวนคน เส้นทางการสื่อสาร
2 1
4 6
6 15

สูตร: n(n−1)/2 (10 คน = 45 เส้นทาง)

7. Size and Complexity ⭐

Breadth issue (ความกว้าง): จำนวน major functions / features ในแต่ละ function / interfaces ระหว่าง features และ functions / interfaces ไปยังระบบภายนอก / จำนวนผู้ใช้พร้อมกันและทั้งหมด Depth issue (ความลึก): ระดับการ nesting / จำนวน chained relationships ⭐ ยิ่งกว้างและลึก ความซับซ้อนยิ่งพุ่งขึ้น (แค่เพิ่มการรอสัญญาณและแตกเงื่อนไข จำนวนเส้นทางที่ต้องออกแบบและทดสอบก็เพิ่มทันที)

8. Implementation, Testing, Supporting

Coding Conventions ครอบคลุม: การจัดไฟล์, ย่อหน้า, comment, ประกาศตัวแปร, statement, white space, การตั้งชื่อ, programming practices, principles, architectural best practices หลักที่ควรทำ 5 ข้อ: Be consistent / Choose names carefully / Test before using / Know the libraries / Do code reviews

Testing ใครทำ / ทำอย่างไร
Acceptance testing ⭐ ถ้าไม่ผ่าน ลูกค้าปฏิเสธโปรแกรม
Unit testing โปรแกรมเมอร์ทดสอบแต่ละชิ้นย่อย
Black-box ทดสอบโดยไม่รู้โค้ดข้างใน ดู data validation
White-box ทดสอบตามเส้นทางในโค้ด

💡 Black-box = หยอดเหรียญดูว่าน้ำออกไหม / White-box = เปิดฝาดูวงจรทุกเส้น

Supporting: ก่อนปล่อย (จำนวนผู้ใช้ที่คาด, ปัญหาที่รู้อยู่และคุณภาพที่คาด, ปริมาณการอบรม, จำนวนรอบการแก้ไข) | หลังปล่อย (Call center, แก้ปัญหาใหญ่และแก้โค้ด, ปรับปรุงฟังก์ชัน)

9. Software Quality

ตัวชี้วัด: Usability / Efficiency / Testability / Maintainability / Reusability — คำถาม: เราจะวัดสิ่งเหล่านี้อย่างไร? (ยากเพราะ software จับต้องไม่ได้) คุณภาพในมุมของแต่ละคน: User (ใช้ง่าย ไม่ล่ม เร็ว) / Customer (คุ้มเงิน ตอบโจทย์ธุรกิจ) / PM (เสร็จทันเวลา ในงบ บั๊กน้อย) / Developer (โค้ดอ่านง่าย แก้ง่าย ทดสอบง่าย)

12. Project & Triple Constraint ⭐

PMBOK: "A temporary endeavour undertaken to create a unique product, service, or result"

Project Operations
ชั่วคราว มีจุดเริ่มและจุดจบ งานประจำเพื่อให้ธุรกิจดำเนินต่อ (sustain the business)
จบเมื่อบรรลุเป้าหมาย หรือถูกยกเลิก ทำซ้ำไปเรื่อย ๆ
สร้างแอปจองโต๊ะ พนักงานรับจองโต๊ะทุกวัน

Project Attributes 7 ข้อ: 1. Has a unique purpose 2. Temporary 3. Drive change 4. Enable value creation 5. Require resources 6. Has customer or sponsor 7. Involves uncertainty

⭐ Triple Constraint: Scope – Cost – Time ตาชั่ง: Scope อยู่ข้างหนึ่ง / Cost + Time อีกข้าง — เปลี่ยนด้านหนึ่ง อีกด้านต้องปรับตาม

  • เพิ่ม scope → ต้องเพิ่มเวลาหรือเงิน | ลดเวลา → ต้องเพิ่มเงิน (เพิ่มคน) หรือลด scope

13. Project Management & 10 Knowledge Areas ⭐

นิยาม: การประยุกต์ใช้ความรู้ ทักษะ เครื่องมือ และเทคนิคกับกิจกรรมของโครงการ เพื่อให้ได้ตาม requirement ทำไมต้องบริหารโครงการ? ⭐ ทุกโครงการ ไม่ว่าเล็กหรือใหญ่ ต้องการ project management เพราะต้องมี planning, organizing, status monitoring, adjustment (= ที่มาของ POMA) Framework (PMBOK): รับความต้องการของ stakeholder → จัดการด้วย 10 knowledge areas → ใช้เครื่องมือและเทคนิค → โครงการสำเร็จ → portfolio → องค์กรสำเร็จ

14. PM & Stakeholders

PM: ทำงานใกล้ชิดกับ stakeholder โดยเฉพาะ sponsor และทีมโครงการ / ต้องรู้จักทั้ง 10 knowledge areas / ใช้เครื่องมือและเทคนิคได้หลากหลาย Stakeholders = คนที่มีส่วนร่วมหรือได้รับผลกระทบจากกิจกรรมของโครงการ: project sponsor/customer, ธนาคารและสถาบันการเงิน, PM, project team (เทคนิคและไม่ใช่เทคนิค), support staff, suppliers

15. POMA ⭐⭐

⚠️ ภาพใหญ่ (macro) ดูเป็นลำดับขั้น แต่ในระดับย่อย (micro) วนซ้ำได้มาก

P — Planning (7 ขั้น): 1. เข้าใจ requirement → 2. กำหนดเป้าหมายที่ วัดผลได้ → 3. ประมาณ work effort → 4. ประมาณ schedule → 5. ประมาณ ทรัพยากร → 6. กำหนดการจัดสรรทรัพยากร → 7. ระบุและวิเคราะห์ ความเสี่ยง (people, process, tools, facilities) ➜ ผลลัพธ์: Project Plan

O — Organizing (4 ขั้น): 1. ออกแบบ โครงสร้างองค์กร ของทีม → 2. จ้างคน → 3. จัด การศึกษาและการอบรม → 4. ตั้ง กลไกติดตาม (risk tracking and mitigation, ติดตามเป้าหมาย)

M — Monitoring (3 ส่วน): 1. เก็บข้อมูลสถานะโครงการ → 2. วิเคราะห์และประเมิน → 3. นำเสนอและสื่อสารสถานะ

A — Adjusting: แทบเป็นไปไม่ได้ที่โครงการจะไม่มีปัญหาเลย — เมื่อสถานะบอกว่าอาจมีปัญหา ต้องกล้าเปลี่ยน อย่ากลัว

  • ⭐ ปรับได้ 3 ด้าน: Resources / Schedule / Project content (scope) = ตรงกับ Cost / Time / Scope ของ triple constraint

⚠️ จุดที่มักสับสน:

Project Management Process (POMA) Development Process / Life Cycle
บริหารโครงการ: วางแผน จัดคน ติดตาม ปรับ สร้างซอฟต์แวร์: requirement, design, code, test, deploy
ครอบทั้งโครงการ (umbrella) งานเทคนิคที่อยู่ใต้การบริหาร

16. Tools & Techniques ⭐

ด้าน เครื่องมือ
Scope Project charter, Scope statement, WBS
Time Gantt charts, Network diagrams, Critical path analysis
Cost Cost estimates, Earned value management

เครื่องมือจริง: Asana, Trello, Zoho Projects, Monday.com, ClickUp, Basecamp, Wrike, Microsoft Teams, Jira, Slack

ขั้นตอนสร้าง WBS 7 ขั้น ⭐

  1. กำหนด project scope (จะมี function อะไรบ้าง)
  2. ระบุ major deliverables — Project Management, Requirements Analysis, UI/UX Design, Development, Testing, Deployment, Training & Documentation
  3. แตก deliverable เป็น sub-deliverables (เช่น Development → Login & registration, Book borrow, Book return, Fine calculation)
  4. เรียงลำดับ task — Sequential (ต้องทำต่อกัน) / Parallel (ทำพร้อมกันได้)
  5. ประมาณเวลาของแต่ละ task
  6. มอบหมายผู้รับผิดชอบ
  7. วาง timeline ของโครงการ

ลำดับชั้น WBS: ระบบ → Module → Function → Task PERT (Program Evaluation and Review Technique): แผนภาพแสดง ลำดับและความสัมพันธ์ของ task พร้อมเวลา (Task 1, 2 ทำก่อนตามลำดับ / กลุ่ม 3, 4, 5 มีงานย่อย a, b, c ที่ ทำขนานกันได้) End Result of WBS = Initial Schedule Estimate (ใครทำ task ไหน นานเท่าไร)

ข้อสังเกตจากตัวอย่าง:

  • งานขนานกัน → กลุ่มเสร็จเมื่องานที่นานที่สุดในกลุ่มเสร็จ
  • เวลารวม = 12 + 2 + 8 + 20 + 5 = 47 units (ถ้าทำทีละงานต่อกันจะใช้ 62 units → การทำขนานช่วยย่นเวลา)
  • ⭐ งานที่นานที่สุดในแต่ละช่วง (1 → 2 → 3a → 4a → 5a) = critical path — ถ้างานบนเส้นทางนี้ช้า โครงการทั้งหมดช้าตาม
  • คนเดียวกันต้องไม่ถูกจ่ายงานซ้อนกันในช่วงเวลาเดียวกัน

Gantt Chart: แผนภูมิแท่งแนวนอน แกนตั้ง = task, แกนนอน = เวลา → เห็นทันทีว่างานไหนเริ่ม/จบเมื่อไร งานไหนซ้อนกัน และช้ากว่าแผนไหม

17. ความสำเร็จ ข้อดี เป้าหมาย

Project Success วัดได้ 3 แบบ: 1. ได้ตาม scope, time, cost 2. ลูกค้า/sponsor พอใจ 3. ได้ตามเป้าหมายหลัก (ทำเงิน/ประหยัดเงิน, ROI) Top 3 success factors: Adequate funding / Staff expertise / Engagement from all stakeholders Advantages 9 ข้อ: ควบคุมทรัพยากรดีขึ้น / ความสัมพันธ์กับลูกค้าดีขึ้น / เวลาพัฒนาสั้นลง / ต้นทุนต่ำลง productivity สูงขึ้น / คุณภาพและความน่าเชื่อถือสูงขึ้น / กำไรมากขึ้น / ประสานงานภายในดีขึ้น / บรรลุเป้าหมายเชิงกลยุทธ์ / ขวัญกำลังใจของทีมดีขึ้น Goals of SPM 5 ข้อ: 1. Satisfy customers' needs 2. Project attributes are met 3. Target & milestones are met 4. Team members work effectively 5. Tools & resources are made available and effectively utilized

คู่ที่มักสับสน

คู่ ต่างกันที่
Customer / End user จ่ายเงินและอนุมัติ / ใช้งานจริง
BA / SA requirement ฝั่งธุรกิจ / technical spec และสถาปัตยกรรม
Functional / Non-functional ทำอะไร / ทำได้ดีแค่ไหน
Black-box / White-box ไม่ดูโค้ด / ดูเส้นทางในโค้ด
Project / Operations ชั่วคราว มีวันจบ / งานประจำต่อเนื่อง
Wear out / Obsolete software ไม่สึก / แต่ล้าสมัยได้
Project Management Process / Software Development Process บริหารโครงการ (POMA) / สร้างซอฟต์แวร์ (life cycle)

แนวคิดที่ต้องอธิบายได้

  • ทำไมเพิ่มคนแล้วงานอาจไม่เร็วขึ้น → เส้นทางการสื่อสารเพิ่มแบบ n(n−1)/2 และโอกาสผิดพลาดเพิ่มตาม
  • ทำไมระบบใหญ่ถึงยาก → มีทั้งความกว้าง (function, interface, user) และความลึก (nesting, chained relationships)
  • ทำไมทุกโครงการต้องมี project management → ทุกโครงการต้องวางแผน จัดองค์กร ติดตาม และปรับแก้
  • ถ้า triple constraint ด้านหนึ่งเปลี่ยน → scope เพิ่ม ต้องเพิ่มเวลาหรือเงิน หรือลดคุณภาพ
  • ในขั้น Adjusting ปรับได้ 3 ด้าน: resources, schedule, project content
