📖 อ่านฉบับเต็ม

1. QA vs QC (สไลด์ 4)

  • ⭐ QA = all activities to measure & improve quality ของ product + process | QC = verify quality ของ product + detect faults | ทั้งคู่ต้องมี process, tools, team ที่ดี

2. Error detection 6 วิธี (สไลด์ 5–11)

วิธี หลัก ตัวอย่าง
⭐ Code review ตรวจโค้ด ก่อนรัน inspection, peer review, walkthrough (author อธิบาย), static analysis
⭐ Testing รัน แล้วดูพฤติกรรม unit, integration, system, acceptance, regression
⭐ Static analysis ไม่รัน syntax/type, unused var, unreachable code, smells, security, null-pointer, coding standards
⭐ Dynamic analysis ขณะรัน runtime error, memory leak, performance, debugging, coverage, profiling
Debugging หาสาเหตุ หลังเห็น error breakpoints, step-by-step, variable inspection, logging/tracing, stack trace
Formal methods คณิตศาสตร์ formal spec, model checking, theorem proving, formal verification
  • Debug: Identify failure → Reproduce → Locate cause → Fix defect → Test again

3. Quality, V&V (สไลด์ 12–14)

  • Quality = conforms to requirements + fit to use
  • ⭐ Verification = ผล phase ตรง requirement ของ phase ก่อน → "building the software right?"
  • ⭐ Validation = ตอนจบ ตรง intended usage → "building the right software?"
  • V: Requirements↔Acceptance (validation) | High-level design↔System, Detailed design↔Integration, Coding↔Unit (verification)

4. Fault / Error / Failure (สไลด์ 15)

  • ⭐ Fault = static defect | Error = incorrect internal state | Failure = external incorrect behavior
  • fault ≈ design mistake ในฮาร์ดแวร์ | ซอฟต์แวร์ไม่เสื่อม

5. Testing (สไลด์ 16–19)

  • ประเมินคุณภาพ + หา defect ก่อน release | dynamic verification บน test case จำนวนจำกัด | ⭐ พิสูจน์ 100% ไม่ได้
  • Progression: Unit → Functional → Component → System/Regression
  • ⭐ Who: programmers, testers, users | What: unit, functional, integration/system, UI | Why: acceptance, conformance, configuration, performance/stress | How: intuition, spec (black-box), code (white-box), regression, faults

6. Black-box (สไลด์ 20–21)

  • behavioral / functional | จาก functional requirements | ที่ interface
  • ⭐ หา: function ผิด/ขาด, interface, data structure/DB access, behavior/performance, initialization/termination
  • เทคนิค: ECP, BVA

7. ECP (สไลด์ 22–26)

แก่น: แบ่ง class → ตัวแทน 1 ค่า (พังตัวเดียว = พังทั้ง class)

  • Largest: F>S (10,7) | S>F (8,12) | F=S (6,6)
  • Age 18–56: valid 18–56 | invalid ≤17 | invalid ≥57
  • Ex1 (1–1000): ≤0 ✗ | 1–1000 ✓ | ≥1001 ✗
  • Ex2 (75, 253, 414): 3 ค่านี้ ✓ | อื่น ✗
  • ⭐ Ex3 ตั๋ว: <0 ✗ | 1–11 Free | 12–17 100 | 18–60 200 | >60 100 (⚠️ อายุ 0 ตกหล่น)

8. BVA (สไลด์ 27–30)

แก่น: ขอบ error ง่าย → ECP + boundary, +1, −1

  • ⭐ reduced: ขอบอยู่ระหว่างเลข (12 → 12, 13 แทน 11, 12, 13) | ~3 case/class | ordinal เท่านั้น
  • ตาราง: All cases → Belonging (อยู่ใน class) → Reduced (ค่าขอบ class)
  • ⭐ Ex4 (1–1000): 0 ✗, 1 ✓, 1000 ✓, 1001 ✗
  • ⭐ Ex5 ตั๋ว reduced: −1 Error | 0, 11 Free | 12, 17 → 100 | 18, 60 → 200 | 61 → 100 (⚠️ สไลด์เขียน class "> 61")

9. White-box (สไลด์ 31–32)

  • glass-box / structural | control structure
  • ⭐ รับประกัน: ทุก independent path ≥ 1 ครั้ง | ทุก decision true/false | ทุก loop ที่ขอบ + ภายใน | internal data structures
  • Path analysis: นับ path + เลือก path | ⭐ coverage มาก→น้อย: logical > independent > branch > statement

10. Paths (สไลด์ 33–38)

  • ⭐ #independent paths = #decision + 1 (cyclomatic) | linearly independent = ทุก path มี edge ใหม่ ≥ 1
  • ขั้นตอน: คำนวณ → list ทุก path → เลือกชุด independent
  • if เดียว: (1,4), (1,2,3) | CASE 3 decision → 4 paths | loop: (1,4), (1,2,3,4)
  • ⭐ 3 decision เรียงกัน: logical = 2³ = 8 | independent = 4 เช่น (1,2,4,6,9), (1,2,4,6,8), (1,2,4,5,7,9), (1,3,6,9)
  • Exercise FindLar_3: 3 decision → 4 (สไลด์ไม่มีเฉลย)

11. Stop testing (สไลด์ 39–40)

  • ⭐ รัน test ที่วางแผนครบ + แก้ปัญหาครบ | หรือ หา error ไม่เจอแล้ว | defect seeding | problem find rate ลดลงตามวัน

12. Inspections vs Testing (สไลด์ 41–42)

Inspections Testing
cost-effective หา error ถูก แต่ แก้แพง
ใช้กับ intermediate artifacts โค้ดเท่านั้น
จับ early จับ late (หลัง implement)
กระจายความรู้ จำเป็นต่อการวัดคุณภาพ
  • ทั้งคู่ใช้ทำ V&V ได้

คู่ที่มักสับสน

A B ต่างกัน
QA QC product + process vs product + หา fault
Verification Validation software right vs right software
Fault Error defect นิ่ง vs state ผิดตอนรัน
Error Failure ข้างใน vs ข้างนอก
Static Dynamic ไม่รัน vs รัน
Black-box White-box spec vs code
ECP BVA ตัวแทน vs ขอบ
Logical paths Independent paths 2ⁿ vs #decision + 1
Inspection Testing early, เอกสารได้ vs late, โค้ดเท่านั้น
