📖 อ่านฉบับเต็ม

1. Programming paradigms (สไลด์ 4)

แก่น: imperative = how | declarative = what | OOP = object (data + behavior) | logic = ปัญหาคืออะไร

  • ⭐ Imperative (C, Python, Java, JS) | Declarative (SQL) | OOP (Java, Python, C++, C#, Ruby) | Logic (Prolog) | หลาย paradigm = multi-paradigm

2. No-code / Low-code / Vibe coding (สไลด์ 5–7)

แก่น: ลดการเขียนโค้ดเอง ทุกแบบ "Dependence on platform/tool"

No-code Low-code Vibe coding
วิธี ไม่เขียนโค้ด, drag-and-drop, logic blocks visual tools + เขียนโค้ดบ้าง ภาษาธรรมชาติ + AI + live feedback
⭐ Benefits เร็ว, technical barrier ต่ำ, ทำ prototype ง่าย เร็วกว่าเขียนเอง, สมดุลง่าย/ยืดหยุ่น barrier ต่ำ, เร็ว interactive
⭐ Limitations logic ซับซ้อนยาก, พึ่ง tool, scale/customize ลึกยาก ต้องมีความรู้เทคนิค, customize ซับซ้อนดูแลยาก, พึ่ง tool logic ซับซ้อนยาก, พึ่ง tool, overreliance on AI

3. Implementation (สไลด์ 9–12)

แก่น: แปลง detailed design → valid program | โค้ดดีต้องสมดุล 6 อย่าง

  • Fowler (1999): โค้ดที่ดีคือโค้ดที่ คน เข้าใจ
  • ⭐ Writing code → Unit testing → Debugging → Configuration management
  • ⭐ Good implementations: Readability, Maintainability, Performance, Traceability, Correctness, Completeness

4. Style guides & rules (สไลด์ 13–22, SE at Google ch.8)

แก่น: กฎส่งเสริม "ดี" กัน "ไม่ดี" (นิยามตามองค์กร) | 3 กลุ่มกฎ

  • กฎเรื่อง: ที่เก็บ source file, formatting, naming/patterns/exceptions/threads | องค์กรควรมี style guide
  • "ดี" อาจ = memory น้อย / runtime optimization / ใช้ feature ใหม่ / consistency
  • ⭐ Avoid dangers (static, lambda, exceptions, threading, access control, inheritance, vocabulary types, hard-to-use) | Enforce best practices (เช่น ต้อง comment ที่ไหน) | Ensure consistency (โฟกัสที่สิ่งที่โค้ดทำ)
  • ⭐ Consistency: 1 enables scaling (tools) | 2 human scaling (ย้ายโปรเจกต์) | 3 resilience to time
  • ตัวอย่าง: catch แล้วไม่ทำอะไร → ต้อง log/rethrow AssertionError หรือ comment เหตุผล (ยกเว้น test ที่ชื่อ expected) | // หรือ /* */ ให้สม่ำเสมอ | empty block {} ได้ ยกเว้น multi-block (try/catch) | indent +2

5. Good practices (สไลด์ 23)

  • ⭐ Functions เล็ก ทำเรื่องเดียว (Extract Method) | DRY (แก้ 3 ที่ ลืม 1) | เขียนให้คนอ่าน | Handle errors explicitly | Commit small & often | Test as you write (ไม่งั้น test ว่าทำอะไร แทน ควรทำอะไร)

6. Code comments 9 rules (สไลด์ 25–35, Ellen Spertus)

แก่น: ข้อ 1–4 อย่าใช้ผิด | ข้อ 5–9 บอกสิ่งที่โค้ดบอกไม่ได้

  1. ⭐ ไม่ซ้ำโค้ด (i = i + 1; // Add one to i ✗)
  2. comment ไม่ใช่ข้ออ้างของโค้ดไม่ชัด (n → bestNode, currentNode)
  3. เขียน comment ให้ชัดไม่ได้ = โค้ดมีปัญหา (Kernighan's Law: debug ยากกว่าเขียน 2 เท่า)
  4. ลดความสับสน ไม่ใช่เพิ่ม (RIPJSB ข้าง 1750)
  5. อธิบาย unidiomatic code (value == null || value.equals(null))
  6. ลิงก์ที่มาของโค้ดที่ copy (Stack Overflow) → รู้ปัญหา ผู้เขียน เหตุผล ความเห็น ยังใช้ได้ไหม ปรับยังไง
  7. ลิงก์ external reference (RFC 4180 → \r\n)
  8. ⭐ comment ตอนแก้ bug (Firefox 2, issue #1425)
  9. ⭐ mark งานไม่เสร็จด้วย TODO

7. Debugging (สไลด์ 36–37)

แก่น: หาและแก้ error | พบจาก testing, inspection, use

  • ⭐ Stabilization (reproduction) → Localization → Correction → Verification
  • Heuristics: บาง routine error เยอะ | มี error แล้วมักมีอีก | โค้ดใหม่ error มาก | บางภาษา/ส่วน/คน
  • Tools: code comparators, lint, interactive debuggers, special libraries, profilers, pre/post conditions, test coverage

8. Refactoring (สไลด์ 38–43)

แก่น: ปรับ internal structure โดยไม่เปลี่ยน external behavior (Fowler)

  • ⭐ ไม่ใช่การเปลี่ยนอะไรก็ได้ | ไม่ใช่ rewrite from scratch | ไม่ใช่ restructuring ใด ๆ | รองรับ emergent design | เล็กหรือใหญ่ก็ได้
  • ⭐ Smells: duplicated code, long method, large class, switch statement, feature envy, intimacy
  • ⭐ Actions: extract method, substitute algorithm, move method, extract class (refactoring.com/catalog)
  • ตัวอย่าง: if ยาว → isMacOs, isIE, wasResized | discountedPrice(basePrice, seasonDiscount, fees) → discountedPrice(basePrice)

9. Code inspection (สไลด์ 45–48)

แก่น: Fagan (IBM) 1976 เพิ่มคุณภาพ + productivity | 6 ขั้น

  • ⭐ ผลสำรวจ n=508: Code Review 27% > Unit Testing 19% > Functional 13% > CI 12% > Integration 9% > Detailed Req 7% > Other 5% > Static Analysis 3% = Training 3% > User Stories 2% > Demo Days 1%
  • ใช้ได้กับ code, design, requirements, user info, documentation, test plans/cases
  • Fagan graph: with inspections ใช้คนมากขึ้นช่วง design/coding แต่ peak ช่วง testing ต่ำกว่า และ ship เร็วกว่า
  • ⭐ Planning (entry criteria, คน, ที่/เวลา) → Overview (อธิบาย, มอบ role) → Preparation (ศึกษา) → Inspection (หา defect, ไม่หาทางแก้) → Rework (author แก้) → Follow-up (moderator/ทีมยืนยัน ไม่มี secondary defect)

10. Modern code review (สไลด์ 49–52)

แก่น: review ใน tool (GitHub, Gerrit, Phabricator) วน author ↔ reviewers จน accepted

  • Initial code → Reviewers → Reviewed changes → Author → Reworked changes → Reviewers → Accepted
  • Motivation (มาก→น้อย): Code improvements > Find defects > knowledge transfer > alternative solutions > improve process > avoid breaking builds > team awareness > shared ownership > team assessment
  • ⭐ Google 6 benefits: correctness | comprehensible | consistency | team ownership | knowledge sharing | historical record

11. Checklist 10 หมวด (สไลด์ 53–56)

  • ⭐ Implementation | Dependencies (docs/config/readme, backward compatibility) | Security & Data Privacy (authn/authz, sensitive data) | Logic Errors & Bugs | Error Handling & Logging (user-friendly message) | Testing & Testability | Readability (smaller methods) | Usability & Accessibility (API documented) | Performance | Experts Opinion (security/usability expert, ทีมอื่น)

12. Discussion (สไลด์ 57)

  • PR แก้ bug ทำงานถูก แต่: ตัวแปร x = ยอดเงิน | ไม่มี comment | logic ซ้ำ 2 method | ไม่มี unit test → โยงกับ Readability, Rule 8, DRY/Duplicated code, Testing (สไลด์ไม่มีเฉลย)

13. Conclusion (สไลด์ 58)

  • โค้ดดี = คนอื่นอ่าน ดูแล ไว้ใจได้ | comment อธิบาย intent | review = ความรับผิดชอบร่วม
  • ⭐ ถามก่อน commit: team lead อ่านตอนนี้สบายใจไหม? | อีก 6 เดือนไม่มี context ยังเข้าใจไหม?
