1. Requirements Analysis ⭐

⭐ Analysis model เป็น "สะพาน" เชื่อมจาก requirement ที่เป็นข้อความ ไปสู่การออกแบบระบบ (ถ้าไม่มีสะพานนี้ นักออกแบบต้องตีความข้อความเอง ซึ่งผิดพลาดง่าย)

Requirements Analysis ทำอะไร:

  • ระบุลักษณะการทำงาน (operational characteristics) ของซอฟต์แวร์
  • ขยายรายละเอียด requirement พื้นฐานจากขั้น elicitation
  • ระบุ interface ของซอฟต์แวร์กับส่วนอื่นของระบบ
  • สร้างโมเดล (user scenarios, functional activities, ความสัมพันธ์ของ class, data flow)
  • กำหนดข้อจำกัด ที่ซอฟต์แวร์ต้องทำตาม
  • ⭐ มักทำโดย Business Analyst (BA)

Objectives 3 ข้อ: 1. อธิบายว่าลูกค้าต้องการอะไร 2. วางรากฐานสำหรับการออกแบบ 3. กำหนดชุด requirement ที่ validate ได้

2. Requirements Modeling Approaches — 5 แบบ ⭐

โมเดล แสดงอะไร แผนภาพ
Scenario-based requirement จาก มุมมองผู้ใช้ (actors) Use case diagram, narrative
Class models class, attribute, operation แบบ OO และความสัมพันธ์ Class diagram
Flow models การเคลื่อนที่ของข้อมูลและการแปลงข้อมูลระหว่าง process DFD (L6–L7)
Behavioral models ซอฟต์แวร์ตอบสนองต่อ event อย่างไร State diagram
Data models information domain ของปัญหา ER diagram

💡 Scenario = ใครทำอะไร / Class = มีของอะไร / Flow = ข้อมูลไหลไปไหน / Behavior = เกิดเหตุแล้วทำอะไร / Data = ข้อมูลสัมพันธ์กันอย่างไร

3. Scenario-based Models

  • อธิบายว่า actor จะมีปฏิสัมพันธ์กับระบบอย่างไรในสถานการณ์เฉพาะ
  • ⭐ เน้น functional requirements จากมุมมองของ actor
  • ⭐ มีประโยชน์ในการ validate requirement กับ stakeholder เพราะอ่านเข้าใจง่าย

Jacobson: "Use-cases are simply an aid to defining what exists outside the system (actors) and what should be performed by the system (use cases)." 💡 ⭐ actor อยู่นอกระบบ ส่วน use case อยู่ในระบบ

4. ขั้นตอน Requirements Analysis and Modeling — 5 ขั้น

  1. วิเคราะห์ functional requirements เพื่อเข้าใจโครงสร้างของ problem domain
  2. แยกโครงสร้างเป็นส่วน ๆ เพื่อเข้าใจธรรมชาติ ความสัมพันธ์ และหน้าที่
  3. ระบุพฤติกรรมของระบบและ functional requirements จากมุมมองของ stakeholder
  4. เขียน พัฒนา และปรับปรุง use case diagram และ narrative
  5. ยืนยันว่าโมเดลตอบความต้องการของ stakeholder ทุกฝ่าย

5. จะเขียนอะไรใน Use Case

การประชุมเก็บ requirement ใช้เพื่อ: ระบุ stakeholders / กำหนดขอบเขตของปัญหา / ระบุเป้าหมายการทำงานโดยรวม / จัดลำดับความสำคัญ / ร่าง functional requirements / อธิบายสิ่งของ (objects) ที่ระบบจะจัดการ ➜ ⭐ จุดเริ่มของการเขียน use case: ลิสต์ฟังก์ชันหรือกิจกรรมที่ actor แต่ละคนทำ

6. System Concepts ⭐

แนวคิด นิยาม
Use case ลำดับขั้นตอน (scenario) ที่สัมพันธ์กันเชิงพฤติกรรม ทั้งอัตโนมัติและทำด้วยมือ เพื่อทำงานธุรกิจหนึ่งอย่างให้สำเร็จ — อธิบายจากมุมมองผู้ใช้ภายนอกด้วยคำที่ผู้ใช้เข้าใจ
Use case diagram แผนภาพแสดงปฏิสัมพันธ์ระหว่างระบบกับระบบภายนอกและผู้ใช้ — บอกว่าใครใช้ระบบและใช้แบบไหน
Use case narrative คำอธิบายเป็นข้อความของ business event และวิธีที่ผู้ใช้โต้ตอบกับระบบ

⚠️ ⭐ 1 use case = 1 business task — "จองตั๋ว" เป็น use case ได้ แต่ "กดปุ่มถัดไป" ไม่ใช่

7. สัญลักษณ์พื้นฐาน ⭐

สัญลักษณ์ รูป กฎการตั้งชื่อ
Use case วงรี (ellipse) ⭐ ขึ้นต้นด้วยคำกริยา (verb) เช่น Book a ticket
Actor คนก้าง (stickman) ใส่ชื่อ actor
System boundary กล่อง ใส่ชื่อระบบ

⭐ actor อยู่นอกกล่อง / use case อยู่ในกล่อง / เส้นทึบเชื่อมกัน 💡 ตั้งชื่อ use case แบบ กริยา + กรรม เสมอ — "Register patient" ไม่ใช่ "Patient registration" หรือ "Registration page"

8. Use Case Relationships ⭐⭐

ระดับ ความสัมพันธ์ อยู่ระหว่าง ใช้ทำอะไร
High-level Association actor ↔ use case แสดงว่า actor มีปฏิสัมพันธ์กับ use case
Detailed Inheritance actor ↔ actor ย้ายพฤติกรรมร่วมไปไว้ที่ abstract actor เพื่อลดความซ้ำซ้อน
Detailed Includes use case ↔ use case ทำ use case ใหญ่ให้เรียบง่าย โดยดึงพฤติกรรมที่ใช้ร่วมกันออกมา
Detailed Extends use case ↔ use case เพิ่มพฤติกรรมเสริม (optional) ให้ base use case

Association: เส้นทึบ ไม่มีหัวลูกศร — actor 1 คนสัมพันธ์กับหลาย use case ได้ (Customer → Browse Items, Place Order) และ use case 1 อันสัมพันธ์กับหลาย actor ได้ (Manage Account ← Customer, Bank) 💡 ⭐ Actor ไม่จำเป็นต้องเป็นคน อาจเป็นระบบภายนอก เช่น Bank หรือ payment gateway

Inheritance: ย้ายพฤติกรรมที่เหมือนกันของหลาย actor ไปไว้ที่ abstract actor ตัวอย่างห้องสมุด: Visitor และ Patron ต่างมีเส้นไป "Search library inventory" → ซ้ำซ้อน → สร้าง abstract actor "Library User" ถือ use case ที่ใช้ร่วม แล้วให้ทั้งคู่สืบทอด (Visitor ยังมี Apply for membership, Patron ยังมี Borrow items) ✏️ ตาม UML ใช้ เส้นทึบ หัวลูกศรสามเหลี่ยมโปร่ง ชี้จาก actor ลูกไปหา actor แม่

Includes: ⭐ ลูกศรเส้นประ เริ่มจาก base ชี้ไปที่ use case ที่ถูกเรียกใช้ ติดป้าย <<includes>> ตัวอย่าง: Checkout → Scan Item, Calculate Total and Tax, Payment (ทำทุกครั้ง) | ATM: Deposit Funds และ Withdraw Cash ต่าง ต้อง ยืนยันตัวตน จึงแยก Customer Authentication ออกมาใช้ร่วม

Extends: ⭐ ลูกศรเส้นประ เริ่มจาก use case ที่มาเสริม (extending) ชี้ไปที่ base ติดป้าย <<extends>> ตัวอย่าง: Registration สมบูรณ์ด้วยตัวเอง อาจเสริมด้วย Get Help On Registration ซึ่งเป็นทางเลือก

⚠️ Includes vs Extends — จุดที่สับสนที่สุด ⭐⭐

<<includes>> <<extends>>
ความหมาย ต้องทำเสมอ เป็นส่วนหนึ่งของ base ทำหรือไม่ทำก็ได้ (optional)
base ขาดส่วนนี้ได้ไหม ไม่ได้ ไม่สมบูรณ์ ได้ ยังสมบูรณ์ในตัวเอง
ทิศลูกศร ⭐ base ──► included ⭐ extending ──► base
จุดประสงค์ ลดความซ้ำ / แยก use case ใหญ่ เพิ่มทางเลือกหรือกรณีพิเศษ
ตัวอย่าง Withdraw Cash ──► Customer Authentication Get Help On Registration ──► Registration

💡 เทคนิคจำทิศลูกศร — อ่านเป็นประโยค:

  • Withdraw Cash ──includes──► Authentication = "ถอนเงิน รวม การยืนยันตัวตน" ✅
  • Get Help ──extends──► Registration = "ขอความช่วยเหลือ ขยาย การลงทะเบียน" ✅ ⭐ ทดสอบง่าย ๆ: "ทุกครั้งที่ทำ A ต้องทำ B ไหม?" — ต้อง = include / แค่บางครั้ง = extend

9. การสร้าง Use Case — 6 ขั้น ⭐

ขั้น ทำอะไร
1. Identify the system boundary ตัดสินว่าจะโมเดลระบบอะไร วาดกล่องแทน scope
2. Identify the actors primary (ใช้ระบบโดยตรงเพื่อบรรลุเป้าหมาย เช่น customer) / secondary (บทบาทสนับสนุน เช่น payment service)
3. Identify use cases ลิสต์งานหลักหรือเป้าหมายที่ actor อยากทำ ต้องแทน functional requirements
4. Establish relationships เชื่อม actor กับ use case ที่เริ่มหรือมีส่วนร่วม + พิจารณาชนิด (include, extend, inheritance)
5. Draw a use case diagram actor นอกกล่อง, use case ในกล่อง
6. Review and refine เช็กว่าครอบคลุมทุก functional requirement และ validate กับ stakeholder

💡 ⭐ วิธีหา actor และ use case จากโจทย์ข้อความ:

  • คำนามที่เป็นคน ตำแหน่ง หรือระบบภายนอก → actor
  • คำกริยาที่ actor ทำกับระบบ → use case
  • สิ่งที่ระบบทำเองอัตโนมัติระหว่างทาง (เช่น "ระบบคำนวณราคา") มักเป็นขั้นตอนใน narrative หรือ include ไม่ใช่ use case ที่มี actor เป็นเจ้าของ

10. Use Case Narrative ⭐

คำอธิบายเป็นข้อความอย่างละเอียด ทีละขั้นตอน (step-by-step) มักเขียนเป็นตาราง

ช่อง ความหมาย
Use Case Name ⭐ ต้องตรงกับชื่อใน use case diagram
Primary Actor ผู้ใช้หรือระบบที่โต้ตอบกับ use case นี้
Goal in Context เป้าหมายหรือจุดประสงค์
Precondition เงื่อนไขที่ต้องเป็นจริงก่อนเริ่ม
Trigger ⭐ เหตุการณ์ที่ทำให้ use case เริ่ม
Scenario ลำดับปฏิสัมพันธ์ปกติ — เรียก "main flow" / "basic flow"
Exception จะเกิดอะไรถ้ามีบางอย่างผิดพลาด (error, input ไม่ถูกต้อง)
Postcondition สภาพของระบบหลัง use case เสร็จ

⚠️ ⭐ Precondition ≠ Trigger — Precondition = สภาพที่ต้องเป็นจริงอยู่แล้ว ("ผู้ใช้ login แล้ว") / Trigger = เหตุการณ์ที่เริ่ม use case ("ผู้ใช้กดปุ่มซื้อตั๋ว")

ตัวอย่าง (Zoo Ticketing):

Field Content
Use Case Name Purchase Ticket Online
Primary Actor Visitor
Goal in Context ซื้อตั๋วล่วงหน้า ได้ตั๋วพร้อม Booking ID และ QR Code
Precondition ผู้ดูแลระบบกำหนดราคาและรอบไว้แล้ว; ผู้เยี่ยมชมเข้าสู่ระบบแล้ว
Trigger ผู้เยี่ยมชมกดเมนู "ซื้อตั๋ว"
Scenario 1. เลือกวันที่ 2. เลือกประเภทบัตรและจำนวน 3. ระบบแสดงราคารวม 4. เลือกชำระเงิน 5. ระบบยืนยัน 6. ระบบออกตั๋วพร้อม Booking ID + QR Code
Exception 1a. วันที่เต็ม/ปิดทำการ → ให้เลือกวันใหม่
5a. ชำระเงินไม่สำเร็จ → ลองใหม่หรือเปลี่ยนช่องทาง
Postcondition บันทึกการจองในระบบ; ได้ตั๋วพร้อม Booking ID และ QR Code

11. แนวทางแบบฝึกหัด

Zoo Ticketing System:

Actor Use cases
Visitor (primary) Purchase Ticket Online, View Ticket Status, Request Ticket Cancellation
Ticket Staff (primary) Sell Ticket at Counter, Manage Ticket Order
Administrator (primary) Manage Visit Rounds, Manage Ticket Prices, Manage Staff Accounts, Generate Sales Report
Payment Gateway (secondary) Make Payment, Process Refund

เหตุผลการออกแบบ:

  • Make Payment ถูก include จากทั้งซื้อออนไลน์และขายหน้าเคาน์เตอร์ เพราะต้องจ่ายเงินทุกครั้ง
  • Process Refund ถูก include จาก Request Ticket Cancellation / แต่กับ Manage Ticket Order ใช้ extend เพราะเจ้าหน้าที่อาจแค่ตรวจ/แก้ไขโดยไม่คืนเงิน
  • "ระบบแสดงราคา" เป็นแค่ขั้นตอนใน scenario ไม่ใช่ use case แยก

POS ร้านคริสต์มาส: Apply Discount = extend (ไม่ได้ใช้ส่วนลดทุกการขาย) | Calculate Total, Receive Payment, Issue Receipt, Update Stock = include (เกิดทุกการขาย) | การแจ้งเตือนสินค้าหมด เขียนเป็น exception ใน narrative หรือ extend "Alert Out of Stock" ⚠️ Login: หลายตำราไม่นิยม include login กับทุก use case แต่ให้เขียนเป็น precondition แทน

คู่ที่มักสับสน

คู่ ต่างกันที่
⭐ Include / Extend ทำเสมอ, base → included / optional, extending → base
Association / Include เส้นทึบ actor–use case / เส้นประ use case–use case
Inheritance / Include ระหว่าง actor / ระหว่าง use case
Primary / Secondary actor ใช้ระบบเพื่อเป้าหมายตัวเอง / สนับสนุน (payment service)
⭐ Precondition / Trigger สภาพที่เป็นจริงอยู่แล้ว / เหตุการณ์ที่เริ่ม
Scenario / Exception ทางปกติ / ทางเมื่อผิดพลาด
Use case diagram / Narrative ภาพรวมทุก use case / รายละเอียดทีละ use case

แนวคิดที่ต้องอธิบายได้

  • ทำไมต้องมี analysis model ก่อน design → เป็นสะพานที่ทำให้ requirement ข้อความกลายเป็นโครงสร้างชัดเจน ที่ทั้ง stakeholder validate ได้และนักออกแบบใช้ต่อได้
  • ทำไม scenario-based model ดีต่อการ validate กับ stakeholder → มองจากมุมของผู้ใช้และใช้คำที่ผู้ใช้เข้าใจ
  • ทำไมใช้ inheritance → ลดเส้นซ้ำซ้อนเมื่อหลาย actor ทำ use case เดียวกัน
  • ทำไมใช้ include → ไม่ต้องเขียนพฤติกรรมที่ใช้ร่วมกันซ้ำ (เช่น authentication) และทำ use case ใหญ่ให้อ่านง่าย
  • โจทย์วาด diagram: หา actor จากคำนามที่เป็นคน/ระบบภายนอก, หา use case จากกริยา, ตัดสิน include/extend ด้วยคำถาม "ต้องทำทุกครั้งไหม?"
อ่านจบแล้ว ลองทดสอบความเข้าใจ
