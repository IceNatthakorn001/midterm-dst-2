2. ทำไมต้องอธิบาย Process ⭐

⭐ DFD บอกแค่ว่า process รับอะไรและส่งอะไรออก แต่ไม่บอกว่าคำนวณอย่างไร (เช่น "Calculate Gross Pay" รับ Hours Worked + Pay Rate → ส่ง Gross Pay แต่ไม่บอกว่าเกิน 40 ชม. คิด OT ไหม) → ถ้าไม่อธิบาย programmer ต้องเดาเอง

เครื่องมือ 3 อย่าง: 1. Process Specification (PSPEC) 2. Structured English 3. Decision Table

3. Process Specification (PSPEC) ⭐

PSPEC = เอกสารอธิบาย process หนึ่งตัวใน DFD (โดยเฉพาะ primitive process ระดับล่างสุด) 5 รูปแบบ: narrative / pseudocode (PDL) / equations / tables / diagrams & charts 💡 PDL = Program Design Language (pseudocode ที่ผสมภาษาอังกฤษกับโครงสร้างโปรแกรม)

ตัวอย่าง Analyze Triangle — แบบ Narrative:

  1. รับค่า A, B, C ที่เป็นความยาวด้าน
  2. ตรวจว่าค่าทั้งหมดเป็นบวก ถ้าเจอค่าติดลบให้ส่ง error message
  3. ถ้าข้อมูลถูกต้อง ตรวจว่าเป็นสามเหลี่ยมได้จริงไหม
  4. ถ้าได้ ระบุชนิด: equilateral (ด้านเท่า) / isosceles (หน้าจั่ว) / scalene (ด้านไม่เท่า)
  5. ส่ง ชนิดสามเหลี่ยม ออก

แบบ PDL (pseudocode):

read side dimensions;
if any dimension is negative then produce error message;
if the largest dimension is less than the sum of the others
then
    determine number of equal sides;
    if three sides are equal then type is equilateral;
    if two sides are equal then type is isosceles;
    if no sides are equal then 1) type is scalene; 2) output triangle type;
else output type = 0, indication that no triangle exists;

⭐ กฎสามเหลี่ยม: ด้านยาวสุดต้องสั้นกว่าผลรวมของอีก 2 ด้าน | type = 0 = ไม่ใช่สามเหลี่ยม 💡 ⭐ Narrative vs PDL: narrative อ่านง่ายสำหรับ stakeholder แต่กำกวมได้ / PDL ชัดเจน ใกล้โค้ด เหมาะกับ programmer

4. Structured English ⭐

นิยาม: ไวยากรณ์ภาษาสำหรับระบุตรรกะของ process — ผสม จุดแข็งของ structured programming (โครงสร้างชัด ลำดับ เงื่อนไข วนซ้ำ) กับ ภาษาอังกฤษธรรมชาติ

6 Constructs:

# Construct ใช้เมื่อ Template
1 Sequence of steps ทำขั้นตอนเรียงกัน ไม่มีเงื่อนไข [Step 1] [Step 2] …
2 Simple condition เงื่อนไขมี แค่ 2 ค่า (ชุด else เป็น optional) If [condition] then [steps] else [steps] End If
3 Complex condition เงื่อนไขมี มากกว่า 2 ค่า Do the following based on [condition]: Case 1 … Case n … End Case
4 Multiple conditions ทดสอบ หลายเงื่อนไขพร้อมกัน → ใช้ decision table แทน if ซ้อนหลายชั้น ตาราง decision table
5 One-to-many iteration วนจนเงื่อนไขเป็นเท็จ ต้องทำอย่างน้อย 1 ครั้ง Repeat the following until [condition]: … End Repeat
6 Zero-to-many iteration วนจนเงื่อนไขเป็นเท็จ อาจไม่ทำเลยสักครั้ง Do while [condition]: … End Do หรือ For … End For

⚠️ ⭐ One-to-many (Repeat…until) ตรวจเงื่อนไข ท้ายรอบ → ทำอย่างน้อย 1 รอบ (= do-while) / Zero-to-many (Do while / For) ตรวจ ต้นรอบ → อาจทำ 0 รอบ (= while/for)

ตัวอย่าง:

Calculate Ticket Price
  Set total price to 0
  For each ticket in the order:
      Do the following based on ticket type:
          Case 1: If ticket type = "Child" then unit price = child price
          Case 2: If ticket type = "Adult" then unit price = adult price
          Case 3: If ticket type = "Senior" then unit price = senior price
      End Case
      Add unit price × quantity to total price
  End For
  If visit date is a special event day
      then apply event price rule (see Decision Table: Event Pricing)
  End If
  Output total price

5. Policies & Decision Tables ⭐

  • Policy = ชุดกฎที่กำหนดว่า process ต้องทำอย่างไร
  • Decision table = ตารางที่ระบุชุดเงื่อนไขและการกระทำที่สอดคล้องกัน

โครงสร้าง: แถวบน = condition stubs (เงื่อนไข) / แถวล่าง = action stubs (การกระทำ) / คอลัมน์ = rules (แต่ละคอลัมน์คือชุดค่าของเงื่อนไข 1 ชุด, X บอกว่าต้องทำ action ไหน) 💡 ⭐ decision table เหมาะกับตรรกะที่มีหลายเงื่อนไขผสมกัน เพราะถ้าเขียนเป็น if-then-else จะซ้อนหลายชั้นจนอ่านยาก

ตัวอย่าง LMART (บัตรแลกเช็คเป็นเงินสด):

"ลูกค้าที่มีสิทธิ์ แลกเช็คส่วนตัวได้ไม่เกิน $75 และแลกเช็คเงินเดือนได้เฉพาะจากบริษัทที่ LMART อนุมัติ"

Conditions and Actions Rule 1 Rule 2 Rule 3 Rule 4
C1: Type of check personal payroll personal payroll
C2: Check amount ≤ $75.00 yes doesn't matter no doesn't matter
C3: Company accredited by LMART doesn't matter yes doesn't matter no
A1: Cash the check X X
A2: Don't cash the check X X

อ่าน: Rule 1 = ส่วนตัว ≤ $75 → แลกได้ | Rule 2 = เงินเดือนจากบริษัทที่อนุมัติ → แลกได้ | Rule 3 = ส่วนตัว > $75 → แลกไม่ได้ | Rule 4 = เงินเดือนจากบริษัทที่ไม่ได้อนุมัติ → แลกไม่ได้ 💡 ⭐ "doesn't matter" ช่วยลดจำนวน rule — ถ้าไม่มี ต้องเขียนครบ 2 × 2 × 2 = 8 rules

6. DFDs: A Look Ahead & A Design Note ⭐

  • ⭐ DFD ใน analysis model ถูก map ไปเป็น design model ที่เป็นโครงสร้างลำดับชั้นของ component
  • ⭐ PSPEC ของ process หนึ่งตัว จะกลายเป็น component หนึ่งตัวหรือมากกว่า ในการออกแบบซอฟต์แวร์

💡 ความเชื่อมโยงทั้งวิชา: Requirement (L3) → Use case (L4) → DFD + PSPEC (L6–L7) → Design components → Code → Test

7. Control Flow Modeling ⭐

DFD ปกติแสดง "ข้อมูล" แต่บางระบบ (โดยเฉพาะ real-time หรือระบบควบคุม) ต้องแสดง "เหตุการณ์ (event)" ที่สั่งให้ process ทำงานด้วย

  • Control flow แทน "events" และ process ที่จัดการ event
  • ⭐ "Event" คือ เงื่อนไข Boolean (จริง/เท็จ)
  • ⭐ Control flow เกิดขึ้นที่จุดเวลาใดเวลาหนึ่ง (discrete point in time)

หา event จาก 5 แหล่ง: 1. ลิสต์ sensor ทั้งหมด ที่ซอฟต์แวร์อ่าน 2. ลิสต์ interrupt conditions 3. ลิสต์ "switch" ที่ผู้ควบคุมกด 4. ลิสต์ data conditions 5. ย้อนดู noun/verb parse แล้วตรวจ "control items" ที่อาจเป็น input/output ของ CSPEC

Data flow Control flow
คืออะไร ข้อมูลที่เคลื่อนที่ สัญญาณหรือ event (Boolean)
เส้น ⭐ เส้นทึบ ⭐ เส้นประ (dotted)
ถูกแปลงไหม ถูก process แปลง ไม่ถูกแปลง ใช้สั่งหรือแจ้ง
เวลา ไหลต่อเนื่องได้ เกิด ณ จุดเวลาหนึ่ง
ตัวอย่าง Hours Worked, Invoice "OK", "Door open", "Button pressed"

วาด control flow: ลูกศรเส้นประ + หัวลูกศรบอกทิศ + เขียนชื่อ event ไว้ข้างลูกศร

ตัวอย่างการหาร: Divisor ถูกส่งไปทั้ง process Divide และ Test that Divisor is Not Zero → ถ้าตัวหารไม่ใช่ 0 process ทดสอบส่ง control flow "OK" (เส้นประ) ไปบอก Divide ว่าทำงานได้ → Divide รับ Divisor + Dividend → ส่ง Quotient และ Remainder 💡 ⭐ "OK" ไม่ใช่ข้อมูลที่ถูกนำไปคำนวณ แต่เป็นสัญญาณอนุญาต จึงวาดเป็นเส้นประ

8. Control Specification (CSPEC) ⭐

CSPEC อธิบายว่าระบบ ตอบสนองต่อ control flow (event) อย่างไร

รูปแบบ ประเภท
State diagram sequential spec (ลำดับของสถานะ)
State transition table combinatorial spec
Decision tables combinatorial spec
Activation tables combinatorial spec

💡 ⭐ PSPEC = อธิบาย process ทำอะไรกับข้อมูล (narrative, PDL, Structured English, decision table) / CSPEC = อธิบายระบบตอบสนองต่อ event อย่างไร (state diagram, state transition table, decision table, activation table) ⭐ decision table ใช้ได้ทั้งสองแบบ

9. แนวทางแบบฝึก: Zoo Ticketing DFD

Data stores: D1 Ticket Prices (ราคาและรอบเข้าชม) / D2 Bookings (ข้อมูลการจองและตั๋ว)

Level 1 — 6 processes:

Process Input Output
1 Manage Pricing Ticket price data, Visit round data (Administrator) Price record → D1
2 Process Ticket Order Ticket order (Visitor), Price info (D1) Ticket price → Visitor, Order details → 3
3 Process Payment and Issue Ticket Order details, Payment details, Payment confirmation Payment request → Provider, Booking record → D2, Ticket → Visitor
4 Check Ticket Status Status inquiry, Booking info (D2) Ticket details and status → Visitor
5 Process Cancellation Cancellation request, Booking info (D2), Refund confirmation Refund request → Provider, Updated status → D2, Cancellation result → Visitor
6 Generate Sales Report Booking data (D2) Sales report → Administrator

ตรวจกับกฎ: ✅ process 6 ตัว (≤7) ✅ ทุก process มี input และ output ✅ D1 เป็น interface ระหว่าง 1 และ 2, D2 ระหว่าง 3, 4, 5, 6 ✅ balancing กับ context ครบ ✅ ไม่มี entity → store หรือ store → store

Level 2 ของ Process 5: 5.1 Validate Cancellation Request / 5.2 Check Refund Eligibility / 5.3 Process Refund / 5.4 Update Booking and Notify Visitor ✅ input/output ของ parent อยู่ครบ ✅ เลขเป็น 5.1–5.4 ✅ flow ใหม่ภายในเพิ่มได้ ✅ Invalid request notice = เส้น error ที่ child เพิ่มได้

คู่ที่มักสับสน

คู่ ต่างกันที่
⭐ PSPEC / CSPEC อธิบาย process และข้อมูล / อธิบายการตอบสนองต่อ event
⭐ Data flow / Control flow เส้นทึบ ข้อมูลถูกแปลง / เส้นประ สัญญาณ Boolean ณ จุดเวลา
Narrative / PDL อ่านง่ายแต่กำกวมได้ / ชัดเจน ใกล้โค้ด
Simple / Complex condition 2 ค่า (if-else) / มากกว่า 2 ค่า (case)
Complex condition / Multiple conditions เงื่อนไขเดียวหลายค่า / หลายเงื่อนไขผสมกัน (decision table)
⭐ One-to-many / Zero-to-many iteration repeat until ทำอย่างน้อย 1 รอบ / do while-for อาจ 0 รอบ
Condition stubs / Action stubs แถวเงื่อนไข / แถวการกระทำ

แนวคิดที่ต้องอธิบายได้

  • ทำไมใช้ decision table แทน if ซ้อน → เงื่อนไขหลายตัวผสมกัน ถ้าเขียนเป็น if ซ้อนหลายชั้นจะอ่านยากและตกหล่นกรณีง่าย ตารางเห็นครบทุกกรณี
  • ทำไม "doesn't matter" สำคัญ → ลดจำนวน rule จาก 2ⁿ เหลือเฉพาะกรณีที่ต่างกันจริง
  • ทำไม "OK" ในตัวอย่างหารเป็นเส้นประ → เป็นสัญญาณอนุญาต ไม่ใช่ข้อมูลที่ถูกคำนวณ
  • โจทย์แปลง policy เป็น decision table: 1. หาเงื่อนไขทั้งหมด 2. หา action ทั้งหมด 3. ไล่กรณีเป็น rule 4. ใช้ "doesn't matter" รวมกรณีที่ผลเหมือนกัน
  • โจทย์วาด Level 1 / Level 2: ต้อง balance กับ parent / process ≤ 7 / ทุก process มี input-output / store อยู่ระหว่าง process / เลข process ถูกต้อง
