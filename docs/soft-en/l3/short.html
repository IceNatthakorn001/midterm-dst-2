1. Software Requirements คืออะไร

  • คำอธิบาย "บริการ" ที่ระบบควรให้ และ ข้อจำกัด ในการทำงานของระบบ
  • สะท้อน ความต้องการของลูกค้า | มักมี นิยามฟังก์ชันที่ละเอียดและเป็นทางการ 💡 ตอบ 2 คำถาม: ระบบต้องทำอะไร และ ต้องทำภายใต้เงื่อนไขอะไร

3. ประเภทของ Requirements ⭐⭐

User vs System requirements

User requirements System requirements
บอกอะไร บริการที่ระบบต้องให้ผู้ใช้ + ข้อจำกัด คำอธิบายละเอียดกว่าของฟังก์ชัน บริการ ข้อจำกัด
ระดับ ประโยคกว้าง ๆ ถึงละเอียด ⭐ กำหนดชัดเจนว่าต้อง implement อะไร
ภาษา ภาษาที่ลูกค้าเข้าใจ ละเอียด เป็นเทคนิคมากขึ้น

ตัวอย่าง Mentcare: user requirement 1 ประโยค ("ออกรายงานรายเดือนแสดงค่ายาที่แต่ละคลินิกสั่ง") → แตกเป็น system requirements 5 ข้อ (1.1 สร้างสรุปวันทำการสุดท้ายของเดือน / 1.2 สร้างรายงานหลัง 17.30 น. / 1.3 แยกต่อคลินิก มีชื่อยา จำนวนใบสั่ง จำนวน dose ราคารวม / 1.4 ยาหลายขนาด (10mg, 20mg) แยกรายงานตามขนาด / 1.5 จำกัดสิทธิ์ตาม access control list)

ใครอ่าน:

User requirements System requirements
Client managers, System end-users, Client engineers, Contractor managers, System architects System end-users, Client engineers, System architects, ⭐ Software developers

⚠️ Managers อ่านแค่ user requirements / Software developers อ่าน system requirements Stakeholders ของ Mentcare (8 กลุ่ม): Patients, Doctors, Nurses, Medical receptionists, IT staff, Medical ethics manager, Health care managers, Medical records staff

Functional vs Non-functional ⭐

Functional Non-functional
บอกอะไร บริการที่ระบบต้องให้ ข้อจำกัดของบริการ (response time, compatibility, memory use)
รายละเอียด ระบบทำอะไร, ตอบสนอง input อย่างไร ⭐ มักใช้กับระบบทั้งระบบ ไม่ใช่ฟีเจอร์เดียว
คำถาม "ทำอะไร" "ทำได้ดีแค่ไหน ภายใต้เงื่อนไขอะไร"

Types of Non-functional (Sommerville) 3 กลุ่ม:

กลุ่ม ความหมาย ประเภทย่อย
Product requirements พฤติกรรมของตัวผลิตภัณฑ์ Usability, Efficiency (Performance, Space), Dependability, Security
Organizational requirements จากนโยบายและขั้นตอนขององค์กร Environmental, Operational, Development
External requirements จากปัจจัยภายนอก Regulatory, Ethical, Legislative (Accounting, Safety/security)

⚠️ ⭐ Non-functional ต้องวัดผลได้และทดสอบได้ (measurable and testable)

Property Measure
Speed Processed transactions/second, user/event response time, screen refresh time
Size Megabytes, number of ROM chips
Ease of use Training time, number of help frames
Reliability Mean time to failure, probability of unavailability, rate of failure, availability
Robustness Time to restart after failure, % events causing failure, probability of data corruption
Portability % target dependent statements, number of target systems

แบบฝึก: "easy-to-use" = Non-functional แต่เขียนไม่ดี เพราะวัดไม่ได้ / "allow users to create accounts" = Functional / "handle 10,000 concurrent users" = Non-functional / "load within 2 seconds for 95%" = Non-functional ที่วัดได้ชัดเจน

4. Requirements Engineering (RE) ⭐

กระบวนการ ค้นหา (finding out), วิเคราะห์ (analysing), จัดทำเอกสาร (documenting), ตรวจสอบ (checking) software requirements

Feasibility Study (ทำตั้งแต่ช่วงต้น ของ RE, สั้นและเจาะจง) — 3 คำถาม:

  1. ระบบช่วยให้องค์กรบรรลุเป้าหมายโดยรวมไหม
  2. สร้างได้ภายในเวลาและงบด้วยเทคโนโลยีปัจจุบันไหม
  3. รวมเข้ากับระบบอื่นที่ใช้อยู่ได้ไหม

⚠️ ⭐ ถ้าคำตอบข้อใดข้อหนึ่งเป็น "ไม่" ก็ไม่ควรเดินหน้าโครงการ

RE Processes: ⭐ เป็นกระบวนการแบบวนซ้ำ (iterative) | Output = System requirements document | มี 4 กระบวนการ: Elicitation → Specification → Validation → Change

5. Requirements Elicitation ⭐

Aim: เข้าใจงานที่ stakeholder ทำ และเข้าใจว่าระบบใหม่จะช่วยงานนั้นอย่างไร หาข้อมูลเรื่อง: application domain / work activities / บริการและฟีเจอร์ที่ต้องการ / performance / ข้อจำกัดด้าน hardware

⭐ Challenges 4 ข้อ — ทำไมเก็บ requirement ยาก:

  1. Stakeholder มักไม่รู้ว่าตัวเองต้องการอะไร
  2. อธิบายสิ่งที่อยากให้ระบบทำได้ยาก
  3. อาจ ขอสิ่งที่เป็นไปไม่ได้ เพราะไม่รู้ว่าอะไรทำได้
  4. Stakeholder ต่างกลุ่มมี requirement ต่างกัน และพูดคนละแบบ

Elicitation and Analysis Process (วนเป็นวงกลม) 4 ขั้น:

  1. Discovery and understanding — คุยกับ stakeholder
  2. Classification and organization — จัดกลุ่ม requirement ที่เกี่ยวข้อง
  3. Prioritization and negotiation — จัดลำดับความสำคัญ + เจรจาเมื่อขัดกัน
  4. Documentation — บันทึกแล้ววนกลับไปข้อ 1

6 Dimensions of Detailed Elicitation: 1. Individual Functionality 2. Business Workflow 3. Data and Data formats 4. User Interfaces 5. Existing Systems & Interfaces 6. Other Constraints (Performance, Reliability)

⭐ 2 แนวทางพื้นฐาน: (1) Interviewing (2) Observation / Ethnography

Interviewing:

Closed interview Open interview
ถามตามชุดคำถามที่เตรียมไว้ ไม่มีสคริปต์ตายตัว คุยเปิดกว้าง

Challenges: stakeholder ใช้ jargon / คุ้นเคยงานมากจนอธิบายยาก หรือคิดว่าเรื่องพื้นฐานไม่ต้องพูด / ⭐ ไม่ค่อยได้ผลกับ requirement ระดับองค์กร เพราะมีความสัมพันธ์เชิงอำนาจที่ละเอียดอ่อน Tips: Be open-minded / Avoid preconceived ideas / Willing to listen / Prompt the interviewee / ⭐ Do not say "tell me what you want"

Ethnography: นักวิเคราะห์เข้าไปอยู่ในสภาพแวดล้อมการทำงานจริง ดูงานประจำวัน → ⭐ ช่วยค้นพบ implicit requirements ที่สะท้อนวิธีทำงานจริง ไม่ใช่กระบวนการทางการที่องค์กรเขียนไว้ เทคนิคอื่น: Sampling of existing documentation, forms, databases / Research and site visits / Questionnaires / JRP (Joint Requirements Planning) ⚠️ แต่ละเทคนิคเหมาะกับสถานการณ์ต่างกัน ไม่มีเทคนิคเดียวที่ดีที่สุด

6. Requirements Specification ⭐

Requirement ที่ดีต้อง clear, unambiguous, easy to understand, complete, consistent | เขียนเป็นประโยคภาษาธรรมชาติที่มีหมายเลข ประเภท: 1. Natural language 2. Structured specifications (รวม user story) 3. Use case specification 4. Prototyping 5. DFD, ERD

Natural Language — Guidelines 5 ข้อ

  1. คิดรูปแบบมาตรฐาน และเขียนทุก requirement ตามรูปแบบนั้น
  2. ⭐ ใช้ภาษาให้สม่ำเสมอ: "Shall" = mandatory (ต้องมี) / "Should" = desirable (ควรมี)
  3. ใช้การเน้นข้อความ (ตัวหนา เอียง สี) กับส่วนสำคัญ
  4. หลีกเลี่ยง jargon, คำย่อ, อักษรย่อ
  5. ใส่ rationale ว่าทำไมต้องมีและใครเสนอ

Structured Specification — 10 Fields ⭐

# Field Description
1 Requirement ID รหัสไม่ซ้ำ ไว้อ้างอิงและติดตาม
2 Requirement type functional / non-functional
3 Description คำอธิบายละเอียด
4 Rationale ทำไมจำเป็น และช่วยเป้าหมายอย่างไร
5 Source ใครให้ requirement นี้
6 Input(s) ข้อมูล/เงื่อนไขที่ต้องใช้
7 Output(s) ผลลัพธ์ที่คาด
8 Action ขั้นตอนการทำงาน
9 Precondition สภาพที่ต้องเป็นจริงก่อน
10 Postcondition สภาพของระบบหลัง

User Story ⭐

ในฐานะ (As a)      … บุคคล ตำแหน่ง หรือบทบาทในระบบ
ฉันต้องการ (I want)  … พฤติกรรมหรือความสามารถในระบบ
เพื่อที่ (So that)    … ได้ประโยชน์อะไร มีคุณค่าอะไรกับธุรกิจ
  • วัดผลด้วย Acceptance Criteria หรือ Definition of Done (DoD)

ลำดับชั้น: User Need → Epic → User Story → Tasks / Acceptance Criteria

ระดับ ความหมาย
User Need ความต้องการใหญ่สุดของผู้ใช้
Epic user story ขนาดใหญ่ที่ต้องแตกย่อยอีก
User Story ชิ้นความต้องการที่ทำเสร็จได้ในรอบเดียว
Tasks งานเทคนิคที่ทีมต้องทำ
Acceptance criteria เกณฑ์ว่าเมื่อไรถือว่าเสร็จ

Acceptance Criteria: เขียนเป็นข้อ ๆ ไม่กำกวม + ⭐ ต้องวัดผลได้ + มักเขียนในรูป Given–When–Then (Gherkin syntax)

กำหนดให้ (Given) … ผู้ใช้อยู่ในสถานการณ์อะไร
เมื่อ (When)      … ผู้ใช้ทำอะไร
จึง (Then)        … ผลลัพธ์ของระบบ

ตัวอย่างระบบขายตั๋วสวนสัตว์:

# Given When Then
1 เข้าหน้าเว็บขายตั๋ว เลือกจำนวนตั๋ว (ผู้ใหญ่/เด็ก) แสดงราคารวมทันที
2 เลือกจำนวนแล้ว ชำระเงิน (บัตรเครดิต/QR) ยืนยันการชำระเงินสำเร็จ
3 ชำระเงินสำเร็จ ระบบออกตั๋ว ได้รับอีเมลยืนยันพร้อม QR Code
4 มี QR Code จากอีเมล ไปที่ทางเข้าและสแกน ระบบตรวจสอบและอนุญาตให้เข้า

💡 ⭐ Then ของข้อก่อน กลายเป็น Given ของข้อถัดไป → criteria ร้อยต่อกันเป็นเส้นทางการใช้งาน

  • บันทึกด้วย high-level use case diagram และ แต่ละ use case ควรมีคำอธิบายเป็นข้อความ
สัญลักษณ์ แทน
Stick figure Actor (คนหรือระบบอื่นก็ได้)
Named ellipse Use case

Prototyping

เน้น User Interface (UI) 2 ด้าน: Visual looks (ขนาด รูปทรง ตำแหน่ง สี) และ Flow (control flow, logical flow)

Low fidelity High fidelity
ใช้กระดาษหรือกระดาษแข็งแทนหน้าจอ แล้วให้คนเลื่อนแผ่น ใช้เครื่องมืออัตโนมัติ (Visual Basic, Figma) เขียนหน้าจอและ logical flow
ถูก เร็ว แก้ง่าย สมจริง แต่ใช้เวลาและแรงมากกว่า

DFD & ERD

DFD = แสดงการไหลของข้อมูล (L6–L7) | ERD = แสดงความสัมพันธ์ของข้อมูล

  • Cardinality: ระบุจำนวนของ entity ที่สัมพันธ์กัน (ผู้แต่ง 1 คน เขียนหนังสือได้หลายเล่ม)
  • Modality: ระบุว่าความสัมพันธ์จำเป็นต้องมีหรือไม่ (| = mandatory, ○ = optional)

7. SRS (Software Requirements Specification) ⭐

  • ข้อความทางการว่านักพัฒนาต้อง implement อะไร | มีทั้ง user และ system requirements (user requirements อยู่ในบทนำ)

ทำไมต้องทำเอกสาร 5 ข้อ: 1. จำเป็นต่อ design และ implementation 2. ใช้สร้าง test case และ test scenario 3. ใช้ควบคุม scope creep 4. ใช้สร้างเอกสารอบรมผู้ใช้ เอกสารการตลาด support maintenance 5. ช่วยแบ่งโครงการใหญ่เป็นส่วน จัดลำดับ release

Users of SRS 5 กลุ่ม:

ผู้ใช้ ใช้ทำอะไร
System customers ระบุ requirement + เช็กว่าตรงความต้องการ — ⭐ ลูกค้าเป็นคนระบุการเปลี่ยนแปลง
Managers ใช้วางแผนเสนอราคา (bid) และวางแผนกระบวนการพัฒนา
System engineers เข้าใจว่าต้องพัฒนาระบบอะไร
System test engineers ใช้สร้าง validation tests
System maintenance engineers เข้าใจระบบและความสัมพันธ์ระหว่างส่วนต่าง ๆ

โครงสร้าง SRS 10 บท: 1. Preface (กลุ่มผู้อ่าน, ประวัติเวอร์ชัน) 2. Introduction (ความจำเป็นของระบบ, ทำงานร่วมกับระบบอื่น, สอดคล้องกับเป้าหมายธุรกิจ) 3. Glossary (ศัพท์เทคนิค) 4. User requirements definition (รวม non-functional, ภาษาที่ลูกค้าเข้าใจ) 5. System architecture (สถาปัตยกรรมระดับสูง, เน้นส่วนที่นำกลับมาใช้ซ้ำ) 6. System requirements specification (แบบละเอียด + interface) 7. System models (object model, data-flow model, semantic data model) 8. System evolution (สมมติฐานพื้นฐาน + การเปลี่ยนแปลงที่คาดว่าจะเกิด) 9. Appendices (hardware, database requirements) 10. Index

8. Requirements Validation ⭐

  • ตรวจว่า requirement กำหนดระบบที่ลูกค้าต้องการจริง ๆ
  • ⭐ สำคัญมาก เพราะความผิดพลาดในเอกสาร requirement ทำให้ต้นทุนแก้งานสูงมาก — เปลี่ยน requirement 1 ข้อ ต้องเปลี่ยน design และ implementation แล้วทดสอบใหม่

Validation Criteria 7 ข้อ:

# Check ตรวจอะไร
1 Validity สะท้อนความต้องการจริงของผู้ใช้
2 Consistency ไม่ขัดแย้งกันเอง
3 Completeness กำหนดทุกฟังก์ชันและข้อจำกัดครบ
4 Realism ทำได้จริงและส่งมอบได้
5 Clarity ไม่กำกวม
6 Verifiability ออกแบบ test ที่ทำซ้ำได้เพื่อพิสูจน์ว่าระบบทำตาม requirement
7 Traceability สืบย้อนไปยังฟังก์ชันของระบบที่กำหนดไว้ได้

ตัวอย่างไม่ผ่าน: Consistency — ข้อ 3 บอกรหัสผ่าน 8 ตัว ข้อ 12 บอก 6 ตัว | Verifiability — "ระบบต้องเร็ว" | Realism — "ไม่ล่มเลย 100% ตลอดไป"

9. Requirements Change & Management ⭐

ทำไม requirement เปลี่ยน:

  • ⭐ Wicked problem = ปัญหาซับซ้อนที่ นิยามให้ครบตั้งแต่แรกไม่ได้
  • ⭐ ความเข้าใจของ stakeholder เปลี่ยน เมื่อเห็นระบบหรือเข้าใจปัญหามากขึ้น

Requirements Management = ติดตาม requirement แต่ละข้อ + รักษาลิงก์ระหว่าง requirement ที่พึ่งพากัน เพื่อ ประเมินผลกระทบของการเปลี่ยนแปลง — มี 2 กระบวนการ:

Requirements management planning Requirements change management
ทำช่วงวางแผน ทำหลังเอกสาร requirement ได้รับอนุมัติแล้ว
กำหนดว่าจะจัดการ requirement ที่เปลี่ยนอย่างไร จัดการการเปลี่ยนแปลงทั้งหมดที่ถูกเสนอ

Planning — พิจารณา 4 เรื่อง: 1. ⭐ Requirements identification (ทุก requirement ต้องมี ID ไม่ซ้ำ) 2. Change management process (ประเมินผลกระทบและต้นทุน) 3. Traceability policies 4. Tool support

Change Management — 3 ขั้น:

  1. Problem analysis and change specification — ระบุปัญหา, ตรวจว่าสมเหตุสมผลไหม, ตัดสินรับหรือถอน
  2. Change analysis and costing — ประเมินโดยใช้ ข้อมูล traceability แล้ว ประมาณต้นทุน
  3. Change implementation — แก้ไข design และ implementation

💡 ⭐ Requirement ID (planning) → ทำให้ traceability ได้ → ทำให้ change analysis ประเมินผลกระทบได้ ถ้าไม่มี ID ก็ไม่รู้ว่าแก้ข้อหนึ่งแล้วกระทบอะไรบ้าง

คู่ที่มักสับสน

คู่ ต่างกันที่
User / System requirements กว้าง ลูกค้าอ่าน / ละเอียด developer อ่าน
Functional / Non-functional ทำอะไร / ข้อจำกัดหรือคุณภาพ ใช้กับทั้งระบบ
Shall / Should ต้องมี (mandatory) / ควรมี (desirable)
Interview / Ethnography ฟังจากที่เขาเล่า / ดูจากที่เขาทำจริง (ได้ implicit requirement)
Closed / Open interview มีชุดคำถาม / คุยเปิด
Low / High fidelity prototype กระดาษ คนเลื่อน / เครื่องมือ flow อัตโนมัติ
Cardinality / Modality กี่อัน / จำเป็นต้องมีไหม
Consistency / Completeness ไม่ขัดกันเอง / ครบทุกฟังก์ชัน
Verifiability / Traceability ทดสอบพิสูจน์ได้ / สืบย้อนไปยังฟังก์ชันหรือ design ได้
Requirements management planning / Change management วางแผนก่อน / จัดการหลังเอกสารอนุมัติแล้ว

แนวคิดที่ต้องอธิบายได้

  • ทำไมห้ามถาม "tell me what you want" → stakeholder มักไม่รู้ว่าต้องการอะไรและอธิบายยาก ต้องชวนคุยจากงานที่เขาทำจริง
  • ทำไม ethnography เจอสิ่งที่สัมภาษณ์ไม่เจอ → คนทำงานจนคุ้นจนไม่คิดจะพูด และการทำงานจริงมักต่างจากกระบวนการทางการ
  • ทำไม "easy-to-use" เป็น requirement ที่แย่ → วัดไม่ได้ ทดสอบไม่ได้ ไม่ผ่าน verifiability
  • ทำไม validation สำคัญ → แก้ requirement หลังพัฒนาแล้วต้องแก้ design + implementation + retest ต้นทุนสูงมาก
  • ทำไม requirement ต้องมี ID ไม่ซ้ำ → เพื่อทำ traceability และประเมินผลกระทบ
  • ทำไม requirement เปลี่ยนแน่นอน → เป็น wicked problem และความเข้าใจของ stakeholder เปลี่ยนตามเวลา
