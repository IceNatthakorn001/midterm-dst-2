1. Requirements Modeling Strategies ⭐

Structured analysis Object-oriented analysis
มองระบบอย่างไร แยกข้อมูล (data) กับ process ที่แปลงข้อมูลออกเป็นคนละส่วน มองเป็น class ที่ทำงานร่วมกัน
เน้น data + process นิยาม class และ วิธีที่ class ร่วมมือกัน
แผนภาพ ⭐ DFD, ERD Class diagram

💡 ⭐ DFD เป็นเครื่องมือของ structured analysis Elements of Requirements Analysis: software requirements ตรงกลาง ล้อมด้วย Scenario-based (L4), Class, Behavioral, Flow models (บทนี้)

2. Flow-Oriented Modeling ⭐

  • แสดงว่า data object ถูกแปลง (transform) อย่างไร ขณะเคลื่อนผ่านระบบ — แผนภาพคือ DFD
  • ⭐ หลายคนมองว่าเป็น "old school" แต่ยังให้มุมมองที่ไม่เหมือนโมเดลอื่น จึงควรใช้ เสริม analysis model อื่น

⭐ ระบบคอมพิวเตอร์ทุกระบบแปลง input เป็น output

3. สัญลักษณ์ DFD — 4 ตัว ⭐⭐

องค์ประกอบ Yourdon / DeMarco Gane / Sarson
External entity สี่เหลี่ยม สี่เหลี่ยม (มักมีเงา)
Process วงกลม (bubble) สี่เหลี่ยมมุมมน มีช่องเลขด้านบน
Data flow ลูกศร ลูกศร
Data store เส้นขนาน 2 เส้น สี่เหลี่ยมเปิดด้านขวา มีช่อง ID (D1) ด้านซ้าย

⚠️ ใช้สัญลักษณ์สำนักเดียวกันตลอดทั้งแผนภาพ อย่าผสมกัน

(1) External Entity: ผู้ผลิตหรือผู้บริโภคข้อมูล — คน องค์กร หรือระบบที่อยู่ภายนอกระบบ มีปฏิสัมพันธ์กับระบบ (คน, อุปกรณ์, sensor, ระบบคอมพิวเตอร์อื่น) 💡 ⭐ ข้อมูลต้องมีต้นทางและปลายทางเสมอ — external entity คือต้นทางและปลายทางนั้น

(2) Process: ตัวแปลงข้อมูล (data transformer) เปลี่ยน input → output (compute taxes, determine area, format report, display graph) Logical process ที่ควรใส่ใน DFD 6 ชนิด:

ชนิด ตัวอย่าง
ทำการคำนวณ calculate grade point average
ตัดสินใจ determine availability of ordered products
เรียง กรอง หรือสรุปข้อมูล identify overdue invoices
จัดข้อมูลให้เป็นสารสนเทศที่มีประโยชน์ generate a report, answer a question
สั่งให้ process อื่นทำงาน turn on the furnace, instruct a robot
ใช้ข้อมูลที่เก็บไว้ CRUD (create, read, update, delete a record)

💡 ตั้งชื่อ process แบบ กริยา + กรรม ("Calculate Gross Pay", "Search for book")

(3) Data Flow: ข้อมูลที่กำลังเคลื่อนที่ (data in motion) — เป็น input/output ของ process หรือการสร้าง/ลบ/อัปเดตข้อมูลใน data store 💡 ตั้งชื่อ data flow ด้วย คำนาม ("Invoice", "Hours Worked") ⭐ Data Flow Packet Concept: ข้อมูลที่ไปด้วยกันควรแสดงเป็น data flow เส้นเดียว ไม่ว่าจะมีเอกสารจริงกี่ชิ้น

(4) Data Store: ที่เก็บ ข้อมูลถาวร (persistent data)

  • ⭐ Data flow ที่ออกจาก data store = การดึงข้อมูล (retrievals)
  • ⭐ Data flow ที่เข้า data store = การอัปเดตหรือเพิ่มข้อมูลใหม่

4. DFD หลายระดับ (Decomposition) ⭐

  • Business process ซับซ้อนเกินกว่าจะแสดงใน DFD แผ่นเดียว → สร้างลำดับชั้นหลาย "level" ด้วย Decomposition
  • ⭐ Child diagram แสดงส่วนหนึ่งของ parent diagram อย่างละเอียดขึ้น

Guidelines 5 ข้อ ⭐:

  1. ทุกสัญลักษณ์ต้องมีชื่อที่มีความหมาย
  2. DFD พัฒนาผ่านหลายระดับความละเอียด
  3. ⭐ เริ่มจาก context level diagram เสมอ (= level 0)
  4. ⭐ แสดง external entities ที่ level 0 เสมอ
  5. ⭐ ใส่ชื่อ data flow ทุกเส้นเสมอ

ขั้นตอนสร้าง DFD: 1. ทบทวน user scenarios / data model แยก data object ออกมา ใช้ grammatical parse หา "operations" → 2. หา external entities → 3. สร้าง level 0 DFD (context diagram) 💡 Grammatical parse = อ่านคำอธิบายระบบแล้วขีดเส้น คำนาม (entity, data store, data flow) และ คำกริยา (process) — เทคนิคเดียวกับการหา actor/use case ใน L4

5. Context Diagram (Level 0) ⭐

  • DFD ระดับบนสุด แสดงบริบทว่า business process อยู่ในสภาพแวดล้อมแบบไหน
  • ⭐ แสดงทั้ง business process เป็น process เดียว คือ process "zero" (0)
  • ⭐ แสดง external entities ทั้งหมด ที่รับหรือส่งข้อมูลกับระบบ
  • ⚠️ ⭐ Context diagram ไม่มี data store (ทุก data store อยู่ภายในระบบซึ่งยุบรวมเป็น process 0 แล้ว)

ตัวอย่าง Digital video processor: entities = user, video source, monitor / process เดียว = digital video processor

6. Data Flow Hierarchy & Flow Modeling Notes

  • process P ใน level 0 ถูกแตกเป็น p1–p5 ใน level 1 โดย ⭐ input a และ output b ยังเหมือนเดิม ส่วน c, d, e, f, g เป็น data flow ใหม่ภายใน
  • 💡 ⭐ V, W, X, Y, Z ของ context diagram ยังอยู่ครบใน level 1 ส่วน A–G และ data store D1, D2 เพิ่งโผล่มา = หลัก balancing

Flow Modeling Notes ⭐:

  • แตกแต่ละ bubble (process) ไปเรื่อย ๆ จนกว่าจะทำแค่อย่างเดียว
  • ⭐ Expansion ratio ลดลงเมื่อจำนวนระดับเพิ่มขึ้น (ระดับลึกแตกออกน้อยลง)
  • ⭐ ระบบส่วนใหญ่ต้องใช้ 3–7 ระดับ
  • data flow เส้นเดียวอาจถูกแตกย่อยเมื่อระดับลึกขึ้น โดยดูรายละเอียดจาก data dictionary

7. Balancing ⭐⭐

  • ทำให้มั่นใจว่า ข้อมูลที่แสดงใน DFD ระดับหนึ่ง ถูกแสดงอย่างถูกต้องในระดับถัดไป
  • ⭐ Data flow ของ parent ต้องถูกนำลงไปใน child
  • ⭐ Child diagram เพิ่ม process และ data flow ใหม่ได้
จุดสังเกต ความหมาย
Matching parent-child decomposition process 3 แตกเป็น 3.1, 3.2, 3.3
Input/output ต้องตรงกับ parent process ทั้ง input และ output ของ process 3 ต้องปรากฏใน child
Matching data store D1 ที่ parent ใช้ ต้องปรากฏใน child ด้วย
⭐ Error lines and transaction files เพิ่มได้ใน child diagram ที่ละเอียด (parent ไม่มีก็ได้)

8. กฎของ DFD ⭐⭐

Rules for Data Flows:

  • Data flow ต้องมีชื่อเสมอ
  • ⭐ ใน logical modeling ชื่อ data flow ต้องบอกว่าเป็นข้อมูลอะไร โดยไม่บอกวิธี implement (ใช้ "Customer Order" ไม่ใช่ "Order Email" หรือ "SQL Query")
  • ทุก data flow ต้องเริ่มและ/หรือจบที่ process

❌ Don't Break DFD Rules — 3 ข้อห้าม:

  1. Data flow ไม่ควรแยกออกเป็น 2 เส้นขึ้นไปที่เป็นข้อมูลต่างกัน
  2. ⭐ ทุก data flow ต้องเริ่มหรือจบที่ process
  3. ⭐ Process ต้องมี input อย่างน้อย 1 เส้น และ output อย่างน้อย 1 เส้น

ชื่อเรียกความผิดที่พบบ่อย:

ชื่อ อาการ
Black hole process มีแต่ input ไม่มี output
Miracle (spontaneous generation) process มีแต่ output ไม่มี input
Gray hole input ไม่พอจะสร้าง output ได้

ตารางต่อจากอะไรไปอะไรได้:

จาก \ ไป Process External Entity Data Store
Process ✅ ✅ ✅
External Entity ✅ ❌ ❌
Data Store ✅ ❌ ❌

💡 ⭐ จำง่าย ๆ: ทุกเส้นต้องแตะ process อย่างน้อยหนึ่งฝั่ง

9. Internal Consistency (ภายในแผ่นเดียว) ⭐

องค์ประกอบ กฎ
Context Diagram ต้องมี / มีแค่ process เดียว / มี input จาก entity ≥1 และ output ไป entity ≥1 / process ต้องมีเลข 0
Detailed DFDs มี process อย่างน้อย 1 และ ⭐ ไม่เกิน 7
Process มี input ≥1 และ output ≥1 / ต้องเชื่อมกับ data store, process หรือ external entity / ต้องมีชื่อ
External Entity ต้องปรากฏเฉพาะใน context diagram / ต้องเชื่อมกับ process / ต้องมีชื่อ
Data Flow ต้องเป็น interface ระหว่าง process กับ process อื่น/data store/entity / flow เข้า-ออก data store ต้องมีองค์ประกอบเป็น subset ของ data store / ต้องมีชื่อ
Data Store ⭐ ต้องเป็น interface ระหว่าง 2 process / ต้องมีชื่อ

10. Hierarchical Consistency (ระหว่างระดับ) ⭐

องค์ประกอบ กฎ
Data Flow Diagram ต้องมี parent diagram ยกเว้น context diagram
Process ต้องแตกย่อยเป็นแผนภาพอื่นหรือเป็น primitive process specification (L7) / ต้องมีเลขที่อ้างอิงกับ parent
Data Flow ⭐ input (output) ใน parent ต้องปรากฏใน child เป็น input (output) และกลับกัน / ชุด flow ใน child ที่แยกจาก parent ต้องมีองค์ประกอบรวมกันตรงกับ flow ของ parent / แตกย่อยเป็น record/element definition
Data Store แตกย่อยเป็น file definition หรือ record definition
Primitive Process Spec input/output ทั้งหมดต้องตรงกับ primitive process ใน DFD / มี identifier เดียวกัน

⚠️ ข้อยกเว้นที่ child ต่างจาก parent ได้: เส้น error และ transaction file

11. Diagram Numbering ⭐

ระดับ รูปแบบเลข ตัวอย่าง

Level 1 เลขจำนวนเต็ม 1, 2, 3
Level 2 1 จุด: parent . เลขเฉพาะ 1.1, 1.2, 1.3

12. ตัวอย่าง: Library Query System

Level 0 (Context): entities = Student, Publishers | process = 0 Library Query System

  • Input: Name of book, Author name, Library ID (จาก Student), Book information (จาก Publishers)
  • Output: Member status, Author(s)/Name of book/Preface/Number of pages, List of books (ไป Student)

Level 2 (แตกจาก process 1 Search for book): 1.1 Search by book name (ใส่ชื่อหนังสือ → ได้ผู้แต่ง ชื่อหนังสือ คำนำ จำนวนหน้า) | 1.2 Search by author name (ใส่ชื่อผู้แต่ง → ได้รายการหนังสือ) — output ตรงกับ level 0 ✅

ภาพ ถูก/ผิด เหตุผล

Apply Insurance Premium: มีแต่ลูกศรออก ไม่มีเข้า ไม่มีเลข ❌ ไม่มี input (miracle) + ไม่มีเลข
2.1 Calculate Gross Pay: Hours Worked, Pay Rate เข้าทั้งคู่ ไม่มีออก ❌ ไม่มี output (black hole)

PAYROLL DEPARTMENT → Paycheck → EMPLOYEE ❌ entity → entity
CUSTOMER → Payment → 3.0 Apply Payment ✅ entity → process

List the Errors — เช็คลิสต์: 1. entity → entity 2. entity → data store 3. data store ไม่ได้เป็น interface ระหว่าง 2 process 4. process มีแต่ input (black hole) 5. ใช้ชื่อ data flow ซ้ำกับเส้นที่ข้อมูลต่างกัน 6. entity วาดซ้ำโดยไม่มีเครื่องหมาย 7. ชื่อไม่มีความหมาย / เลขกับชื่อสลับกัน

คู่ที่มักสับสน

คู่ ต่างกันที่
DFD / Use case diagram มุมข้อมูลไหล / มุมผู้ใช้ทำอะไร
External entity / Data store อยู่นอกระบบ ส่งหรือรับข้อมูล / อยู่ในระบบ เก็บข้อมูล
⭐ Data flow ออกจาก store / เข้า store อ่านข้อมูล (retrieval) / เขียนข้อมูล (update)

แนวคิดที่ต้องอธิบายได้

  • ทำไม DFD ยังสำคัญแม้เป็น "old school" → ให้มุมมองการไหลและการแปลงข้อมูลที่โมเดลอื่นไม่มี ใช้เสริมกันได้
  • ทำไมต้องแตก DFD หลายระดับ → business process ซับซ้อนเกินจะแสดงในแผ่นเดียว
  • ทำไมต้อง balancing → ไม่ให้ข้อมูลหายหรือโผล่มาเองระหว่างระดับ ถ้าไม่ balance แสดงว่ามีข้อมูลที่ไม่รู้ที่มาหรือไม่มีที่ไป
  • ทำไมห้ามต่อ entity → store → ข้อมูลต้องถูก process (ตรวจสอบหรือแปลง) ก่อนเก็บ ภายนอกระบบเขียนลงฐานข้อมูลตรง ๆ ไม่ได้
  • โจทย์หาข้อผิด: ไล่เช็กว่า ทุกเส้นแตะ process ไหม / process มี input และ output ไหม / store อยู่ระหว่าง 2 process ไหม / ทุกอย่างมีชื่อและเลขถูกไหม / ชื่อซ้ำหรือกำกวมไหม
