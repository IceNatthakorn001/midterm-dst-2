Lab 3: User story + Acceptance criteria + NFR 5 stories × 2 AC + 5 NFR

โจทย์สั่ง: user story 5 ข้อที่ครอบคลุม actor ทุกบทบาท ข้อละ AC 2 ข้อ และ NFR 5 ข้อ

ขั้นตอน

  1. นับ actor (3 บทบาท) แล้วแบ่ง 5 stories เช่น 2–2–1 ห้ามมีบทบาทไหนหายไป
  2. เลือกฟีเจอร์หลักของโจทย์ ไม่ใช่ฟีเจอร์ทั่วไป ข้อแรกที่ควรหยิบ: รายงานหลุม, ติดตามด้วย Report ID, ดู/บันทึกคำสั่งงาน, คำนวณค่าใช้จ่าย, รายงานสรุป
  3. เขียน story ตามสูตร แล้วเขียน AC 2 ข้อ: ข้อ 1 ทางปกติ (สำเร็จ) + ข้อ 2 ทางผิดพลาด / กรณีขอบ
  4. NFR: เลือก 5 หมวดที่ต่างกัน และทุกข้อต้องมีตัวเลขที่วัดได้

สูตร User story

ในฐานะ [บทบาทจากโจทย์] ฉันต้องการ [ทำอะไรกับระบบ 1 อย่าง] เพื่อที่ [ได้ประโยชน์อะไร]

ช่องกฎผิดบ่อยควรเป็น
ในฐานะใช้ชื่อบทบาทตามโจทย์ ห้ามใช้ "ผู้ใช้" เฉย ๆ ถ้าโจทย์มีหลายบทบาทในฐานะผู้ใช้ในฐานะหัวหน้างาน
ฉันต้องการกริยาหนึ่งเรื่อง เล็กพอให้ทำเสร็จในหนึ่งรอบ ถ้ามี "และ" หลายเรื่องให้แยก storyต้องการรายงานสรุปถนน รายงานการซ่อม และรายงานค่าใช้จ่ายต้องการดูรายงานสรุปถนนชำรุดแยกตามเขตและระดับความรุนแรง
เพื่อที่ประโยชน์ของคนในบทบาทนั้น ห้ามพูดซ้ำกับ "ฉันต้องการ" ห้ามลอกวัตถุประสงค์ของระบบมาทั้งประโยคเพื่อที่สามารถติดตาม ดำเนินการ และบันทึกข้อมูลได้อย่างมีประสิทธิภาพเพื่อที่จัดลำดับเขตที่ต้องซ่อมก่อนได้

สูตร Acceptance criteria (Given–When–Then)

ช่องคืออะไรตรวจยังไง
Givenสภาพก่อนเริ่ม: ใครอยู่หน้าไหน มีข้อมูลอะไรอยู่แล้วต้องเป็นสิ่งที่เป็นอยู่แล้ว ไม่ใช่การกระทำ ("เข้าสู่ระบบแล้ว" ✓, "กรอกรหัสผิด" ✗ เพราะเป็นการกระทำ)
Whenการกระทำหนึ่งอย่างของผู้ใช้ (หรือเหตุการณ์)เป็นกริยาที่กดหรือกรอกได้จริง ("กด ส่งรายงาน") ไม่ใช่ความรู้สึก ("ลืมรหัส" ✗)
Thenผลที่ระบบแสดงหรือทำ ที่มองเห็นและทดสอบได้ถามตัวเองว่า "tester จะเช็กยังไงว่าผ่าน" ถ้าตอบไม่ได้แปลว่ายังกำกวม
💡 เทคนิคให้ Then ชัด: ใส่ข้อความที่ระบบแสดงในเครื่องหมายคำพูด, ใส่ตัวเลขตัวอย่าง (ระดับ 11, 3 คน × 4 ชม.), บอกว่าข้อมูลไปอยู่ที่ไหน (ใครเห็น สถานะเป็นอะไร)
⭐ AC ต้องทดสอบ story ของตัวเอง ถ้า story พูดเรื่องดูรายงาน AC ก็ต้องพูดเรื่องดูรายงาน การเอา AC เรื่อง login ไปใส่ใต้ story เรื่องรายงานถือว่าผิด

สูตร Non-functional requirement

ระบบต้อง + [คุณภาพ] + [ตัวเลข + หน่วย] + [ภายใต้เงื่อนไข / วิธีวัด]

เช่น "หน้ารายงานต้องโหลดเสร็จภายใน 3 วินาที สำหรับ 95% ของคำขอ เมื่อมีผู้ใช้พร้อมกัน 5,000 คน"

หมวด (เลือก 5 หมวดไม่ซ้ำ)วัดด้วยอะไรตัวอย่างใน PHTRS
Performanceวินาที, ผู้ใช้พร้อมกันบันทึกรายงานและแสดง Report ID ภายใน 3 วินาที
Availability / Reliability% uptime, ชั่วโมงปิดปรับปรุงใช้งานได้ 99.5% ต่อเดือน ปิดปรับปรุงเฉพาะ 00:00–04:00
Securityมาตรฐานการเข้ารหัส, สิทธิ์รหัสผ่านเก็บแบบ hash, ส่งข้อมูลผ่าน HTTPS, เจ้าหน้าที่เห็นเฉพาะงานของตน
Usabilityเวลาที่ผู้ใช้ใหม่ทำงานสำเร็จ, % ผู้ทดสอบผู้ใช้ใหม่ส่งรายงานสำเร็จใน 3 นาทีโดยไม่ต้องอ่านคู่มือ
Compatibility / Portabilityรายชื่อเบราว์เซอร์, ขนาดจอใช้ได้บน Chrome, Safari, Edge และจอมือถือกว้าง 360 px ขึ้นไป
Capacity / Storageจำนวนรายการ, MBรูปแนบไม่เกิน 5 MB ต่อรูป · รองรับรายงาน 1,000,000 รายการ
Legal (External)กฎหมาย / มาตรฐานเก็บเลขบัตรประชาชนตาม พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล (PDPA)
⭐ คำต้องห้ามใน NFR ถ้าไม่มีตัวเลขกำกับ: ง่าย, เร็ว, เสถียร, ปลอดภัย, สวย, มีประสิทธิภาพ, ตลอดเวลา, เหมาะสม · และห้ามเขียนฟังก์ชันปนมา เช่น "ผู้ใช้ติดตามสถานะได้" เป็น functional ถ้าจะเป็น NFR ต้องพูดถึงคุณภาพ เช่น "หน้าติดตามสถานะแสดงข้อมูลล่าสุดไม่ช้ากว่า 1 นาทีหลังเจ้าหน้าที่อัปเดต"

US1 AC1Given "เข้าเว็บไซต์" ยังไม่บอกว่า login แล้ว · Then "ระบบมีข้อมูลเพิ่มขึ้น" ผู้ใช้มองไม่เห็นและทดสอบไม่ได้Then: ระบบบันทึกรายงาน แสดง Report ID และสร้าง Work Order ส่งให้เจ้าหน้าที่

US2 AC2สลับ Given กับ When "กรอกรหัสผิด" เป็นการกระทำ ต้องอยู่ใน WhenGiven: อยู่หน้าเข้าสู่ระบบ · When: กรอกรหัสผ่านผิดแล้วกดเข้าสู่ระบบ · Then: แสดง "ชื่อผู้ใช้หรือรหัสผ่านไม่ถูกต้อง"
US3"ต้องการรายงานข้อมูล…จากระบบ" อ่านไม่ออกว่าจะส่งหรือรับ · "เพื่อที่" มีสองเป้าหมาย (ซ่อม + บันทึก) · Then "บันทึกการทำงาน ค่าใช้จ่ายต่าง" ไม่ครบประโยคแยกเป็น 2 story: ดู Work Order ที่ได้รับ และ บันทึกผลการซ่อม · Then ให้บอกค่าที่ระบบคำนวณออกมา
US4ขอรายงาน 3 แบบใน story เดียว (ใหญ่เกินไป เป็น epic) · "เพื่อที่" ลอกวัตถุประสงค์ระบบ · AC1 เปลี่ยนสถานะเป็นเสร็จ ไม่เกี่ยวกับการดูรายงาน (และตามโจทย์เจ้าหน้าที่เป็นคนตั้งสถานะ) · AC2 เรื่อง login ไม่เกี่ยวกับ storyเลือกรายงานเดียว เช่น สรุปถนนชำรุดแยกเขต/ระดับ · AC: เลือกเขตแล้วเห็นจำนวนหลุมแยกตามระดับ 1–10 / เลือกเขตที่ไม่มีข้อมูลแล้วเห็น "ไม่มีรายงาน"
US5 AC1ตรรกะขัดกัน: Given เข้าสู่ระบบแล้ว แต่ When ลืม password และ Then "password ผิด" · "ลืม" เป็นสิ่งที่ระบบตรวจไม่ได้ตัดทิ้ง หรือเปลี่ยนเป็นกรณีกรอกรหัสผิด 5 ครั้งแล้วระบบล็อกบัญชี 15 นาที
NFR 1 และ 4เป็นเรื่องเดียวกัน (ใช้ได้ตลอด ยกเว้นปิดปรับปรุง) และวัดไม่ได้ · ข้อ 4 "ติดตามได้" เป็น functionalรวมเป็นข้อเดียว: "ใช้งานได้ 99.5% ต่อเดือน ปิดปรับปรุงไม่เกิน 4 ชม./เดือน ช่วง 00:00–04:00"
NFR 2มีตัวเลข ✓ แต่บอกแค่จำนวน ไม่บอกว่ารองรับแล้วต้องเร็วแค่ไหน"…100,000 คนพร้อมกัน โดยหน้าเว็บตอบสนองภายใน 3 วินาที"

NFR ที่ขาดไม่มีด้าน security เลย ทั้งที่ระบบมี login และข้อมูลส่วนบุคคลเพิ่ม HTTPS + hash รหัสผ่าน หรือ PDPA

User story #5

ในฐานะ หัวหน้างาน ฉันต้องการ ดูรายงานสรุปถนนชำรุดแยกตามเขตและระดับความรุนแรง เพื่อที่ จัดลำดับเขตที่ต้องซ่อมก่อนและวางงบประมาณได้

ACGivenWhenThen
1มีรายงานถนนชำรุดในระบบเลือก "รายงานสรุปถนนชำรุด" และเลือกเขตบางกะปิระบบแสดงจำนวนหลุมของเขตบางกะปิแยกตามระดับ 1–10 พร้อมยอดรวม
2หัวหน้างานอยู่ที่หน้ารายงานสรุปเลือกเขตที่ยังไม่มีรายงานระบบแสดง "ไม่มีรายงานในเขตนี้" และยอดรวม 0

ข้อที่ใช้แทนกันได้: หัวหน้างานดูรายงานสรุปค่าใช้จ่าย (แรงงาน วัสดุ อุปกรณ์ รวม) · หัวหน้างานดูรายงานสรุปการซ่อม (สถานะ/ความคืบหน้า) · ประชาชนแนบรูปภาพ

เปิดดู 5 NFR
  1. Performance: ระบบต้องบันทึกรายงานและแสดง Report ID ภายใน 3 วินาทีสำหรับ 95% ของคำขอ ขณะมีผู้ใช้พร้อมกัน 5,000 คน
  2. Availability: ระบบต้องใช้งานได้อย่างน้อย 99.5% ต่อเดือน ปิดปรับปรุงได้เฉพาะ 00:00–04:00 และแจ้งล่วงหน้าบนเว็บไซต์ 24 ชั่วโมง
  3. Security: รหัสผ่านต้องเก็บแบบ hash (เช่น bcrypt) และข้อมูลทั้งหมดต้องรับส่งผ่าน HTTPS (TLS 1.2 ขึ้นไป)
  4. Usability: ผู้ทดสอบที่ไม่เคยใช้ระบบ อย่างน้อย 90% ต้องส่งรายงานสำเร็จภายใน 3 นาทีโดยไม่อ่านคู่มือ
  5. Compatibility: เว็บไซต์ต้องใช้งานได้บน Chrome, Safari และ Edge สองเวอร์ชันล่าสุด และบนจอมือถือกว้าง 360 px ขึ้นไป

Lab 4: Use case diagram + Use case narrative 2 กรณี

ขั้นตอนวาด diagram

  1. วาดกรอบระบบ แล้วเขียนชื่อระบบไว้ด้านบน
  2. วาด actor ไว้นอกกรอบ: คนไว้ซ้าย ระบบภายนอก (Google Maps) ไว้ขวา
  3. ไล่ตารางสกัดโจทย์ทีละแถว ทุกกริยาเป็นหนึ่ง use case ตั้งชื่อแบบ กริยา + กรรม ("รายงานถนนชำรุด" ไม่ใช่ "รายงาน")
  4. ลากเส้น association (เส้นทึบ ไม่มีหัวลูกศร) จาก actor ไป use case ที่เขาทำ
  5. ใส่ include / extend เฉพาะจุดที่โจทย์บอก ("ต้อง" → include · "สามารถ…เพิ่มเติมได้" → extend)
  6. ถ้า actor หลายตัวทำ use case เดียวกัน (เช่น เข้าสู่ระบบ) ให้ใช้ actor แม่แบบ abstract แล้วลาก generalization
  7. ไล่เช็กย้อนว่าทุกประโยคในโจทย์มี use case รองรับ
สัญลักษณ์หน้าตาทิศลูกศรใช้เมื่อ
Associationเส้นทึบ ไม่มีหัว—actor มีส่วนร่วมกับ use case
<<include>>เส้นประ หัวเปิดbase → ตัวที่ถูก includeต้องทำทุกครั้ง: รายงานถนนชำรุด → ระบุตำแหน่งบนแผนที่
<<extend>>เส้นประ หัวเปิดส่วนเสริม → baseทำหรือไม่ทำก็ได้: แนบรูปภาพ → รายงานถนนชำรุด
Generalizationเส้นทึบ หัวสามเหลี่ยมโปร่งลูก → แม่หัวหน้างาน/เจ้าหน้าที่/ผู้ใช้ทั่วไป → ผู้ใช้ที่มีบัญชี
💡 จำทิศง่าย ๆ: include ชี้ไปหา "สิ่งที่ต้องทำด้วย" · extend ชี้กลับไปหา "ตัวหลักที่มันไปต่อ" · generalization ชี้ไปหาแม่ (เหมือน inheritance ใน OOP)

หัวลูกศรที่ชี้ไป "ทุกคน" เป็นหัวเล็ก ๆgeneralization ต้องใช้หัวสามเหลี่ยมโปร่ง (▷) ถ้าหัวผิด อาจารย์อาจอ่านว่าเป็นเส้นแบบอื่น
ชื่อ actor "ทุกคน"ตั้งชื่อเป็นบทบาทให้ชัด เช่น "ผู้ใช้ที่มีบัญชี" หรือ "ผู้ใช้ระบบ"
"ตรวจสอบ" ต่อกับ "ทุกคน"ในโจทย์ หัวหน้างานเป็นคนตรวจสอบรายงาน ย้ายเส้นไปที่หัวหน้างาน และตั้งชื่อเต็ม "ตรวจสอบรายงานความเสียหาย" (ส่วนการตรวจดูของผู้ใช้ทั่วไปรวมอยู่ใน "ติดตามสถานะรายงาน")
ชื่อสั้นเกินไป: "สร้างรายงาน", "ติดตาม", "อัปเดตข้อมูล"โจทย์มีทั้ง "รายงานถนนชำรุด" และ "รายงานสรุป" คำว่าสร้างรายงานจึงกำกวม เปลี่ยนเป็น "รายงานถนนชำรุด", "ติดตามสถานะรายงาน", "บันทึก/อัปเดตผลการซ่อม"
ขาด "ดูรายงานสรุป" ของหัวหน้างานโจทย์ย่อหน้าสุดท้ายบอกไว้ทั้งย่อหน้า เป็นจุดที่ถูกหักได้ง่ายที่สุด
หัวหน้างานดูคำสั่งงานได้ด้วย"หัวหน้างานสามารถเข้าดูคำสั่งงาน" จึงควรลากเส้นจากหัวหน้างานไป "ดูคำสั่งงาน" ด้วย
ไม่มีเรื่องคำนวณค่าใช้จ่ายระบบคำนวณเองทุกครั้งที่บันทึกหรืออัปเดต วาดเป็น บันทึก/อัปเดตผลการซ่อม ─<<include>>→ คำนวณค่าใช้จ่าย ได้ (ไม่บังคับ แต่แสดงว่าอ่านโจทย์ครบ)
"สร้างคำสั่งงาน" กับ "มอบหมาย" แยกกันไม่ผิด แต่โจทย์เขียนเป็นการกระทำเดียว ("สร้างคำสั่งงานและมอบหมายงาน") รวมเป็น use case เดียวจะดูเป็นเป้าหมายเดียวของหัวหน้างานมากกว่า

Lab 6: Context diagram (DFD Level 0)

Lab นี้ใช้โจทย์เดียวกับ Lab 4 และยังไม่ได้ส่ง ส่วนนี้จึงเป็นวิธีทำและตัวอย่างเฉลย

ขั้นตอน

  1. วาดวงกลม process เดียว ตรงกลาง ใส่เลข 0 และชื่อระบบ
  2. วาดสี่เหลี่ยม external entity ตาม actor ใน Lab 4 (ผู้ใช้งานทั่วไป, หัวหน้างาน, เจ้าหน้าที่, Google Maps) · actor abstract ไม่นับ
  3. ไล่ทีละ entity ถามสองคำถาม: "เขาป้อนอะไรเข้าระบบ" (ลูกศรเข้า) และ "เขาได้อะไรกลับไป" (ลูกศรออก)
  4. ตั้งชื่อลูกศรทุกเส้นเป็นคำนามของข้อมูล เช่น "ข้อมูลรายงานถนนชำรุด" ไม่ใช่ "รายงาน" หรือ "ลงทะเบียน"
  5. เช็กกฎ: ไม่มี data store · ไม่มีเส้น entity–entity · ทุกเส้นมีชื่อและหัวลูกศร
💡 วิธีแปลง use case เป็น data flow: use case หนึ่งตัวมักให้ลูกศรเข้า 1 เส้น (สิ่งที่ผู้ใช้กรอก) และลูกศรออก 1 เส้น (สิ่งที่ระบบตอบกลับ)
รายงานถนนชำรุด→เข้า: ข้อมูลรายงานถนนชำรุดออก: Report ID
ดูรายงานสรุป→ออก: รายงานสรุป 3 ประเภท
บันทึกผลการซ่อม→เข้า: ข้อมูลผลการซ่อมออก: ค่าใช้จ่ายที่คำนวณ

ตัวอย่างเฉลย context diagram

รายงานสรุป 3 ประเภทจะแยกเป็น 3 เส้นก็ได้ (รายงานสรุปถนนชำรุด · รายงานสรุปการซ่อมแซม · รายงานสรุปค่าใช้จ่าย) ถ้ามีที่พอ ส่วนเส้น "ข้อมูลเข้าสู่ระบบ" บางอาจารย์ไม่ต้องการ ถ้าไม่แน่ใจให้ใส่ไว้ เพราะเป็นข้อมูลที่ไหลเข้าระบบจริง

กับดักใน Lab 6 (ตัวที่โจทย์ PHTRS ล่อให้ผิด)

ที่ผิดเหตุผลที่ถูก
วาด data store "ฐานข้อมูลรายงาน" เพราะโจทย์บอกว่า "ข้อมูลทั้งหมดจะถูกจัดเก็บในระบบ"ที่เก็บข้อมูลอยู่ข้างในระบบ จึงถูกรวมอยู่ใน process 0 แล้วไม่วาด data store ใน context diagram (ไปวาดใน Level 1)
หัวหน้างาน → เจ้าหน้าที่ "มอบหมายงาน"ห้ามลากเส้น entity–entity เพราะไม่ผ่านระบบหัวหน้างาน → ระบบ "ข้อมูลคำสั่งงาน" แล้วระบบ → เจ้าหน้าที่ "คำสั่งงานที่ได้รับมอบหมาย"
วาด process ย่อย เช่น "คำนวณค่าใช้จ่าย" เป็นวงกลมที่สองcontext diagram มี process เดียวใช้ผลของมันเป็นลูกศรออก "ค่าใช้จ่ายที่คำนวณ"
ชื่อลูกศรเป็นกริยา: "ลงทะเบียน", "login", "ตรวจสอบ"data flow คือข้อมูล ไม่ใช่การกระทำ"ข้อมูลลงทะเบียน", "ข้อมูลเข้าสู่ระบบ", "ผลการตรวจสอบรายงาน"
ลูกศรสองหัวเส้นเดียว ชื่อ "ข้อมูล"ไม่รู้ว่าอะไรไปทางไหนแยกเป็นเส้นเข้าและเส้นออก ชื่อเฉพาะแต่ละเส้น
ลืม Google Mapsระบบภายนอกที่แลกข้อมูลกับระบบก็เป็น entityระบบ → Google Maps "คำขอแผนที่/พิกัด" · Google Maps → ระบบ "ข้อมูลแผนที่และพิกัด"
ใส่ "ทุกคน / ผู้ใช้ที่มีบัญชี" เป็น entityเป็น actor นามธรรมใน use case diagram ไม่ได้มีตัวตนแยกใช้ entity ของคนจริงแต่ละบทบาท
process เลข 1 หรือไม่มีเลขcontext diagram = level 0เลข 0 + ชื่อระบบ

  • ไม่มี data store · ไม่มีเส้น entity–entity · ทุกเส้นมีชื่อเป็นคำนามและมีหัวลูกศร

  1. อ่านโจทย์และขีด 4 สี (5 นาที) ทำตารางสกัด actor / use case / ข้อมูลเข้า / ข้อมูลออก ไว้มุมกระดาษ
