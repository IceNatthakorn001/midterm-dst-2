Lecture 9 – Design Architecture and Methodology

⏱ อ่านประมาณ 10 นาที · 14 หัวข้อ

📖 ฉบับเต็ม⚡ สรุปสั้น

1. ทำไมต้องออกแบบ? (สไลด์ 4–6, 9)

แก่นrequirement เดียวสร้างได้หลายแบบ ต้องตัดสินใจโครงสร้างก่อน: มี component อะไร สัมพันธ์กันยังไง

  • สะพาน 6 แบบ (beam, arch, truss, cantilever, suspension, cable-stayed) | HelloWorld 3 แบบ (1 class → MessagePrinter → HelloProvider+WorldProvider+MessagePrinter)
  • เริ่มจาก requirements | 2 ส่วน: Architectural (high-level) + Detailed

2. Architectural vs Detailed (สไลด์ 7–13)

แก่นarchitectural = ส่วนหลัก + ความสัมพันธ์ | detailed = ข้างใน component | detailed มาจาก requirements & architecture

  • Analysis model 4 กลุ่ม (scenario-based, class-based, flow-oriented, behavioral) → Design model พีระมิด (ฐาน→ยอด): Data/Class → Architectural → Interface → Component-level
Architectural Detailed
นิยาม major parts; responsibilities, properties, interfaces; relationships & interactions internal elements ของ component + data structure + algorithm
Key components Layers & Modules, Components & Services, Data Flow & Storage, Security & Performance, Scalability & Maintainability, Integration & APIs Module-level, Class & Object, Function & Algorithm, DB Schema, Interface & API, Error Handling & Logging, Security
  • ⭐ แบบฝึก (แนวคำตอบ ไม่มีเฉลยในสไลด์): 1 binary search = D | 2 แยก UI = A | 3 เวลา client/server = A | 4 hash table = D | 5 thread-safe library = A | 6 Car register Clock = D | 7 implement ClockUser = D

3. Architectural styles 6 แบบ (สไลด์ 14–22)

แก่นpipe&filter, data-centered, layered, client-server, microservice, call&return

Style หลักคิด ⭐ Pros ⭐ Cons
Batch seq. / Pipe&filter data ผ่าน filter (แปลง) ต่อด้วย pipe reuse filter, งานคำนวณเป็นลำดับอิสระ ไม่เหมาะ interactive, ต้องเพิ่ม filter ให้เข้ากัน, อาจ tight coupling
Data-centered central repository ใครก็ CRUD ได้ แชร์ข้อมูลมาก, component อิสระ, backup กลาง แก้ data model ยาก/แพง, ต้องใช้ data model ร่วม
Layered ชั้นพึ่งเฉพาะชั้นล่าง (UI→Application→Utility→Core) portable, แตกปัญหา, เปลี่ยนชั้นได้ถ้า interface เดิม แยกชั้นชัดยาก, ชั้นเยอะ = ช้า
Client-server server = provider, client = requester distributed, เพิ่ม/อัปเกรด server ง่าย third-party server จัดการยาก, server ล้น
Microservice suite of small services, process ของตัวเอง, HTTP API, deploy แยกอัตโนมัติ (สไลด์ไม่มีตาราง) (สไลด์ไม่มีตาราง)
Call & return main → controller → application program modular, scale/แก้ง่าย interface ไม่ชัด → tight coupling, แก้ data structure กระทบโมดูลอื่น
  • Call & return = most dominant ตั้งแต่ยุคแรก | Microservice เทียบ monolith (single DB) vs microservices (application DBs)

4. Structured design (สไลด์ 23–31)

แก่นDFD → call&return (structure chart) | บน = ตัดสินใจ ล่าง = worker

  • Objective: partitioned architecture | Approach: map DFD + PSPEC & STD บอกเนื้อในโมดูล | Notation: structure chart
  • Transform flow = ไหลเป็นสาย | Transaction flow = มี transaction center แตกหลาย action path
  • Mapping: แยก incoming/outgoing boundary (transaction → แยก center) → map จาก boundary ออกนอก → เพิ่ม control module → refine ด้วย modularity → ⭐ first-level factoring → second-level factoring
  • ⭐ Factoring: บน = decision-making, ล่าง = input/computation/output (worker), กลาง = control บ้าง ทำงานปานกลาง, control แบบ top-down
  • Transform mapping: a…j → x1 (บน) → x2 (ขาเข้า b,c,a) | x3 (กลาง d,e,f) | x4 (ขาออก g,h,i,j)
  • ⭐ First-level = input / processing / output controller | Second-level = map จาก flow boundary ออกนอก

5. ตัวอย่างหุ่นยนต์ (สไลด์ 32–36)

แก่นDFD L1 → L2 → isolate flow paths → map → refine

  • Top = process operator commands → command input controller (read / validate command / produce error message) + determine type → fixture status controller (read fixture status / determine setting / format setting), report generation controller (read record / calculate output values / format report), send control value

6. Logical vs Physical module (สไลด์ 37–39)

แก่นlogical = business activity (ทำอะไร) | physical = physical process (ทำยังไง)

  • ตัวอย่าง: Login (logical) → Two Factor Authentication 2 server (physical)
  • ระบบไปรษณีย์: analysis chart 6 โมดูล (Create Parcel, Update Parcel info, View history & status, Feedback, Bank@post, Pay Online) | design chart: Login, Deduct Balance เป็นโมดูลกลางที่หลายตัวใช้ร่วม → เขียนโค้ด Create_Parcel() เรียก Fill/Create tracking/Calculate weight/Update history
  • ⚠️ สไลด์ 38 ข้าม 1.2 และมี 4.1 ซ้ำ

7. Design process & principles (สไลด์ 40–43)

แก่นSRS → candidate หลายแบบ → ประเมิน → design document | principles = อะไรทำให้ design ดีขึ้น

  • ⭐ Basic (ตอบ stakeholder): Feasibility (ต้องสร้างได้), Adequacy (ตอบความต้องการมากกว่า), Economy (ถูก/เร็ว/เสี่ยงน้อย), Changeability (แก้ง่าย)
  • ⭐ Constructive (จากประสบการณ์): Modularity, Implementability (สร้างง่าย), Aesthetic (สวย)

8. Modularity (สไลด์ 44–49)

แก่นหน่วยที่ well-defined, simple, independent คุยผ่าน well-defined interface

  • หน่วย: sub-system → package → class/function → attribute/operation/block → lines of code
  • ข้อดี: เข้าใจ, ทำเอกสาร, แก้, test/debug, tune ง่าย
  • Software modularity: Services / Components / Objects / Modules
  • ⭐ 5 หลัก: Small modules | Information hiding | Least privilege | Cohesion (relatedness ภายใน) | Coupling (dependence ระหว่าง)

9. Cohesion & Coupling (สไลด์ 50–55)

แก่นcohesion ยิ่งสูงยิ่งดี | coupling ยิ่งต่ำยิ่งดี

  • Staff: email+printLetter = low cohesion | salary/email + get/set = high cohesion
  • ⭐ Cohesion: Functional (1 หน้าที่, สูงสุด) … Coincidental (หลายหน้าที่ไม่เกี่ยวกัน, ต่ำสุด)
  • ⭐ Coupling: Content (เข้าถึง internal data, สูงสุด) … Data (ส่งเฉพาะที่จำเป็น) … No coupling (ideal แต่ทำไม่ได้)
  • High coupling → แก้ตัวเดียวกระทบทุกตัวที่เชื่อม
  • Data coupling: arg ธรรมดา หรือ structure ที่ใช้ทุก element | เขียน contract ง่าย แก้แยกได้
  • ⭐ High level = cohesion Strong / coupling Tight | Low level = Weak / Loose
  • ⚠️ สไลด์ 53 วาง "No coupling" ใต้ "Data coupling (lowest)" ตีความกำกวม

10. แบบฝึก (สไลด์ 56–60) — แนวคำตอบ

  • 56: 1 low cohesion | 2 high coupling | 3 high cohesion | 4 low coupling | 5 high coupling | 6 high cohesion
  • 57: A ส่ง name/address/billing ตรงกับ data coupling (B เป็น data coupling ด้วยถ้าใช้ทุก element) ⚠️ กำกวม
  • 58: A ดีกว่า (coupling): ส่ง ID/Address vs ใช้ global variable ร่วม
  • 59: A ดีกว่า (cohesion): FileReader vs DataProcessor
  • 60: B ดีกว่า (cohesion): EmployeeDatabase vs Utility catch-all

11. Implementability & Aesthetic (สไลด์ 61–63)

แก่นสร้างง่าย + สวย

  • ⭐ Implementability: Simplicity | Design with reuse (ใช้ของเดิม) | Design for reuse (สร้างของให้ใช้ซ้ำ)
  • ⭐ Aesthetic: Beauty (เรียบ ไม่ซ้ำซ้อน, ไม่ใช่ UI) | Symmetry (คล้ายกันออกแบบคล้ายกัน) | Balance (ไม่มี God class) | Proportion (ขนาดพอดี)
  • Beauty: calc(a,b,op) if-else = hardcoded, not extensible, low readability | interface Operation + Add, Multiply = simple, extensible, separation of concerns

12. Relationship among principles (สไลด์ 64)

  • เสริมกัน: Cohesion+Coupling+Information hiding | Simplicity+Beauty | Simplicity+Small modules
  • ⭐ ขัดกัน: Simplicity ↔ Design for reuse | Small modules ↔ Design for reuse | Cohesion ↔ Small modules
  • ขึ้นกับกรณี

13. Summary (สไลด์ 65)

  • design = principles + concepts + practices → model ที่ implement ทุก requirement | architecture = holistic view | design principles = แนวทางออกแบบ component

คู่ที่มักสับสน

A B ต่างกัน
Architectural Detailed ระดับระบบ vs ข้างใน component
Cohesion Coupling ภายใน (สูงดี) vs ระหว่าง (ต่ำดี)
Strong/Weak Tight/Loose คำของ cohesion vs คำของ coupling
Functional Coincidental 1 หน้าที่ vs หลายหน้าที่ไม่เกี่ยวกัน
Content Data coupling เข้าถึงไส้ใน vs ส่งเฉพาะที่จำเป็น
Transform flow Transaction flow สายตรง vs transaction center
Logical Physical module ทำอะไร vs ทำยังไง
Design with reuse Design for reuse ใช้ของเดิม vs สร้างให้ใช้ซ้ำ
Basic Constructive ตอบ stakeholder vs จากประสบการณ์
