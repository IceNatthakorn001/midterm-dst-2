1. Software Process L2

กิจกรรมพื้นฐาน 6 อย่าง ⭐

ทุกโมเดลมีกิจกรรมเหมือนกัน ต่างกันแค่ลำดับ จำนวนรอบ และความละเอียด

  1. Requirements analysis
  2. System and software design
  3. Implementation (coding)
  4. Testing and quality assurance
  5. Deployment and release
  6. Maintenance and evolution

Layered Technology ⭐

บนลงล่าง: Tools → Methods → Process → Quality focus

  • Quality focus = ฐานของทุกอย่าง
  • Process = ตัวยึดทุกชั้นไว้ด้วยกัน กำหนดกรอบงาน
  • Methods = วิธีทำเชิงเทคนิค
  • Tools = ช่วยทำให้ง่ายหรืออัตโนมัติ

Process Framework

  • Framework activities = กิจกรรมหลัก
  • Task sets = work tasks + work products + milestones/deliverables + QA checkpoints
  • Umbrella activities = ทำตลอดโครงการ

Process framework = กรอบวิธีทำงาน / Development framework (React, Django) = โครงโค้ดสำเร็จรูป

Umbrella Activities 8 อย่าง ⭐

Software project management · Formal technical reviews · Software quality assurance · Software configuration management · Work product preparation and production · Reusability management · Measurement · Risk management

Process model คืออะไร / ต้องกำหนดอะไร ⭐

เป็นกรอบมาตรฐานที่ประสานงานและควบคุม task กับคนทำ task (คำสำคัญ: coordination, tasks, people) มีไว้ 3 อย่าง: วางแผนและบริหาร / ทำให้งานสม่ำเสมอมีคุณภาพ / ช่วยสื่อสารระหว่าง stakeholder

ต้องกำหนด 5 อย่าง: (1) ชุดของ task (2) input/output ของแต่ละ task (3) pre-/post-conditions (4) ลำดับการไหลของ task (5) คนทำแต่ละ task

เปรียบเทียบโมเดล ⭐⭐

โมเดลลักษณะเด่นเหมาะกับข้อดีข้อเสีย
Code and Fixเขียน → ทดสอบ → แก้ วนไปงานเล็กมากเริ่มเร็วมักข้าม test, เริ่มทั้งที่ยังไม่เข้าใจ requirement
Waterfallเส้นตรง ไม่ซ้อนทับ จบช่วงหนึ่งก่อนเริ่มช่วงถัดไป · deliverable ของช่วงหนึ่งเป็น input ช่วงถัดไป · เน้นเอกสารrequirement ชัดและไม่เปลี่ยนเข้าใจง่าย, เอกสารครบไม่ยืดหยุ่น, เจอปัญหาช้า (test หลังเขียนโค้ดเสร็จ), ใช้เวลานาน
Incrementalแบ่ง requirement เป็นชิ้น
A = integration bucket (รวมแล้วส่งครั้งเดียว)
B = multiple release (ส่งทีละ release)		ระบบใหญ่ ซับซ้อนDivide and conquerต้องทำงานขนาน, บริหารมากขึ้น, integration ยาก
Spiralวนเกลียว 4 quadrant: Plan → Objectives/Alternatives/Constraints → Evaluate & resolve risks (prototype) → Develop & verify · รอบใหญ่ขึ้นเรื่อย ๆโครงการใหญ่ ความเสี่ยงสูงบังคับให้มี prototype, แก้ของรอบก่อนได้ต้องมีผู้เชี่ยวชาญประเมินความเสี่ยง
Agile / Scrumรอบสั้น, ลูกค้ามีส่วนร่วมตลอด, รับการเปลี่ยนแปลงrequirement ไม่แน่นอน ต้องออกเร็วยืดหยุ่น, ส่งของเร็ว, เจอปัญหาเร็วคาดการณ์เวลาและเงินยาก, ต้องมีทีมที่มีวินัย, ยากกับ scope ตายตัว

Agile Manifesto ⭐ (ซ้าย over ขวา)

  • Individuals and interactions over processes and tools
  • Working software over comprehensive documentation
  • Customer collaboration over contract negotiation
  • Responding to change over following a plan

"over" ไม่ได้แปลว่าไม่เอาด้านขวา แค่ให้ค่าด้านซ้ายมากกว่า

Scrum ⭐

  • Vision → Product Backlog (เรียงตามความสำคัญ) → Sprint Backlog
  • Sprint 2–4 สัปดาห์ · Daily Scrum ทุก 24 ชม.
  • จบ sprint ได้ Potentially Shippable Product Increment
  • ทีม cross-functional

2. Requirements Engineering L3

RE = กระบวนการ ค้นหา วิเคราะห์ จัดทำเอกสาร และตรวจสอบ requirement · เป็นกระบวนการวนซ้ำ · output = system requirements document

ประเภทของ requirement ⭐⭐

User vs System

  • User req. = ภาษาที่ลูกค้าเข้าใจ บอกบริการและข้อจำกัด · ผู้อ่าน: client managers, contractor managers, end-users, client engineers, architects
  • System req. = ละเอียด บอกชัดว่าต้อง implement อะไร · ผู้อ่าน: end-users, client engineers, architects, software developers
  • ตัวอย่าง Mentcare: user req. 1 ประโยค (รายงานค่ายารายเดือน) → system req. 5 ข้อ (1.1–1.5)

Functional vs Non-functional

  • Functional = ระบบทำอะไร ตอบสนอง input อย่างไร
  • Non-functional = ข้อจำกัด/คุณภาพ (เวลา, ความปลอดภัย, ความพร้อมใช้) มักใช้กับทั้งระบบ
  • NFR ต้อง measurable & testable
NFR (Sommerville)มาจากประเภทย่อย
Productพฤติกรรมตัวผลิตภัณฑ์Usability, Efficiency (Performance, Space), Dependability, Security
Organizationalนโยบาย/ขั้นตอนขององค์กรEnvironmental, Operational, Development
ExternalปัจจัยภายนอกRegulatory, Ethical, Legislative (Accounting, Safety/security)

หน่วยวัด: Speed = transactions/sec, response time · Size = MB · Ease of use = training time · Reliability = mean time to failure, availability · Robustness = time to restart · Portability = % target-dependent statements

Feasibility study ⭐

ทำต้น RE สั้นและเจาะจง ตอบ 3 คำถาม: ช่วยเป้าหมายองค์กรไหม? · สร้างได้ในเวลาและงบด้วยเทคโนโลยีปัจจุบันไหม? · รวมกับระบบเดิมได้ไหม? → ข้อใดตอบ "ไม่" ไม่ควรทำต่อ

RE process: Elicitation → Specification → Validation → Change

Elicitation ⭐

  • ความยาก 4 ข้อ: stakeholder ไม่รู้ว่าต้องการอะไร · อธิบายยาก · ขอสิ่งที่เป็นไปไม่ได้ · แต่ละกลุ่มต้องการต่างกันและพูดคนละแบบ
  • วงจร 4 ขั้น: Discovery & understanding → Classification & organization → Prioritization & negotiation → Documentation
  • 6 dimensions: individual functionality, business workflow, data & formats, user interfaces, existing systems & interfaces, other constraints
  • Interview (closed = มีชุดคำถาม / open = คุยเปิด) · ห้ามถาม "tell me what you want" · ไม่เหมาะกับ requirement ระดับองค์กร (มีเรื่องอำนาจ)
  • Ethnography = เข้าไปดูงานจริง → ได้ implicit requirements ที่สะท้อนวิธีทำงานจริง
  • อื่น ๆ: sampling เอกสาร/ฟอร์ม/DB, research & site visits, questionnaires, JRP

Specification

  • ดี = clear, unambiguous, easy to understand, complete, consistent
  • "shall" = mandatory / "should" = desirable ⭐ · หลีกเลี่ยง jargon/ตัวย่อ · ใส่ rationale
  • รูปแบบ: natural language · structured spec · use case · prototyping (low/high fidelity) · DFD, ERD
  • Structured spec 10 ช่อง: ID, type, description, rationale, source, inputs, outputs, action, precondition, postcondition
  • User story: As a … I want … so that … · วัดด้วย acceptance criteria / DoD · ลำดับ User need → Epic → User story → Tasks/AC
  • Acceptance criteria เขียนแบบ Given–When–Then ต้องไม่กำกวมและวัดได้ · Then ของข้อก่อนมักเป็น Given ของข้อถัดไป

SRS

ผู้ใช้ SRS: customers (ระบุ requirement และการเปลี่ยนแปลง) · managers (วางแผน bid) · system engineers · test engineers (สร้าง validation test) · maintenance engineers

Change & management

requirement เปลี่ยนเพราะเป็น wicked problem และความเข้าใจของ stakeholder เปลี่ยน · Planning (ก่อน): requirement ID, change process, traceability policy, tools · Change management (หลังเอกสารอนุมัติ): problem analysis → change analysis & costing → change implementation

3. Use Case Diagram L4

"Use cases define what exists outside the system (actors) and what should be performed by the system (use cases)" — Jacobson

สัญลักษณ์รูปกฎ
Actorคนก้างอยู่นอกกล่อง · คนหรือระบบภายนอกก็ได้ · primary (ใช้เพื่อเป้าหมายตัวเอง) / secondary (สนับสนุน เช่น payment gateway, SMS)
Use caseวงรีอยู่ในกล่อง · ชื่อ กริยา + กรรม (Place Order ไม่ใช่ Order Page) · 1 use case = 1 business task
System boundaryกล่องใส่ชื่อระบบ

4 ความสัมพันธ์ ⭐⭐

ความสัมพันธ์ระหว่างวิธีวาดใช้เมื่อ
Associationactor – use caseเส้นทึบ ไม่มีหัวลูกศรactor มีปฏิสัมพันธ์กับ use case
Inheritanceactor – actorเส้นทึบ หัวสามเหลี่ยมโปร่ง ชี้จากลูกไปแม่หลาย actor ทำ use case เดียวกัน → สร้าง abstract actor ลดเส้นซ้ำ
<<include>>use case – use caseเส้นประ base → includedส่วนที่ต้องทำทุกครั้ง / ใช้ร่วมหลาย use case / แยก use case ใหญ่
<<extend>>use case – use caseเส้นประ extending → baseส่วนเสริมที่ทำบางครั้ง (optional) base สมบูรณ์ได้โดยไม่มีมัน
ทดสอบ include/extend: "ทุกครั้งที่ทำ A ต้องทำ B ไหม?" ต้องทำ → A ─include→ B · แค่บางครั้ง → B ─extend→ A
จำทิศลูกศร: อ่านเป็นประโยค "Withdraw Cash includes Authentication", "Get Help extends Registration" → ลูกศรชี้ไปทางกรรมของประโยคเสมอ

6 ขั้นวาด use case diagram ⭐

  1. Identify system boundary — วาดกล่อง ใส่ชื่อระบบ
  2. Identify actors — คำนามที่เป็นคน ตำแหน่ง หรือระบบภายนอก (แยก primary/secondary)
  3. Identify use cases — คำกริยาที่ actor ทำกับระบบ (เป้าหมายของ actor)
  4. Establish relationships — association, include, extend, inheritance
  5. Draw — actor นอกกล่อง use case ในกล่อง
  6. Review & refine — ครบทุก functional requirement ไหม validate กับ stakeholder

ข้อผิดพลาดที่พบบ่อย

❌ ผิด✅ ถูก
ชื่อเป็นคำนามหรือหน้าจอ: "Payment Page", "Report"กริยา + กรรม: "Make Payment", "Generate Report"
ขั้นตอนย่อยเป็น use case: "Click Next", "ระบบแสดงราคา"ใส่เป็น step ใน narrative
actor อยู่ในกล่อง / ไม่มีชื่อระบบactor นอกกล่อง ชื่อระบบบนกล่อง
ลากเส้นระหว่าง actor กับ actor (association)ระหว่าง actor ใช้ได้แค่ inheritance
association มีหัวลูกศร หรือใช้เส้นประเส้นทึบ ไม่มีหัว
include/extend ทิศกลับ หรือใช้ include กับสิ่งที่ optionalใช้คำถาม "ต้องทำทุกครั้งไหม?"
ลาก Login include ทุก use case จนรกเขียน "login แล้ว" เป็น precondition ใน narrative (ถ้าอาจารย์ไม่ได้สั่งให้วาด Login)
ใส่ระบบตัวเองเป็น actor (เช่น "ระบบ")สิ่งที่ระบบทำเอง = step หรือ include · ระบบภายนอกเท่านั้นที่เป็น actor

4. Use Case Narrative L4

คำอธิบายเป็นข้อความทีละขั้นว่า actor โต้ตอบกับระบบอย่างไร 1 narrative ต่อ 1 use case มักเขียนเป็นตาราง 8 ช่อง

ช่องเขียนอะไรเคล็ดลับ
Use Case Nameชื่อ use caseต้องตรงกับใน diagram ทุกตัวอักษร
Primary Actorผู้เริ่ม use caseตรงกับ actor ที่ลากเส้นใน diagram
Goal in Contextactor ต้องการบรรลุอะไรเขียนเป็นประโยค "ใคร ทำอะไร เพื่ออะไร"
Preconditionสภาพที่ต้องเป็นจริงก่อนเริ่มเช่น "login แล้ว", "มีออเดอร์ที่ชำระแล้ว"
Triggerเหตุการณ์ที่ทำให้ use case เริ่มเช่น "นักศึกษากดปุ่ม 'สั่งอาหาร'" ไม่ใช่ "ต้องการสั่งอาหาร"
Scenario (main/basic flow)ขั้นตอนปกติที่สำเร็จใส่เลข · มีประธานทุกข้อ · สลับ actor ทำ ↔ ระบบตอบ
Exceptionเมื่อผิดพลาดหรือ input ไม่ถูกอ้างเลข step เช่น 3a + บอกว่าระบบทำอะไรต่อ
Postconditionสภาพระบบหลังจบสิ่งที่ตรวจได้: ข้อมูลถูกบันทึก สถานะเปลี่ยนเป็นอะไร ใครได้อะไร
Precondition ≠ Trigger — precondition เป็นสภาพที่เป็นอยู่แล้ว trigger เป็นเหตุการณ์ที่เกิดขึ้นตอนนั้น
ถ้าเขียน precondition ว่า "login แล้ว" อย่าเขียนขั้น login ซ้ำใน scenario

5. Context Diagram (DFD Level 0) L6

DFD ระดับบนสุด แสดงทั้งระบบเป็น process เดียว (เลข 0) และ external entity ทั้งหมดที่ส่งหรือรับข้อมูลกับระบบ

สัญลักษณ์Yourdon/DeMarcoGane/Sarsonตั้งชื่อ
External entityสี่เหลี่ยมสี่เหลี่ยม (มักมีเงา)คำนาม: คน องค์กร ระบบภายนอก
Processวงกลมสี่เหลี่ยมมุมมน มีช่องเลขใน context = เลข 0 + ชื่อระบบ
Data flowลูกศรลูกศรคำนาม บอกว่าเป็นข้อมูลอะไร (logical)
Data storeเส้นขนาน 2 เส้นสี่เหลี่ยมเปิดขวา + D1ไม่มีใน context diagram

กฎของ context diagram ⭐⭐

  • มี process เดียว เลข 0 มีชื่อ
  • มี input จาก entity อย่างน้อย 1 เส้น และ output ไป entity อย่างน้อย 1 เส้น
  • ไม่มี data store (ข้อมูลที่เก็บอยู่ข้างในระบบ ถูกยุบรวมไว้ใน process 0)
  • ไม่มีเส้น entity → entity (สิ่งที่เกิดนอกระบบไม่ต้องวาด) · ทุกเส้นต้องแตะ process
  • ทุกเส้นมีชื่อ เป็นคำนาม บอกข้อมูลไม่ใช่วิธี (Customer order ✅, SQL Query / Email ❌) · ห้ามใช้ชื่อกริยา เช่น "Send order"
  • ข้อมูลที่ไปด้วยกันเป็นเส้นเดียวได้ (data flow packet) · ข้อมูลต่างกันแยกเส้น
  • ใช้ notation สำนักเดียวทั้งแผ่น

วิธีวาดจากโจทย์ (หรือจาก use case diagram) ⭐

  1. วาดวงกลม 0 <ชื่อระบบ> ตรงกลาง
  2. actor ทุกตัว (ทั้ง primary และ secondary) → external entity · ถ้ามี inheritance รวมเป็น entity เดียวได้ (เช่น Borrower)
  3. ไล่ use case ทีละอัน แล้วถาม: actor ส่งข้อมูลอะไรเข้าระบบ? (ลูกศรเข้า) และ ได้ข้อมูลอะไรกลับไป? (ลูกศรออก)
  4. ตั้งชื่อทุกเส้นด้วยคำนาม
  5. ตรวจ: ไม่มี data store, ไม่มี entity–entity, ทุก entity มีเส้น, ไม่มีเส้นไหนไม่มีชื่อ
"ระบบคอมพิวเตอร์ทุกระบบแปลง input เป็น output" — context diagram คือภาพ input/output ทั้งหมดของระบบในแผ่นเดียว

โจทย์ 1: ระบบสั่งอาหารล่วงหน้าโรงอาหาร ฝึกเต็มชุด

Canteen Pre-order System ของมหาวิทยาลัย ให้นักศึกษาสั่งอาหารล่วงหน้าแล้วมารับโดยไม่ต้องต่อคิว

นักศึกษา สมัครสมาชิกด้วยรหัสนักศึกษาและอีเมล จากนั้นเข้าสู่ระบบ ดูเมนูของแต่ละร้านพร้อมราคา สั่งอาหารโดยเลือกร้าน เมนู จำนวน และเวลารับ ระบบคำนวณยอดรวม ถ้านักศึกษามีคูปองส่วนลดสามารถใส่รหัสคูปองได้ จากนั้นชำระเงินผ่าน QR Code ซึ่งระบบเชื่อมต่อกับ Payment Gateway ของธนาคาร เมื่อชำระสำเร็จระบบส่งออเดอร์ให้ร้านและแสดงรหัสรับอาหาร นักศึกษาติดตามสถานะออเดอร์ได้ และยกเลิกออเดอร์ได้ถ้าร้านยังไม่เริ่มทำ ระบบจะคืนเงินผ่าน Payment Gateway

ร้านค้า เข้าสู่ระบบเพื่อจัดการเมนู (เพิ่ม แก้ไข ปิดเมนูที่หมด) รับออเดอร์และอัปเดตสถานะ (กำลังทำ / พร้อมรับ) ซึ่งระบบจะแจ้งนักศึกษา และดูยอดขายของร้านตัวเอง

ผู้ดูแลระบบ จัดการบัญชีร้านค้า และสร้างรายงานยอดขายรวมของทุกร้านตามช่วงวันที่

Triggerผู้ยืมนำอุปกรณ์มาคืน และเจ้าหน้าที่กดเมนู "บันทึกการคืน"
Scenario1. เจ้าหน้าที่ค้นหารายการด้วยเลขคำขอหรือรหัสผู้ยืม
2. ระบบแสดงอุปกรณ์ จำนวน และวันกำหนดคืน
3. เจ้าหน้าที่ตรวจสภาพและยืนยันจำนวนที่คืน
4. ระบบบันทึกวันที่คืนและเพิ่มจำนวนคงเหลือ
5. ระบบเปลี่ยนสถานะรายการเป็น "คืนแล้ว"
Extension points: หลังขั้น 3 ถ้าชำรุด → Record Damage · หลังขั้น 4 ถ้าคืนช้า → Charge Late Fee
Exception1a. ไม่พบรายการ: ระบบแจ้งให้ตรวจเลขคำขอ
3a. คืนไม่ครบ: ระบบบันทึกเฉพาะจำนวนที่คืน สถานะเป็น "คืนไม่ครบ"
Postconditionรายการยืมมีสถานะ "คืนแล้ว" · จำนวนคงเหลือถูกอัปเดต · (ถ้ามี) ค่าปรับหรือบันทึกความเสียหายผูกกับรายการ
เฉลย (3) Context diagram
  • ข้อมูลการจองกิจกรรมคณะรวมอยู่ใน Borrowing request ได้ (หรือแยกเป็น Event reservation ถ้าวาด Staff เป็น entity แยก)
  • ผลอนุมัติไปถึงผู้ยืมผ่าน Email Service จึงเป็น flow Notification message ไป Email Service ไม่ใช่ลูกศรจาก Email Service ไปผู้ยืม (entity → entity ห้ามวาด)

D1. Functional หรือ Non-functional? (ถ้า NF เป็นกลุ่มไหน)

  1. The system shall allow students to cancel an order before the vendor accepts it.
  2. The menu page shall load within 2 seconds for 95% of requests.
  3. The system shall be easy to use.
  4. The system shall comply with the Personal Data Protection Act (PDPA).
  5. The system shall be developed in Python and deployed on the university's server.
  6. The system shall generate a daily sales report for each vendor.
  7. Passwords shall be stored in encrypted form.
  8. The system shall be available 99.5% of the time during office hours.

  2. NF – Product (Efficiency/Performance)
  3. NF – Product (Usability) แต่เขียนไม่ดี วัดไม่ได้ ควรเขียนเช่น "new users shall complete an order within 3 minutes without training"
  4. NF – External (Legislative)
  5. NF – Organizational (Development / Operational)
  6. F
  7. NF – Product (Security)
  8. NF – Product (Dependability)

D2. include หรือ extend? เขียนทิศลูกศรด้วย

  1. Withdraw Cash / Verify PIN
  2. Place Order / Apply Coupon
  3. Checkout / Calculate Total
  4. Book Flight / Choose Extra Baggage
  5. Register / Get Help on Registration
  6. Report Damaged Road / Attach Photo (PHTRS)
  7. Borrow Book / Check Membership Status
  8. Record Return / Charge Late Fee
เฉลย D2
  1. Withdraw Cash ─include→ Verify PIN
  2. Apply Coupon ─extend→ Place Order
  3. Checkout ─include→ Calculate Total
  4. Choose Extra Baggage ─extend→ Book Flight
  5. Get Help on Registration ─extend→ Register
  6. Attach Photo ─extend→ Report Damaged Road (โจทย์ใช้คำว่า "สามารถแนบได้")
  7. Borrow Book ─include→ Check Membership Status
  8. Charge Late Fee ─extend→ Record Return

สังเกตว่า include ชื่อ base อยู่หน้าลูกศร ส่วน extend ชื่อ base อยู่ท้ายลูกศร

D3. หาข้อผิดใน use case diagram นี้ (มี 6 จุด)

เฉลย D3
  1. Customer อยู่ในกล่อง — actor ต้องอยู่นอก system boundary
  2. "Payment Page" เป็นชื่อหน้าจอ (คำนาม) → ควรเป็น "Make Payment"
  3. "Click Next Button" เป็นขั้นตอนย่อยของ UI ไม่ใช่ business task → ตัดออก ใส่ใน narrative
  4. Verify Login → Checkout ด้วย include ทิศกลับ — ถ้า Checkout ต้อง verify ทุกครั้ง ต้องเป็น Checkout ─include→ Verify Login (หรือเขียนเป็น precondition)
  5. Checkout ─include→ Apply Discount — ส่วนลดเป็น optional ควรเป็น Apply Discount ─extend→ Checkout
  6. เส้นระหว่าง Customer กับ Admin — actor ต่อกันเองด้วย association ไม่ได้ และ Admin ไม่มี use case เลย

D4. หาข้อผิดใน context diagram นี้ (มี 5 จุด)

เฉลย D4
  1. process เลข 1 — context diagram ต้องเป็นเลข 0
  2. เส้นจาก Supplier ไม่มีชื่อ — ทุก data flow ต้องมีชื่อ
  3. Customer → Supplier "Complaint" — entity → entity ห้ามวาด ทุกเส้นต้องแตะ process
  4. "SQL Query" — ชื่อบอกวิธี implement (physical) ควรเป็นชื่อข้อมูล เช่น "Payment confirmation" · และ Bank ส่งข้อมูลเข้าในเชิงตรรกะ
  5. มี data store D1 Orders — context diagram ไม่มี data store (ไปอยู่ใน Level 1)

D5. เลือก process model

  1. ระบบคำนวณภาษีตามกฎหมาย requirement ชัด เปลี่ยนน้อย ต้องมีเอกสารให้ตรวจสอบ
  2. สตาร์ทอัปแอปส่งอาหาร ต้องออกตลาดเร็ว ฟีเจอร์เปลี่ยนตาม feedback ผู้ใช้ทุกเดือน
  3. ระบบควบคุมรถไฟฟ้าอัตโนมัติ เทคโนโลยีใหม่ ความเสี่ยงสูง งบใหญ่ มีผู้เชี่ยวชาญด้านความเสี่ยง
  4. ระบบ ERP มหาวิทยาลัยขนาดใหญ่ แบ่งเป็นโมดูลทะเบียน การเงิน บุคคล ทยอยเปิดใช้ทีละโมดูล
  5. สคริปต์เล็ก ๆ ใช้ครั้งเดียวเพื่อแปลงไฟล์
เฉลย D5
  1. Waterfall — requirement ชัดและนิ่ง เน้นเอกสาร
  2. Agile / Scrum — requirement ไม่แน่นอน ต้องเร็ว ใช้ feedback
  3. Spiral — risk-driven มี prototype ทุกรอบ
  4. Incremental (multiple release) — ระบบใหญ่ divide and conquer ส่งทีละ release
  5. Code and Fix — งานเล็กมาก

D6. ข้อใดไม่ผ่าน validation check อะไร

  1. REQ-3 บอกรหัสผ่านอย่างน้อย 8 ตัว แต่ REQ-12 บอก 6 ตัว
  2. "ระบบต้องตอบสนองเร็ว"
  3. "ระบบต้องไม่ล่มเลยตลอดไป"
  4. ระบบให้ยกเลิกตั๋วได้ แต่ไม่มี requirement เรื่องการคืนเงินเลย
  5. นักพัฒนาเพิ่มมินิเกมที่ลูกค้าไม่ได้ต้องการ
  6. ไม่รู้ว่า requirement ข้อนี้ใครเสนอ และไปอยู่ส่วนไหนของ design
  7. "ระบบจะแสดงรายงานที่เหมาะสม"

  2. Verifiability

  4. Completeness

เช็กลิสต์ 1 นาทีก่อนส่งกระดาษ

Use case diagram

  • ☐ มีกล่องพร้อมชื่อระบบ
  • ☐ actor อยู่นอกกล่อง มีชื่อ ครบทุกบทบาทในโจทย์ + ระบบภายนอก
  • ☐ use case = กริยา + กรรม ไม่ใช่ขั้นตอนย่อย
  • ☐ association เส้นทึบไม่มีหัว
  • ☐ include/extend เส้นประ มีป้าย ทิศถูก
  • ☐ ใช้ inheritance เมื่อ actor หลายตัวทำ use case เดียวกัน
  • ☐ ทุก requirement ในโจทย์มี use case รองรับ

Use case narrative

  • ☐ ครบ 8 ช่อง
  • ☐ ชื่อ/actor ตรงกับ diagram
  • ☐ precondition = สภาพ · trigger = เหตุการณ์
  • ☐ ไม่เขียน login ใน scenario ถ้าอยู่ใน precondition แล้ว
  • ☐ scenario มีเลข มีประธาน สลับ actor/ระบบ
  • ☐ exception อ้างเลข step + ระบบทำอะไรต่อ
  • ☐ postcondition = สภาพที่ตรวจได้

Context diagram

  • ☐ process เดียว เลข 0 ชื่อระบบ
  • ☐ entity = actor ทุกตัว (รวมระบบภายนอก)
  • ☐ ไม่มี data store
  • ☐ ไม่มีเส้น entity–entity
  • ☐ ทุกเส้นมีชื่อ (คำนาม, logical) มีหัวลูกศร
  • ☐ มีทั้ง input และ output
  • ☐ notation สำนักเดียว
