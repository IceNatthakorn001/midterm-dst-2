📖 อ่านฉบับเต็ม

1. CM (สไลด์ 4–5)

แก่น: initiating, evaluating, controlling change ระหว่างและหลังการพัฒนา

  • ⭐ มาตรฐาน IEEE 828 (SCM Plans) | IEEE 1042 (Guide to SCM)
  • CM ↔ Project Management (รับ planning data / ส่ง CM plan, status reports, audit results) | Product Development ส่ง work products + change requests → CM ส่ง controlled work products + approved change requests กลับ

2. Configuration item (สไลด์ 6)

แก่น: อะไรที่เปลี่ยนได้และต้องติดตาม

  • ⭐ โค้ดทุกชนิด, เอกสาร (req/analysis/design), test drivers, user/dev manuals, system config (compiler version), hardware config (CPU, bus speed)

3. Version identification (สไลด์ 7)

  • ⭐ Version numbering (V1, V1.1, V2.1 — linear, ชื่อไม่สื่อความหมาย) | Attribute-based (Date, Creator, Language, Customer, Status)

4. VCS (สไลด์ 9–11)

แก่น: ส่วนหนึ่งของ CM

  • ⭐ Purposes: 1 Restore previous configurations | 2 Coordinate changes | 3 Identify versions & components
  • ไม่มี VCS → FINAL_rev.22…doc, final-project-v2-FINALFINAL.doc

5. CVS / SVN / Git (สไลด์ 12–14)

CVS Subversion Git
repo กลาง กลาง (+ .svn ในเครื่อง) distributed (+ staging + repo ในเครื่อง)
ลง/ขึ้น ⭐ checkout / checkin ⭐ update / commit ⭐ pull / commit + push

6. Git (สไลด์ 15–16)

  • free, open-source, distributed | easy, tiny footprint, เร็ว | เหนือ SVN/CVS | cheap local branching, staging, หลาย workflow
  • ⭐ Distributed: everything local | fast | clone = backup | offline | full history

7. Staging & lifecycle (สไลด์ 17–19)

  • ⭐ staging area (index) = การเปลี่ยนแปลงที่จะ commit (Git มี ระบบอื่นไม่มี)
  • ⭐ untracked →add→ staged →commit→ unmodified →edit→ modified →add→ staged | staged →remove→ untracked
  • git add <file> | git commit -m "message" | ⚠️ สไลด์สะกด "modifed"

8. Add / Commit / Pull / Push (สไลด์ 20–23)

จาก → ไป จุดสำคัญ
⭐ Add working dir → staging เลือกว่าอะไรเข้า commit, review ก่อนได้
⭐ Commit staging → local repo เวอร์ชันใหม่ + message
⭐ Pull remote → local fetch + merge, ปกติอัตโนมัติ, conflict จัดการไม่ยาก
⭐ Push local → remote ถูก reject ได้ ถ้า remote มีของที่ local ไม่มี
  • นอก push/pull: สร้าง / integrate patch

9. Decentralized but Centralized (สไลด์ 24)

  • origin กลาง ↔ alice, bob, clair, david (push/pull) + subteam fetches ระหว่างกันเอง

10. Branch (สไลด์ 25–27)

  • ⭐ master = default, deployable, production, stable | ห้าม push ที่ไม่ test/ทำ build พัง
  • ⭐ สร้าง branch เมื่อ: feature ใหม่ | release ใหม่ | ทดลอง | แก้ bug
  • ง่าย, ชั่วคราว, สนับสนุนให้ branch, merge อัตโนมัติ | ⚠️ conflict ตอน merge, ไม่มี tool = เจ็บ → ใช้ defined workflow

11. Branching model (สไลด์ 28–33, nvie)

  • ⭐ Main: master (production-ready) | develop (latest changes for next release)
  • ⭐ Supporting:
Branch ใช้ จาก → กลับ
Feature (topic) feature ใหม่ (release ถัดไป/อนาคต) develop → develop
Release เตรียม production release, ปล่อย develop รับ feature ถัดไป, only bugfixes develop → master (tag) + develop
Hotfix แก้ด่วน production (critical bug) tag บน master → master (tag ใหม่ เช่น 1.2.1) + develop

คู่ที่มักสับสน

A B ต่างกัน
CM VCS กระบวนการ vs เครื่องมือ (ส่วนหนึ่งของ CM)
Numbering Attribute-based เลขเรียง vs ชุด attribute
Centralized Distributed repo กลาง vs ทุกคนมี repo ครบ
Add Commit → staging vs → local repo
Commit Push local vs remote
Pull Push remote→local vs local→remote
master develop production vs next release
Release Hotfix จาก develop vs จาก tag บน master
