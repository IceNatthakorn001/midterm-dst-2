1. กรณีศึกษา: เมื่อกระบวนการพัง

CrowdStrike Outage (2024): บั๊กใน Content Validator ซึ่งเป็นส่วนหนึ่งของ deployment process ปล่อยให้อัปเดตที่ผิดพลาดหลุดออกไป → เครื่อง Windows ทั่วโลกขึ้น จอฟ้า (Blue Screen) แล้ว restart วนไป บทเรียน: ตัว "ด่านตรวจ" ในกระบวนการเองก็มีบั๊กได้ ถ้าไม่มีการป้องกันหลายชั้น ความผิดพลาดเล็ก ๆ ก็ลุกลาม

Knight Capital (2012): ระบบเทรดส่งคำสั่งที่ไม่ได้ตั้งใจจำนวนมหาศาล เทรดต่อเนื่อง ~45 นาที → เสียหายมากกว่า $440 ล้าน ต้นเหตุจริงไม่ใช่แค่บั๊ก แต่เป็นความล้มเหลวของ การ deploy และการควบคุมการปฏิบัติงาน: ทดสอบไม่เพียงพอ / ไม่มี safeguards / บริหารความเสี่ยงไม่ดี

3. Layered Technology ⭐

SE เป็นชั้น ๆ ซ้อนกัน (บนลงล่าง): Tools → Methods → Process → Quality focus (ฐานของทุกอย่าง)

  • Quality focus เป็นฐาน | Process เป็นตัวยึดชั้นต่าง ๆ ไว้ด้วยกัน กำหนดกรอบการทำงาน | Methods = วิธีทำเชิงเทคนิค | Tools ช่วยให้ทำได้ง่ายหรืออัตโนมัติ

4. Process Framework vs Development Framework

A Process Framework (กล่องซ้อนกัน):

ชั้น ความหมาย
Common Process Framework กรอบใหญ่ที่ใช้ได้กับทุกโครงการ
Framework Activities กิจกรรมหลัก (requirement, design, coding, testing)
Task Sets Work tasks (งานที่ต้องทำ) + Work products (ชิ้นงาน) + Milestones, deliverables + QA checkpoints
Umbrella Activities กิจกรรมที่ครอบทุกช่วง

A Development Framework (React, Django, Laravel): Foundation (โครงสร้างพื้นฐาน ไม่ต้องเริ่มจากศูนย์) / Components and Tools (สำเร็จรูป พัฒนาเร็วขึ้น) / Best Practices and Guidelines / Customization ⚠️ Process framework = กรอบ "วิธีทำงาน" ของทีม / Development framework = "โครงโค้ด" สำเร็จรูป

5. Umbrella Activities — 8 อย่าง ⭐

(ทำต่อเนื่องตลอดโครงการ ไม่ได้อยู่ช่วงใดช่วงหนึ่ง)

  1. Software project management (POMA) 2. Formal technical reviews 3. Software quality assurance 4. Software configuration management (จัดการเวอร์ชัน เช่น Git) 5. Work product preparation and production 6. Reusability management 7. Measurement 8. Risk management

6. Process Models คืออะไร ⭐

  • เป็น framework มาตรฐาน ให้แนวทางในการ ประสานงานและควบคุม task และคนที่ทำ task
  • อธิบาย ลำดับกิจกรรม, บทบาท (roles), ชิ้นงาน (artifacts) และ workflow
  • มีไว้เพื่อ 3 อย่าง: 1. ช่วยทีม วางแผน ลงมือทำ และบริหาร 2. ทำให้ชิ้นงาน สม่ำเสมอและมีคุณภาพ 3. ช่วย สื่อสารและประสานงานระหว่าง stakeholders 💡 คำสำคัญ: coordination, tasks, people

⭐ Process model ต้องกำหนด 5 อย่าง:

  1. ชุดของ task 2. Input และ output ของแต่ละ task 3. Pre-conditions และ post-conditions 4. ลำดับการไหล ของ task 5. คนที่ทำ แต่ละ task

7. Code and Fix Model

เขียนโค้ด → คอมไพล์ → ทดสอบ → เจอปัญหากลับไปแก้ → วนจนใช้ได้ → ปล่อย ข้อสังเกต: 1. คนส่วนใหญ่ทำแบบนี้ แต่บางคนข้าม unit test หรือ debug ไปเลย 2. บางคน เริ่มทำโดยยังไม่เข้าใจ problem statement (= requirement) ⚠️ เหมาะกับงานเล็กมาก ๆ เท่านั้น — ใช้กับระบบใหญ่จะแก้ไม่จบ

8. Waterfall Model ⭐

Traditional – Linear and sequential Key Characteristics: ⭐ ช่วงต่าง ๆ ไม่ซ้อนทับกัน ต้องจบช่วงหนึ่งก่อนเริ่มถัดไป / ⭐ แต่ละช่วงผลิต deliverable ที่เป็น input ของช่วงถัดไป / เน้นเอกสารและการวางแผน

✅ Pros ❌ Cons
เรียบง่าย เข้าใจง่าย ใช้เวลาพัฒนานาน
เหมาะกับโครงการเล็กที่ requirement ชัดและไม่เปลี่ยน ไม่ยืดหยุ่น เมื่อเริ่มพัฒนาแล้วเปลี่ยนยาก
เอกสารครบ ช่วยการดูแลระยะยาว ⭐ เจอปัญหาช้า เพราะทดสอบหลังเขียนโค้ดเสร็จ
ไม่เหมาะกับ requirement ที่เปลี่ยนบ่อย

💡 เหมือน สร้างบ้าน — สร้างเสร็จแล้วอยากย้ายห้องน้ำต้องทุบใหม่ แพงมาก

9. Incremental Model ⭐

แบบ A – Integration Bucket: ⭐ แต่ละ requirement หลักพัฒนาแยกกัน ผ่านลำดับเดียวกัน (requirement → design → code → unit test) → ชิ้นที่เสร็จถูกรวมเข้า "ถังรวม (integration bucket)" อย่างต่อเนื่อง เพื่อทำ integrated system test แบบ B – Multiple Release: requirement แต่ละชุดเล็ก ๆ ถูก พัฒนา แพ็ก และปล่อยเป็นหลาย release ⚠️ ความต่าง: A รวมทุกชิ้นแล้วส่งครั้งเดียว / B ส่งให้ผู้ใช้ทีละ release

✅ Pros ❌ Cons
⭐ Divide and conquer ต้องทำงานขนานกันหลายส่วน (parallel execution)
เหมาะกับ ระบบใหญ่และซับซ้อนมาก ใช้แรงบริหารจัดการมากขึ้น
⭐ ปัญหาตอนรวมระบบ (integration challenges)

10. Spiral Model ⭐

วนเป็นเกลียว แต่ละรอบผ่าน 4 quadrant และแต่ละรอบใหญ่ขึ้นเรื่อย ๆ (ต้นทุนสะสมมากขึ้น) มีจุด "Review" คั่นระหว่างรอบ

Quadrant กิจกรรม ตัวอย่างงาน
1. Plan Next Phase วางแผนรอบถัดไป req. plan, dev plan, test plan
2. Determine Objectives, Alternatives, Constraints กำหนดเป้าหมาย ทางเลือก ข้อจำกัด –
3. Evaluate Alternatives, Identify, Resolve Risks ประเมินทางเลือก หาและแก้ความเสี่ยง risk analysis, prototype
4. Develop, Verify Next-level Product พัฒนาและตรวจสอบผลิตภัณฑ์ระดับถัดไป req. spec, design, code, unit test, sys. test

ลำดับตามเกลียว (ในสุดออกนอก): รอบแรก = แผนและ prototype → รอบกลาง = spec และ design → รอบนอกสุด = code, unit test, system test

✅ Pros ❌ Cons
บังคับให้มี prototyping และ modeling ⭐ ต้องมีผู้เชี่ยวชาญการประเมินความเสี่ยง
Iterative และ evolutionary ทุกกิจกรรม ปรับตามจำนวนความเสี่ยง
แก้สิ่งที่ทำไปในรอบก่อนได้

💡 ⭐ Spiral = ขับเคลื่อนด้วยความเสี่ยง (risk-driven) เหมาะกับโครงการใหญ่ที่เสี่ยงสูง

11. Agile และ Scrum ⭐⭐

Agile Manifesto — ให้คุณค่ากับด้านซ้ายมากกว่าด้านขวา:

✅ ให้ความสำคัญมากกว่า มากกว่า
Individuals and interactions processes and tools
Working software comprehensive documentation
Customer collaboration contract negotiation
Responding to change following a plan

⚠️ "over" ไม่ได้แปลว่า "ไม่เอา" — Agile ยังมีเอกสารและแผน แต่ให้น้ำหนักด้านซ้ายมากกว่า

Agile Processes: เป็น ตระกูล (family) ของวิธี ไม่ใช่วิธีเดียว — Short releases and iterations / Incremental design / User involvement / Minimal documentation / Informal communications / Change

Scrum (วิธีหนึ่งใน Agile):

องค์ประกอบ ความหมาย
Vision ภาพเป้าหมายของผลิตภัณฑ์
Product Backlog รายการฟีเจอร์และงานทั้งหมด เรียงตามความสำคัญ
Sprint Backlog งานที่เลือกมาทำในรอบนี้
Sprint ⭐ รอบการทำงาน 2–4 สัปดาห์
Daily Scrum Meeting ⭐ ประชุมสั้น ๆ ทุก 24 ชั่วโมง
Potentially Shippable Product Increment จบแต่ละ sprint ได้ชิ้นงานที่ พร้อมส่งมอบได้

Key Characteristics: Iterative development / Incremental delivery / Customer collaboration / Responding to change / ⭐ Cross-functional teams (ทีมที่มีทักษะครบในทีมเดียว) / Minimal documentation

✅ Pros (Agile) ❌ Cons
ยืดหยุ่นและปรับตัวสูง ต้องการทีมที่ มีประสบการณ์และมีวินัย
ส่งซอฟต์แวร์ที่ใช้ได้เร็วขึ้น ⭐ คาดการณ์ต้นทุนและเวลาได้ยาก
ลูกค้าพอใจมากขึ้น (feedback สม่ำเสมอ) ยากกับโครงการใหญ่ที่ scope ตายตัว
⭐ เจอปัญหาเร็ว เอกสารอาจไม่พอถ้าจัดการไม่ดี

12. Agile vs Traditional (Heavy) ⭐

ด้าน Agile Traditional / Heavy
Requirements สมมติว่าจะเปลี่ยน, ไม่เป็นทางการ, คุยกับผู้ใช้ตลอด สมมติว่าไม่เปลี่ยน, เอกสารครบ ละเอียด เป็นทางการ
Design ไม่เป็นทางการ, iterative เป็นทางการ, ทำล่วงหน้าทั้งหมด (upfront)
User involvement ⭐ สำคัญมาก บ่อย ⭐ แค่ตอนต้น (requirement) และตอนท้าย (acceptance test)
Documentation น้อยที่สุด, source code ก็เป็นเอกสาร เอกสารหนัก เป็นทางการ
Communication ไม่เป็นทางการ ตลอดโครงการ ผ่านเอกสาร memo และประชุมทางการ
Complexity ต่ำ สูง
Overhead ต่ำ สูง

💡 เลือกอย่างไร: requirement ชัด ไม่เปลี่ยน มีกฎหมาย/สัญญาคุม → Traditional | requirement ไม่แน่นอน ต้องแข่งขันเร็ว ลูกค้าคุยได้บ่อย → Agile

13. Spotify vs HealthCare.gov ⭐

✅ Spotify's "Squad" Model (สำเร็จ) — อยากออกฟีเจอร์ใหม่เร็วในตลาดที่แข่งขันสูง

  • Squads = ทีมเล็ก อิสระ (autonomous) และ cross-functional เป็นเจ้าของฟีเจอร์เฉพาะด้าน | Tribes = กลุ่มของ squads
  • เน้น continuous delivery, A/B testing, feedback ที่รวดเร็ว
  • ทำไมสำเร็จ: Fast iteration (ไอเดียถึงปล่อยใช้ในไม่กี่สัปดาห์) / Autonomy (ไม่ต้องรออนุมัติจากเบื้องบน) / Data-driven decisions (ข้อมูลผู้ใช้ real-time)

❌ HealthCare.gov (ล้มเหลว) — เว็บกลางให้คนอเมริกันสมัครประกันสุขภาพ

  • อ้างว่าใช้ Agile: ผู้รับจ้างหลายเจ้าทำคนละ module, ประชุมบ่อย
  • ทำไมล้มเหลว: ⭐ Fake Agile (ยังมี deadline ตายตัวและ scope มหาศาลแบบ Waterfall แต่ไม่มีวินัยการประสานงาน) / Poor integration / Late testing (ทดสอบทั้งระบบแค่ไม่กี่สัปดาห์ก่อนเปิด) / ไม่มีรอบ feedback จากผู้ใช้จริง
Factor Spotify HealthCare.gov
Iteration & Delivery รอบสั้น, continuous delivery deadline ตายตัว scope ใหญ่ ปล่อยครั้งเดียว
User Feedback A/B testing, real-time ไม่มี — ผู้ใช้ได้ลองครั้งแรกวันเปิดตัว
Team Autonomy squad ตัดสินใจเองได้ ผู้รับจ้างหลายเจ้าแยกกัน ขาดการประสาน
Integration Testing รวมและทดสอบบ่อย ประกอบแล้วใช้ไม่ได้ ทดสอบช้าเกินไป

⚠️ ⭐ บทเรียน: แค่ประชุมบ่อยไม่ได้ทำให้เป็น Agile — หัวใจคือส่งของที่ใช้ได้เป็นรอบ ๆ, ได้ feedback จริง, รวมระบบและทดสอบตั้งแต่เนิ่น ๆ

14. Process Assessment

คำถาม: องค์กรของเรามีกระบวนการ SE ที่ "โตเต็มที่ (mature)" แค่ไหน และต้องปรับปรุงไหม? องค์กรที่ช่วยประเมิน: ISO (มาตรฐาน ISO 9000 series) และ SEI (Software Engineering Institute ที่ Carnegie Mellon) (SEI พัฒนา CMM/CMMI แบ่งความ mature เป็น 5 ระดับ: Initial → Optimizing)

15. เปรียบเทียบทุกโมเดล ⭐

โมเดล ลักษณะ เหมาะกับ จุดอ่อนหลัก
Code and Fix เขียน → ทดสอบ → แก้ วนไป งานเล็กมาก มักข้าม test และไม่เข้าใจ requirement
Waterfall เรียงเส้นตรง ไม่ซ้อนทับ เอกสารเยอะ requirement ชัด ไม่เปลี่ยน โครงการเล็ก ไม่ยืดหยุ่น เจอปัญหาช้า
Incremental แบ่ง requirement เป็นชิ้น พัฒนาแยกแล้วรวม / ปล่อยหลาย release ระบบใหญ่ ซับซ้อน บริหารยาก integration ยาก
Spiral วนเกลียว 4 quadrant เน้นความเสี่ยง มี prototype โครงการใหญ่ ความเสี่ยงสูง ต้องมีผู้เชี่ยวชาญประเมินความเสี่ยง
Agile / Scrum รอบสั้น 2–4 สัปดาห์ ลูกค้ามีส่วนร่วม ยอมรับการเปลี่ยนแปลง requirement ไม่แน่นอน ต้องเร็ว คาดการณ์เวลาและเงินยาก ต้องใช้ทีมมีวินัย

คู่ที่มักสับสน

คู่ ต่างกันที่
Incremental A / B รวมใน integration bucket แล้วทดสอบทั้งระบบ / ปล่อยเป็นหลาย release
Incremental / Spiral แบ่งตาม requirement / วนรอบตามความเสี่ยง
Process framework / Development framework กรอบวิธีทำงาน / โครงโค้ดสำเร็จรูป
Agile / Traditional: user involvement ตลอดโครงการ / แค่ตอนต้นกับตอนท้าย
Real Agile / Fake Agile ส่งของเป็นรอบ มี feedback / ประชุมบ่อยแต่ scope และ deadline ตายตัว

แนวคิดที่ต้องอธิบายได้

  • ทำไม Waterfall เจอปัญหาช้า? → testing มาหลัง implementation ถ้า requirement ผิดตั้งแต่ต้น จะรู้ตอนท้าย ซึ่งแก้แพงที่สุด
  • ทำไม Incremental เหมาะกับระบบใหญ่? → divide and conquer แต่แลกกับการบริหารและ integration ที่ยากขึ้น
  • ทำไม Spiral ต้องมีผู้เชี่ยวชาญความเสี่ยง? → ทุกรอบขับเคลื่อนด้วยการวิเคราะห์ความเสี่ยง ถ้าประเมินผิดทั้งกระบวนการเสีย
  • ทำไม HealthCare.gov ล้มเหลวทั้งที่ "ใช้ Agile"? → นำแค่พิธีกรรม (ประชุมบ่อย) มาใช้ แต่ไม่มีหลักสำคัญ
  • โจทย์ "ควรใช้โมเดลไหน": ดู 3 อย่าง — requirement ชัดไหม / ระบบใหญ่และเสี่ยงแค่ไหน / ลูกค้าคุยได้บ่อยไหม
