1. UI คืออะไร ⭐

ส่วนที่ผู้ใช้เห็นชัดที่สุด (most apparent to the user) — ผู้ใช้ตัดสินซอฟต์แวร์จาก UI ก่อนสิ่งอื่น

ประเด็นหลัก 2 เรื่อง:

ประเด็น ความหมาย
1. Flow of interactions ลำดับการโต้ตอบ — ผู้ใช้ทำอะไรก่อนหลัง กดแล้วไปหน้าไหน
2. Look and feel หน้าตาและความรู้สึก — สี ฟอนต์ ปุ่ม การจัดวาง

💡 เชื่อมกับ L3: prototype ของ requirement ก็เน้น 2 เรื่องนี้ (visual looks และ flow)

2. ประเภทของ UI ⭐

ประเภท ลักษณะ ตัวอย่าง
CLI (Command-Line Interface) พิมพ์คำสั่งเป็นข้อความ developer/sysadmin ที่ต้องการควบคุมแม่นยำ — Terminal, Command Prompt
Text Menu Interface แสดงเมนูเป็นข้อความ เลือกโดยกดตัวเลข ตัวอักษร หรือลูกศร BIOS setup, POS รุ่นเก่า
GUI (Graphical User Interface) ใช้องค์ประกอบกราฟิก (ไอคอน หน้าต่าง) OS และแอปทั่วไป
Touchscreen UI โต้ตอบด้วยท่าทางสัมผัส (แตะ ปัด ซูม) สมาร์ทโฟน แท็บเล็ต ตู้ kiosk
VUI (Voice User Interface) โต้ตอบด้วยเสียงพูด Siri, Alexa
Gesture-Based → AR ซ้อนองค์ประกอบเสมือนเข้ากับสภาพแวดล้อมจริง AR นำทาง เกม การศึกษา
Gesture-Based → VR สร้างสภาพแวดล้อมเสมือนทั้งหมดให้ดื่มด่ำ เกม VR การจำลอง การฝึกอบรม

⚠️ ⭐ AR = โลกจริง + ของเสมือน (Pokémon GO) / VR = โลกเสมือนทั้งหมด (ใส่แว่นแล้วไม่เห็นโลกจริง)

3. Basic Rules — 5 ข้อ ⭐

ซอฟต์แวร์จะได้รับความนิยมมากขึ้นถ้า UI:

  1. Attractive (ดูน่าใช้ สวยงาม)
  2. Simple to use (ใช้ง่าย)
  3. Responsive in short time (ตอบสนองเร็ว)
  4. Clear to understand (เข้าใจชัดเจน)
  5. ⭐ Consistent on all interface screens (สม่ำเสมอทุกหน้าจอ)

4. UI Design Process — 4 Phases (เกลียววนซ้ำ) ⭐⭐

กระบวนการเป็น spiral วน 4 phase ซ้ำไปเรื่อย ๆ (คล้าย spiral model ใน L2)

Phase 1: User, Task, Environmental Analysis and Modeling

วิเคราะห์ 3 ด้าน โดยอิง profile ของผู้ใช้

ด้าน วิเคราะห์อะไร
User ทักษะ ความรู้ และประเภท ของผู้ใช้
Task งานที่ผู้ใช้ต้องทำ
Environment สภาพแวดล้อมทางกายภาพที่ใช้งาน

คำถามเรื่องสภาพแวดล้อม: UI จะตั้งอยู่ที่ไหนทางกายภาพ / ผู้ใช้จะนั่ง ยืน หรือทำอย่างอื่นไปด้วยไหม / hardware รองรับข้อจำกัดเรื่องพื้นที่ แสง หรือเสียงไหม / มีปัจจัยด้านมนุษย์ (human factors) พิเศษไหม

ตัวอย่าง 3 สภาพแวดล้อม:

สภาพแวดล้อม ผลต่อการออกแบบ
ช่างยืนใช้เครื่องตั้งศูนย์ล้อในอู่ (มือเปื้อน เสียงดัง) ตัวอักษรใหญ่ มองไกลได้ ปุ่มใหญ่
พนักงานออฟฟิศนั่งใช้จอ 2 จอ (เงียบ ใช้นาน ข้อมูลเยอะ) แสดงข้อมูลละเอียดได้ ใช้คีย์บอร์ดลัดได้
คนยืนกดตู้ kiosk ในห้าง (ใช้ครั้งแรก มีคนต่อคิว) touchscreen เมนูน้อย ใช้ได้ทันทีไม่ต้องเรียนรู้

💡 ⭐ ซอฟต์แวร์เดียวกันอาจต้องใช้ UI คนละแบบ ถ้าผู้ใช้และสภาพแวดล้อมต่างกัน

Phase 2: Interface Design

กำหนด ชุดของ interface objects (ปุ่ม ช่องกรอก รายการ) และ ชุดของ interface actions (กด ลาก พิมพ์) Design issues 3 เรื่อง: Response time (เร็วแค่ไหน ถ้าช้าต้องแสดงอะไร) / Command and action structure (จัดคำสั่งและเมนูให้หาเจอง่าย) / Error handling (บอกว่าผิดอะไร และแก้อย่างไร)

Phase 3: Interface Construction and Implementation

  1. เริ่มกิจกรรมการ implement → 2. สร้าง prototype → 3. ปรับปรุงการออกแบบวนซ้ำ (iterative design) ตาม feedback

Phase 4: Interface Validation

ทดสอบว่า UI: ทำ task ของผู้ใช้ได้ทุก task อย่างถูกต้อง / รองรับ task ทุกรูปแบบ (task variations) / บรรลุ requirement ทั่วไปของผู้ใช้ทั้งหมด ประเมินว่า UI: ใช้ง่าย (easy to use) และเรียนรู้ง่าย (easy to learn) แค่ไหน / ผู้ใช้ยอมรับว่าเป็นเครื่องมือที่มีประโยชน์ต่องานของเขา

5. Golden Rules (Theo Mandel) ⭐⭐

1. Place the user in control — ให้ผู้ใช้เป็นผู้ควบคุม 2. Reduce the user's memory load — ลดภาระการจำของผู้ใช้ 3. Make the interface consistent — ทำ UI ให้สม่ำเสมอ

Rule 1: Place the User in Control

หลักการ ตัวอย่าง
Define interaction modes that do not force unnecessary or undesired actions เลือก spell check mode — หน้าจอต้องแสดงว่าอยู่ในโหมดตรวจคำ และออกจากโหมดได้ง่าย
Provide for flexible interaction ใช้ คีย์บอร์ด, เมาส์, touch screen หรือเสียง ได้
Allow user interaction to be interruptible and undoable หยุดกลางคันได้ + ย้อนกลับ (undo) ได้ (Ctrl+Z)
Allow advanced users to customize their interface ตั้ง shortcut เอง, จัด toolbar
Hide technical interfaces from casual users ไม่แสดง error code หรือ stack trace กับผู้ใช้ทั่วไป
Design for direct interaction with objects on the screen ลากไฟล์ไปที่ไอคอนถังขยะเพื่อลบ

Rule 2: Reduce the User's Memory Load

หลักการ ตัวอย่าง
Reduce demand on short-term memory ให้ visual clues ช่วยให้จำได้ว่าทำอะไรไปแล้ว (ลิงก์ที่กดแล้วเปลี่ยนสี, แถบขั้นตอน 1-2-3)
Establish meaningful defaults ค่าเริ่มต้นที่สมเหตุสมผลสำหรับผู้ใช้ทั่วไป
Define shortcuts that are intuitive Ctrl + P = print, Ctrl + S = save, Cmd + C = copy
Visual layout based on a real-world metaphor ใช้ รูปบ้าน แทน "Back to home screen"
Disclose information in layers แสดงข้อมูลทั่วไปก่อน แล้วค่อยแสดงรายละเอียด

💡 ⭐ "Recognition over recall" — ผู้ใช้จำได้เมื่อเห็นง่ายกว่านึกออกเอง จึงควรแสดงตัวเลือกให้เห็น

Rule 3: Make the Interface Consistent

หลักการ ตัวอย่าง
Allow a user to put the current task into a meaningful context ผู้ใช้รู้ว่าตอนนี้อยู่ตรงไหน โดยมีตัวบ่งชี้ — window titles, graphical icons, consistent color coding
Maintain consistency across the system ปุ่ม "ยืนยัน" อยู่ตำแหน่งและสีเดียวกันทุกหน้า
Do not make changes to the existing interactive models ⭐ Ctrl + S เป็นที่รู้กันว่าคือ save อย่าเอาไปใช้กับคำสั่งอื่น

⚠️ ⭐ ความต่างของ Ctrl+S ใน 2 rule: Rule 2 = เลือกคีย์ลัดที่สื่อความหมาย (Save = Ctrl+S) / Rule 3 = เมื่อทุกโปรแกรมใช้เป็น save แล้ว อย่าเอาไปทำอย่างอื่น

6. UI Design Prototype ⭐

Low fidelity High fidelity
ลักษณะ เรียบง่าย หยาบ ๆ ละเอียดมาก มี UI element, เนื้อหา และการโต้ตอบที่สมจริง
เน้น โครงสร้างพื้นฐานและฟังก์ชัน ไม่สนรายละเอียดการออกแบบ เลียนแบบผลิตภัณฑ์จริงให้ใกล้ที่สุด บางครั้งมี animation และ transition
เหมาะกับ feedback ช่วงแรก และ brainstorming user testing ที่แม่นยำ + สาธิตงานออกแบบสุดท้าย + validate design, usability และ functionality ก่อนพัฒนาจริง
ตัวอย่าง Paper prototypes, click-through prototypes Digital code-free prototypes, coded prototypes
ต้นทุน/เวลา ต่ำ แก้ง่าย ทิ้งง่าย สูงกว่า แก้ช้ากว่า

ตัวอย่าง Low fidelity: Outlook แบบกระดาษและ post-it / สเก็ตช์ดินสอของเว็บไซต์ / Paper prototype ที่ให้คนหนึ่งเล่นเป็น "คอมพิวเตอร์" คอยสลับแผ่นกระดาษ / wireframe สีเทาใน Adobe XD ที่มีเส้นสีฟ้าเชื่อมบอก flow ⚠️ ⭐ Low fidelity ไม่ได้แปลว่าต้องเป็นกระดาษเสมอ — prototype ในโปรแกรมก็เป็น low fidelity ได้ ถ้ายังเป็นแค่โครงสีเทาที่เน้น flow

ตัวอย่าง High fidelity: 3-Panel Selector ที่มี spec ละเอียดระดับ pixel (ขนาด 176/506/496 px, ฟอนต์ Roboto Medium 14pt, รหัสสี #4C4C4C, เส้นขอบ 1px) + ระบุสถานะของ element (Selected, Static, Hover) — พร้อมส่งให้ developer สร้างตามได้ทันที

💡 ⭐ เลือกใช้เมื่อไหร่: ช่วงแรก ยังไม่แน่ใจว่า flow ถูกไหม → low fidelity (ถูก เร็ว ทิ้งได้) | ช่วงท้าย flow นิ่งแล้ว ต้องทดสอบกับผู้ใช้จริงหรือส่งให้ dev → high fidelity | ตรงกับ Phase 3 (Prototype → Iterative design)

คู่ที่มักสับสน

คู่ ต่างกันที่
Flow of interactions / Look and feel ลำดับการใช้งาน / หน้าตา
CLI / Text Menu พิมพ์คำสั่งเอง / เลือกจากเมนูที่แสดง
AR / VR ซ้อนบนโลกจริง / โลกเสมือนทั้งหมด
Phase 2 / Phase 3 ออกแบบ objects-actions / สร้าง prototype และปรับวนซ้ำ
Phase 1 / Phase 4 วิเคราะห์ผู้ใช้ก่อนออกแบบ / ทดสอบ UI หลังสร้าง
Rule 1 / 2 / 3 ผู้ใช้ควบคุมได้ / ผู้ใช้ไม่ต้องจำ / ทุกที่เหมือนกัน
Intuitive shortcuts / Don't change existing models เลือกคีย์ลัดให้เดาง่าย / อย่าเปลี่ยนคีย์ลัดที่คนคุ้นแล้ว
Low / High fidelity หยาบ เร็ว ใช้ช่วงแรก / ละเอียด สมจริง ใช้ validate ก่อนพัฒนา

แนวคิดที่ต้องอธิบายได้

  • ทำไมต้องวิเคราะห์สภาพแวดล้อม (Phase 1) → ผู้ใช้ที่ยืนในอู่ซ่อมรถ / นั่งในออฟฟิศ / กดตู้ kiosk ต้องการ UI ต่างกันมาก
  • ทำไม UI design เป็นเกลียววนซ้ำ → ต้องสร้าง prototype ไปทดสอบกับผู้ใช้ แล้วนำ feedback กลับมาวิเคราะห์และออกแบบใหม่
  • ⭐ โจทย์ "ข้อนี้ละเมิด golden rule ข้อไหน":
    • ไม่มีปุ่ม undo / ออกจากโหมดไม่ได้ → Rule 1 (user in control)
    • ต้องจำรหัสสินค้าจากหน้าก่อนมากรอกหน้านี้ → Rule 2 (memory load)
    • ปุ่มยืนยันอยู่คนละตำแหน่งแต่ละหน้า / ใช้ Ctrl+S เป็นคำสั่งลบ → Rule 3 (consistent)
  • ทำไมเริ่มจาก low fidelity → ถูกและเร็ว ได้ feedback เรื่องโครงสร้างและ flow ก่อนเสียเวลากับรายละเอียดที่อาจต้องทิ้ง
