1. Pipelining Analogy ⭐

Pipelined laundry: overlapping execution — ซักผ้า 4 ขั้น (ซัก → อบ → พับ → เก็บ)

  • ไม่ใช้ pipeline: ทำตะกร้า A ครบ 4 ขั้นก่อน แล้วค่อยเริ่ม B | ใช้ pipeline: A ย้ายไปอบเมื่อไหร่ ใส่ B ลงเครื่องซักได้ทันที
  • Four loads: speedup = 8/3.5 = 2.3 | Non-stop (n ตะกร้า): 2n/(0.5n+1.5) ≈ 4 = จำนวน stage
  • Parallelism improves performance — pipeline ไม่ได้ทำให้ตะกร้าเดียวเสร็จเร็วขึ้น แต่ทำให้เสร็จต่อชั่วโมงได้มากขึ้น (throughput)

2. RISC-V Pipeline — 5 Stages ⭐⭐

# Stage ทำอะไร
1 IF Instruction fetch จาก memory
2 ID Instruction decode & register read
3 EX Execute operation หรือ calculate address
4 MEM Access memory operand
5 WB Write result back to register

3. Pipeline Performance ⭐⭐

สมมติ register read/write = 100ps, stage อื่น = 200ps

Instr IF Reg read ALU Mem Reg write Total
ld 200 100 200 200 100 800ps
sd 200 100 200 200 – 700ps
R-format 200 100 200 – 100 600ps
beq 200 100 200 – – 500ps

(sd ไม่เขียน register / R-format ไม่ใช้ memory / beq ไม่ใช้ทั้งคู่)

Single-cycle Pipelined
Tc 800ps (พอกับคำสั่งช้าที่สุด = ld) 200ps (พอกับ stage ช้าที่สุด)
เริ่มคำสั่งใหม่ทุก 800 ps 200 ps
  • Speedup อุดมคติ = 800/200 = 4 เท่า — ไม่ถึง 5 (จำนวน stage) เพราะแต่ละ stage ใช้เวลาไม่เท่ากัน
  • ⚠️ Pipeline เพิ่ม throughput แต่ไม่ลด latency — คำสั่งเดียวใน pipeline ใช้ 5 × 200 = 1000ps ซึ่งนานกว่า 800ps ของ single-cycle ด้วยซ้ำ

4. Pipelining and ISA Design ⭐

คุณสมบัติของ RISC-V ISA ช่วย pipeline อย่างไร
ทุกคำสั่งยาว 32 บิต fetch/decode ใน 1 cycle ง่ายกว่า (x86 คำสั่งยาว 1–17 bytes)
รูปแบบคำสั่งน้อยและสม่ำเสมอ decode + อ่าน register ได้ในขั้นเดียว
Load/store addressing คำนวณ address ใน stage 3 และเข้าถึง memory ใน stage 4

5. Hazards ⭐⭐

สถานการณ์ที่ทำให้เริ่มคำสั่งถัดไปใน cycle ถัดไปไม่ได้

Hazard สาเหตุ วิธีแก้
Structure ทรัพยากรที่ต้องใช้ไม่ว่าง แยก instruction memory กับ data memory (หรือ split I-cache/D-cache)
Data ต้องรอคำสั่งก่อนหน้าอ่าน/เขียนข้อมูลเสร็จ Forwarding, stall, code scheduling
Control การตัดสินใจว่าจะทำอะไรต่อขึ้นกับผลของคำสั่งก่อนหน้า Branch prediction, ย้ายการตัดสิน branch ไป ID

Structure Hazard

ถ้ามี memory เดียว: load/store ต้องเข้า data memory → instruction fetch ต้อง stall → เกิด pipeline "bubble" → ต้องแยก instruction/data memory

Data Hazard & Forwarding ⭐

add x19, x0, x1
sub x2, x19, x3     ← ต้องใช้ x19 แต่ add ยังไม่เขียน (เขียนตอน WB)
  • Forwarding (bypassing): ใช้ผลลัพธ์ทันทีที่คำนวณเสร็จ ไม่ต้องรอเก็บลง register ก่อน — ต้องเพิ่มเส้นทางเชื่อมใน datapath
  • Load-use data hazard: forwarding ไม่ช่วยทุกกรณี — "Can't forward backward in time!" เพราะ ld ได้ค่าตอนปลาย MEM แต่คำสั่งถัดไปต้องใช้ตอนต้น EX (เวลาเดียวกัน)

Code Scheduling to Avoid Stalls ⭐

C: a = b + e; c = b + f;

โค้ดเดิม (13 cycles) โค้ดเรียงใหม่ (11 cycles)
ld x1, 0(x0) ld x1, 0(x0)
ld x2, 8(x0) ld x2, 8(x0)
stall → add x3, x1, x2 ld x4, 16(x0) ← ย้ายขึ้นมา
sd x3, 24(x0) add x3, x1, x2
ld x4, 16(x0) sd x3, 24(x0)
stall → add x5, x1, x4 add x5, x1, x4
sd x5, 32(x0) sd x5, 32(x0)

นับ cycle: 7 คำสั่ง, pipeline 5 stage = 5 + (7−1) = 11 cycles; + stall 2 = 13

Control Hazard & Branch Prediction

  • branch กำหนดว่าจะทำคำสั่งไหนต่อ → pipeline fetch คำสั่งที่ถูกต้องไม่ได้เสมอ เพราะ branch ยังอยู่ที่ ID
  • Stall on branch: รอจนรู้ผลแล้วค่อย fetch → or ถูก fetch ช้าไป 400ps แทน 200ps = เสีย 1 cycle
  • Branch prediction: pipeline ยาวขึ้นรู้ผล branch เร็วไม่ได้ → stall penalty สูงจนรับไม่ได้ → เดาผล แล้ว stall เฉพาะตอนเดาผิด | RISC-V เดาว่า branch not taken → fetch คำสั่งถัดไปได้เลย
Static branch prediction Dynamic branch prediction
วิธี ดูจากพฤติกรรมทั่วไปของ branch hardware วัดพฤติกรรมจริง เก็บประวัติล่าสุดของแต่ละ branch ถือว่าอนาคตเป็นไปตามแนวโน้มเดิม
กฎ backward branch → เดา taken (ท้าย loop), forward branch → เดา not taken ถ้าเดาผิด: stall ระหว่าง fetch ใหม่ แล้ว อัปเดตประวัติ

6. Pipeline Summary (BIG Picture)

  • pipelining เพิ่มประสิทธิภาพด้วยการเพิ่ม instruction throughput (ทำหลายคำสั่งพร้อมกัน) แต่ละคำสั่งยังมี latency เท่าเดิม
  • มี hazards: structure, data, control | การออกแบบ instruction set มีผลต่อความซับซ้อนของ pipeline

7. Pipelined Datapath & Pipeline Registers

  • ข้อมูลส่วนใหญ่ไหล ซ้ายไปขวา (IF → WB) — การไหลขวาไปซ้ายทำให้เกิด hazards มี 2 จุด:
    • WB → ID (เขียนผลกลับ register) = data hazard
    • MEM → IF (ส่งผล branch กลับไปเลือก PC) = control hazard
  • Pipeline registers 4 ตัว: IF/ID, ID/EX, EX/MEM, MEM/WB — เก็บข้อมูลที่ stage ก่อนหน้าสร้างไว้ใน cycle ที่แล้ว (ตั้งชื่อตาม stage สองฝั่งที่คั่น)

8. Pipeline Operation ทีละ Stage

  • IF: อ่านคำสั่งจาก instruction memory ตาม PC + คำนวณ PC + 4 → เก็บลง IF/ID
  • ID: อ่านค่า register 2 ตัว + sign-extend immediate → เก็บลง ID/EX (รวมค่า PC)
  • EX (load): ALU บวก base register + offset → ได้ address → เก็บลง EX/MEM
  • MEM (load): อ่าน data memory → เก็บลง MEM/WB
  • WB (load) ⚠️: เขียนค่ากลับ register — ปัญหา: เลข register ปลายทางมาจาก IF/ID ปัจจุบัน ซึ่งเป็นคำสั่งอื่นแล้ว = wrong register number
  • แก้: ส่งเลข rd ตามไปกับ pipeline register ID/EX → EX/MEM → MEM/WB 💡 หลักสำคัญ: ข้อมูลที่ stage ถัดไปต้องใช้ ต้องถูกส่งต่อไปกับ pipeline register ไม่งั้นถูกคำสั่งใหม่เขียนทับ
  • EX (store): ALU คำนวณ address + ส่งค่าจาก rs2 ที่จะเขียนต่อไปที่ EX/MEM
  • MEM (store): เขียนข้อมูลลง data memory | WB (store): ไม่ทำอะไร (sd ไม่เขียน register)

Pipeline diagrams: Multi-clock-cycle = การทำงานตามเวลา (แบบรูปทรัพยากร IM/Reg/ALU/DM หรือแบบเขียนชื่อ stage IF ID EX MEM WB เลื่อนทีละ cycle) | Single-clock-cycle = สถานะของ pipeline ใน cycle ที่กำหนด (ในแต่ละ stage มีคำสั่งไหนอยู่)

Pipelined Control: สัญญาณควบคุมถูกสร้างตอน ID จาก opcode แล้วส่งต่อไปกับ pipeline register

  • EX: ALUOp, ALUSrc | MEM: Branch, MemRead, MemWrite | WB: MemtoReg, RegWrite

9. Data Hazards: Forwarding ⭐⭐

sub x2, x1, x3
and x12, x2, x5     ← ต้อง forward (กรณี 1a: EX/MEM)
or  x13, x6, x2     ← ต้อง forward (กรณี 2b: MEM/WB)
add x14, x2, x2     ← cycle เดียวกับ WB: register เขียนครึ่งแรก อ่านครึ่งหลัง จึงได้ค่าถูก
sd  x15, 100(x2)    ← มาหลัง WB แล้ว ไม่มีปัญหา

เงื่อนไขตรวจจับ

ส่งเลข register ไปตาม pipeline — operand ของ ALU ใน EX คือ ID/EX.RegisterRs1 และ ID/EX.RegisterRs2

กรณี เงื่อนไข forward จาก
1a EX/MEM.RegisterRd = ID/EX.RegisterRs1 EX/MEM
1b EX/MEM.RegisterRd = ID/EX.RegisterRs2 EX/MEM
2a MEM/WB.RegisterRd = ID/EX.RegisterRs1 MEM/WB
2b MEM/WB.RegisterRd = ID/EX.RegisterRs2 MEM/WB

เพิ่มเติม: forward เฉพาะเมื่อ EX/MEM.RegWrite / MEM/WB.RegWrite = 1 (เขียน register จริง) และ RegisterRd ≠ 0 (⚠️ เพราะ x0 เป็น 0 เสมอ ถ้า forward จะได้ค่าผิด)

Forwarding Conditions ⭐

Mux control Source ความหมาย
ForwardA/B = 00 ID/EX มาจาก register file (ไม่ forward)
ForwardA/B = 10 EX/MEM forward จากผล ALU ของคำสั่งก่อนหน้า
ForwardA/B = 01 MEM/WB forward จาก data memory หรือผล ALU ที่เก่ากว่า

💡 จำ: 10 = ใกล้กว่า (EX/MEM), 01 = ไกลกว่า (MEM/WB), 00 = ไม่ forward Forwarding unit รับ Rs1/Rs2 จาก ID/EX และ Rd + RegWrite จาก EX/MEM และ MEM/WB → ควบคุม mux ForwardA/ForwardB หน้า ALU

Double Data Hazard ⭐

add x1, x1, x2
add x1, x1, x3
add x1, x1, x4

เกิด EX hazard และ MEM hazard พร้อมกัน (ชี้ไป x1 ทั้งคู่) → ต้องใช้ค่าล่าสุด = EX/MEM ปรับเงื่อนไข: forward จาก MEM/WB ก็ต่อเมื่อเงื่อนไข EX hazard ไม่เป็นจริง

if (MEM/WB.RegWrite
    and (MEM/WB.RegisterRd ≠ 0)
    and not(EX/MEM.RegWrite and (EX/MEM.RegisterRd ≠ 0)
            and (EX/MEM.RegisterRd = ID/EX.RegisterRs1))
    and (MEM/WB.RegisterRd = ID/EX.RegisterRs1)) ForwardA = 01

อ่าน 4 ข้อ: 1. คำสั่งใน MEM/WB เขียน register จริง 2. rd ไม่ใช่ x0 3. ไม่มี EX hazard ที่ชี้ไป register เดียวกัน (มีเมื่อไหร่ EX/MEM ชนะ) 4. rd ตรงกับ Rs1/Rs2 ของคำสั่งใน EX

10. Load-Use Hazard Detection & Stalling ⭐⭐

ตรวจตอนที่คำสั่งที่ใช้ค่าถูก decode อยู่ใน ID stage — operand ใน ID คือ IF/ID.RegisterRs1, IF/ID.RegisterRs2

ID/EX.MemRead and
  ((ID/EX.RegisterRd = IF/ID.RegisterRs1) or
   (ID/EX.RegisterRd = IF/ID.RegisterRs2))

(ID/EX.MemRead = 1 แปลว่าคำสั่งใน EX เป็น ld)

วิธี stall ⭐ 3 ข้อ:

  1. บังคับสัญญาณควบคุมใน ID/EX register ให้เป็น 0 → EX, MEM, WB ทำ nop = bubble
  2. ไม่ให้อัปเดต PC และ IF/ID register → คำสั่งที่ใช้ค่าถูก decode ซ้ำ, คำสั่งถัดไปถูก fetch ซ้ำ
  3. stall 1 cycle ทำให้ MEM อ่านข้อมูลของ ld ได้ทัน → จากนั้น forward ไป EX stage ได้

Hazard detection unit (ที่ ID stage): รับ ID/EX.MemRead, ID/EX.RegisterRd, IF/ID.RegisterRs1/Rs2 → ส่ง PCWrite และ IF/IDWrite เพื่อหยุดการอัปเดต + ควบคุม mux ที่เลือก control = 0 Stalls and Performance: stall ทำให้ประสิทธิภาพลดลง แต่จำเป็นเพื่อผลลัพธ์ที่ถูกต้อง | compiler จัดเรียงโค้ดเลี่ยง hazard ได้ แต่ต้องรู้โครงสร้างของ pipeline

11. Control Hazards: Branch ⭐⭐

ถ้ารู้ผล branch ตอน MEM stage: pipeline fetch มาแล้ว 3 คำสั่ง (40 beq, 44 and, 48 or, 52 add) → ถ้า taken ต้อง Flush these instructions (set control values to 0) แล้ว PC ไปที่ 72

Reducing Branch Delay ⭐: ย้าย hardware ตัดสิน branch มาไว้ที่ ID stage

  • Target address adder (บวกหา address ปลายทาง) + Register comparator (เปรียบเทียบ register)
36:  sub x10, x4, x8
40:  beq x1, x3, 16    // PC-relative → 40 + 16*2 = 72
44:  and x12, x2, x5
48:  or  x13, x2, x6
52:  add x14, x4, x2
56:  sub x15, x6, x7
72:  ld  x4, 50(x7)

target = 40 + 16 × 2 = 72 (offset ของ branch ใน RISC-V คูณ 2 — เชื่อมกับ SB-format)

  • Clock 3: and อยู่ IF, beq อยู่ ID (comparator พบ x1 = x3 → taken, adder คำนวณ target 72), sub อยู่ EX → ยก IF.Flush ล้างคำสั่ง and ที่ fetch ผิด
  • Clock 4: ld x4, 50(x7) อยู่ IF (fetch จาก 72), Bubble (nop) อยู่ ID, beq อยู่ EX, sub อยู่ MEM
  • เสียไปแค่ 1 cycle (เทียบกับ 3 cycles ถ้าตัดสินที่ MEM)
