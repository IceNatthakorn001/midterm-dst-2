⚡ สรุปสั้น · Lecture 3 — CPU (Process) Scheduling

📖 อ่านฉบับเต็ม📝 ทำแบบทดสอบ

คำถามหลักของบท: เมื่อ OS สลับ process แล้ว จะเลือก process ไหนมารันต่อ → scheduling policy

1. พื้นฐาน

  • Process ทำงานเป็นวงจร CPU burst ↔ I/O burst; ขณะ I/O CPU ว่าง = BAD → switch ไป process อื่น = GOOD
  • CPU-bound: คำนวณมาก burst น้อยครั้งแต่ยาว / I/O-bound: I/O มาก burst สั้นแต่ถี่
  • Multiprogramming: Descheduling (Running→Ready) + Scheduling (Ready→Running) → ภาพลวงว่ามี CPU หลายตัว
  • ต้อง schedule เมื่อ: yield, block (I/O), สร้าง child แล้วรอ, terminate, timer interrupt
  • Queueing diagram: ready queue → CPU → ออกเพราะ I/O request (I/O queue) / time slice expired / fork a child / wait for an interrupt → กลับ ready queue

2. เป้าหมาย & Metrics ⭐

ระบบ เป้าหมาย
ทุกระบบ Fairness, Policy enforcement, Balance
Batch Throughput, Turnaround time, CPU utilization
Interactive Response time, Proportionality
Real-time Meeting deadlines (ไม่เสียข้อมูล), Predictability (ไม่เสียคุณภาพ)
  • Turnaround = T_completion − T_arrival = CPU time + waiting time
  • Waiting = เวลารอใน ready queue
  • Response = T_first run − T_arrival (แค่ได้รันครั้งแรก ไม่ใช่ output ทั้งหมด)
  • อัลกอริทึมที่ดี: Max utilization, throughput / Min turnaround, waiting, response
  • ตัวอย่างสไลด์ 14: P1 wait 0 TAT 24, P2 wait 24 TAT 27, P3 = ? (ถ้า P3=3 → wait 27, TAT 30)

3. อัลกอริทึม ⭐

อัลกอริทึม หลัก Preempt? จุดเด่น/ปัญหา
FIFO/FCFS มาก่อนได้ก่อน ❌ Convoy effect (งานสั้นติดหลังงานยาว)
SJF งานสั้นสุดก่อน ❌ ดีต่อ turnaround แต่แย่ถ้างานสั้นมาทีหลัง
STCF เหลือเวลา น้อยสุดก่อน ✅ แก้ late arrival ของ SJF
Priority เลขน้อย = priority สูง – Starvation
RR วนคนละ q ✅ response ดี + fairness ดีเยี่ยม / turnaround แย่
  • Non-preemptive = ถือ CPU จนจบหรือเข้า waiting (FIFO, SJF) / Preemptive = ถูกแย่งได้โดย clock หรือ process priority สูงกว่า
  • RR: q ใหญ่ไป ⇒ กลายเป็น FIFO / q เล็กไป ⇒ context switch overhead สูง / q ควรใหญ่กว่าเวลา context switch มาก (slice 10ms + switch 1ms ≈ เสีย 10%)
  • process time 10: q=12 → 0 switch, q=6 → 1, q=1 → 9

4. Incorporating I/O

  • process ถูก block → รันตัวอื่น; I/O เสร็จ → อาจรันตัวที่ขอ I/O ทันที → overlap CPU กับ I/O
  • A,B ใช้ CPU 50; A ใช้ disk 10ms ทุก 10ms
    • ไม่ overlap: (90+140)/2 = 115
    • STCF มอง A เป็น sub-job 10ms, B ถูก preempt เมื่อ A พร้อม: (90+100)/2 = 95

5. MLFQ ⭐

  • Motivation: SJF/STCF ดีต่อ turnaround แต่ OS ไม่รู้ความยาวงาน; RR ดีต่อ response แต่ turnaround แย่ → ต้องการทั้งสองอย่างโดยไม่รู้ความยาวงาน
  • โดย Corbato et al.; หลายคิวหลาย priority, แต่ละคิวใช้ RR, เริ่มที่คิวบนสุด ลดลงเมื่อใช้ slice หมด
Rule สาระ
1 Priority(A) > Priority(B) → A รัน
2 เท่ากัน → RR ด้วย quantum ของคิวนั้น
3 งานใหม่ → คิวบนสุด
4 ใช้ time allotment ของชั้นหมด (ไม่ว่าจะปล่อย CPU กี่ครั้ง) → ลด 1 คิว — กันโกง (gaming)
5 ทุกช่วง S → ทุกงานกลับคิวบนสุด (priority boost) — กัน starvation + รับมือพฤติกรรมเปลี่ยน
  • Simple example: งานยาวตกไป Q0; งานสั้นมาที่ T=100 เข้า Q2 แย่ง CPU แล้วเสร็จเร็ว → เลียนแบบ SJF
  • Intensive I/O: งาน interactive ปล่อย CPU ก่อนหมด slice → อยู่ Q บนตลอด (ประมาณ priority จากความยาว burst)
  • Config ตัวอย่าง: Q0 RR q=8ms → Q1 RR q=16ms → Q2 FCFS (ไม่เสร็จใน 8 → ลง Q1 ได้อีก 16 → ไม่เสร็จ → ลง Q2)

6. OS จริง

Linux 2.6+

  • Real-time: SCHED_FIFO, SCHED_RR (preemptive priority, สูงกว่า Normal) / Normal: SCHED_OTHER, SCHED_BATCH → CFS
  • CFS: เลือก task vruntime ต่ำสุด, รัน 1 slice แล้วใส่กลับ runqueue, ใช้ Red-Black Tree
  • nice −20 (สูงสุด) ถึง +19 (ต่ำสุด); nice 0: physical = virtual; nice ต่ำ: physical > virtual; nice สูง: physical < virtual

Windows

  • priority-based preemptive; รันจน block / หมด slice / ถูก thread priority สูงกว่าแย่ง; real-time preempt non-real-time ได้
  • 32 ระดับ: variable 1–15, real-time 16–31, 0 = memory-management thread; มีคิวต่อ priority
  • ตาราง class × relative: เช่น real-time/normal = 24, normal/normal = 8, high/normal = 13, idle/normal = 4, time-critical = 31 (real-time) หรือ 15 (คลาสอื่น), idle = 16 (real-time) หรือ 1
  • quantum หมด → ลด priority (ไม่ต่ำกว่า base); wait → boost ตามสิ่งที่รอ; foreground window ×3
